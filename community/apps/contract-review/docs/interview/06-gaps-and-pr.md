# 已知限制与交付说明

## 1. 已知限制（都是真的，不是客套）

### 1.1 模型输出不确定：同一份合同两次抽取结果不同

失败重试场景里第二轮抽出的条款与第一轮并不完全一致：第一轮 `payment` 判 `medium`
（关注 50% 预付款），第二轮判 `high`（关注 24 个月无息质保金）。

这是 LLM 的固有属性，不是 bug，但对**业务可用性**有直接影响：同一个合同审两次得到不同建议，
用户会困惑。当前版本没有处理这一点。可能的做法（未实现）：落库时记录模型与提示词版本、
同一审查单固定一次抽取结果、或对同一合同做多次抽取取交集/并集。

### 1.2 超时判定是「惰性」的，不是后台定时任务

`failStaleExtractions` 只在**有人读视图时**才执行。因此如果一份审查单卡在 `extracting`
且之后没有任何人打开工作台，它会一直停在 `extracting`，直到下一次有人读。

这是刻意的取舍（见 `contract-review.service.ts` 的注释）：避免引入定时器与额外的生命周期复杂度，
且宿主重启后失败态不会丢。代价是状态推进依赖"有人来看"。

### 1.3 条款序号可能重复（影响很小）

`recordClause` 用 `count()` 作为下一个 `sequence`。当 Agent 并发提交多条 `record_clause`
时可能算出相同的序号——本次验证中确实观察到了两条 `sequence = 2` 的条款。

影响可控：`getCase` 的排序是 `sequence ASC, createdAt ASC`，有 `createdAt` 兜底，展示顺序仍稳定。
正确做法是用数据库序列或 `MAX(sequence)+1` 加锁。

### 1.4 视图 manifest 里的 `defaultPageSize` 是注册时快照

修好配置读取后，`defaultPageSize` 在**运行时**（列表分页）改配置立刻生效，
但视图 manifest 中 `dataSource.querySchema.defaultPageSize` 由宿主在插件注册时缓存，
改配置不会刷新它，需重装/重启插件。

### 1.5 明确不做的（范围取舍）

| 不做 | 理由 |
| --- | --- |
| PDF / Word 解析 | 粘贴文本已足以验证核心流程；文件解析属于接入层，会显著膨胀范围 |
| 全文问答 / 聊天式合同助手 | 那是聊天机器人，不是业务应用；评分标准明确排除纯问答 |
| 多用户权限、审批流 | 超出 2–6 小时建议范围，且不是核心流程的必要条件 |
| 合同模板比对、条款库、历史版本 diff | 属于"功能更多"，评分标准明确说明不因此加分 |

### 1.6 没有自动化测试

`pnpm test` 目前只跑类型检查（`tsc --noEmit` ×2），没有单元测试或集成测试。
本次验证全部是手工 + 脚本化的端到端验证（脚本见 `02-runbook.md` 中的命令）。
对一个 2–6 小时范围的交付，我认为"把端到端流程跑通并留下可重跑证据"优先于补单测；
但如果要继续演进，`saveReview` 的部分保存闸门与 `recordClause` 的幂等覆盖策略
是最该先补测试的两个函数——它们的边界条件最容易写错。

### 1.7 运行环境限制

- **API 必须用 Node 启动，不能用 Bun**（原因见 [`02-runbook.md`](./02-runbook.md) §1）。
- 插件代码改动后需要「重新构建 + 重新安装 + 重启 API」三步才生效，
  单副本本地开发下平台的自动收敛会判定 `already-current` 而不真正重启。
