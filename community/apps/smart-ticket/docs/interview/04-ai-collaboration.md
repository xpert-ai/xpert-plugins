# AI 开发协作与技术复盘

---

## 一、 AI 工具与模型选型

在本次任务开发中，我们结合 AI 辅助编码工具推进工程实现与架构设计：
* **开发辅助环境**：AI Agent 辅助编程工具。
* **主要协助环节**：技术方案设计、NestJS 插件架构搭建、TypeORM 实体映射、Remote Component 前端交互设计、自动化测试用例编写与多层兼容性问题排查。

## 二、 代表性协作场景与工程决策

| 协作场景 | AI 最初的方案 / 行为 | 候选人的判断、纠偏与最终方案 | 工程经验与收获 |
| :--- | :--- | :--- | :--- |
| **1. 业务场景设计与范围收敛** | AI 最初提议对接复杂的外部 Salesforce / Jira OAuth 认证体系。 | **果断否决过度设计**：题目明确建议投入 2–6 小时，聚焦一个可靠、范围合理的小闭环。外部授权不仅受限于网络环境，还会分散核心考核点的注意力。最终收敛为“客诉提取 $\to$ 优先级/情绪打标 $\to$ 回复建议 $\to$ 工作台人工复核 $\to$ 持久化落库”的小闭环。 | **克制是做产品的第一准则**。一个坚实、可靠、能够完整复现的小闭环，远胜于半成品的大而全系统。 |
| **2. 官方实体命名检查排错** | AI 在编写 TypeORM 实体时使用了动态函数命名 `@Entity(tableName(...))`。 | **深入阅读官方构建脚本**：发现官方 `check-entity-names.mjs` 使用了硬编码的静态正则 `/@Entity\(\s*['"`]([^'"`]+)['"`]/g`，若非字面量字符串且非 `plugin_*` 开头则直接退出构建失败。立即重构为 `@Entity('plugin_smart_ticket_record')`，一次性通过校验。 | **永远先看构建与 CI 检查脚本的底层实现**，避免依赖假设。 |
| **3. Remote Component 架构落地** | AI 试图引入庞大的 Webpack / Vite 外部打包流，容易导致构建链路断裂。 | **参考官方优秀设计，采用 IIFE + React UMD 极简无构建方案**：参考官方 `procurement-quote-comparison`，利用 `@xpert-ai/plugin-sdk` 的 `renderRemoteReactIframeHtml`，直接注入纯净的现代化 React UI，既保证了 iframe 隔离安全与 postMessage 通信性能，又实现了秒级构建。 | **保持打包流水线尽可能轻量自洽**，降低部署与审阅者的复现成本。 |
| **4. Node.js 版本模块加载排错** | 在 Node 18 环境下运行测试时，上游 CJS 产物 `require('lodash-es')` 抛出 `ERR_REQUIRE_ESM` 致命错误。 | **对照文档建议并运用多版本环境定位**：文档特别提示“Node.js、包管理器和 SDK 版本以项目配置及测试平台版本为准”，Node 20 对 ESM 互操作性具有更成熟的支持。通过 `nvm use 20.20.0` 切换至 Node 20 后，9 项测试全部顺利通过。 | **严格遵循框架官方指定的基础环境矩阵**，不要在底层运行时不匹配的泥潭里盲目打补丁。 |
| **5. 失败重试的幂等性设计** | AI 最初设计的重试逻辑是每次重试都调用一次新建逻辑。 | **纠正为按 Ticket ID 更新现有草稿**：如果不做幂等控制，用户点击重试会导致数据库出现多条同名且未完成的垃圾数据。最终方案为在重试时更新同一记录的 `failureCode` 与 `retryCount`，彻底消除脏数据。 | **容灾重试必须与业务状态幂等性绑定**。 |

## 三、 候选人总结与思考

在与 AI 的深度协同中，AI 极大地加速了样板代码的搭建（如 Zod Schema、NestJS Decorator、TypeORM 字段定义与测试用例模板），但**关键的技术边界判断、平台规范对照、模块解耦与异常防护逻辑，必须由工程师把关**。

通过本次实作，不仅加深了对 Xpert 平台“智能体中间件（Middleware） + 工作台（Workbench） + 模板（DSL）”三位一体 Agentic App 架构的理解，也验证了高效的人机协作研发范式。
