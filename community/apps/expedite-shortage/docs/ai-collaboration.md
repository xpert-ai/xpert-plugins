# AI 协作说明

## 工具和模型

| 阶段 | 工具 | 做了什么 |
|---|---|---|
| 规划（11-12） | Claude（Cowork 对话，Opus 系列模型） | 读题目、读示例源码和 Xpert Skills，写产品设计、技术方案、开发计划 |
| 开发与验证（11-12～11-16） | Claude Code 桌面版（Opus 系列模型） | 搭 WSL2 平台环境、写代码和单测、读平台源码核实接口、操作数据库和日志做验证、写文档 |
| 插件里的智能体 | DeepSeek `deepseek-v4-flash`（在 Xpert 里配置） | 实际执行缺料分析 |

Xpert Skills 用了 `xpert-agentic-app-developer`、`xpert-plugin-development`、`xpert-platform-local-environment` 三个，作为 AI 写代码时的依据。

整个过程我都让 AI 写一份开发记录，每一步按四类记：**介绍**（我怎么把需求交代给 AI）、**选择**（我对 AI 建议的取舍）、**定位**（问题怎么一起查）、**验证**（怎么确认结果）。下面挑几段有代表性的。

## 一、我怎么把需求和背景介绍给 AI

- **规划和开发分成两个对话。** 规划对话只写文档，开发在本机 Claude Code 里做。每个对话开头用一份启动 prompt 交代背景、必读文件、产出和规则，先让 AI 复述它理解的题目和完成标准，再动手。上下文快满时，让 AI 写一份“续接 prompt”，新对话贴进去就能接着做。
- **不让 AI 凭记忆写 Xpert 接口。** 要求它先克隆插件仓库、Skills 仓库和平台仓库的相关目录，所有结论都注明依据的文件和行号，没读到的标“未核实”。技术方案最后有一张“未核实清单”，开发时逐条回填。比如 `assistant.chat.send_message` 是直接发送还是只填进输入框，就是读了平台前端源码才确定的（直接发送，而且支持 `newThread`）。
- **给 AI 定边界。** 凭证 AI 不读也不回显：部署要登录时，我在自己的终端里用 `read -s` 设置账号密码。push、建 PR、联系任何人之前都要先给我看。我外出期间授权它连续推进，但只能本地提交、不部署；遇到需要拍板的事先选最保守的做法，并记进“待确认”。

## 二、对 AI 建议的选择和调整

- **主数据放哪。** AI 初稿建议“存表 + 首次访问时按组织写种子”（参照 `crm`）。我拿不准，让它把两种做法讲清楚再定。它读完 `crm` 和 `smart-maintenance` 后改了建议：主数据（BOM、库存）在流程里只读，用代码常量 + 数据源接口就够；业务数据（请求、任务、结论）存表。它还更正了自己初稿里“常量会让恢复讲起来弱”的说法：恢复考的是业务数据，和主数据放哪无关。我采纳了。
- **示例不等于规范。** AI 对照 Skill 发现参考示例 `smart-maintenance` 有几处旧写法（有数据表却用 organization 级别、工具 schema 不严格、手写 2000 多行的 `app.js`）。后来在平台上实际部署它，被平台拒绝安装（HTTP 400），原因是平台 11-02 新加了命名空间规则。我们的设计一开始就按 Skill 走（tenant 级别 + `expedite_shortage` 命名空间），所以没受影响。开发时 AI 又把参考示例换成更新的 `material-identity-governance`。
- **AI 主动改了两处我已经拍板的设计**，并在文档里写了修订说明：
  - 工具只接收 `analysisJobId`。Skill 要求模型只提供需要它判断的参数。
  - 演示故障从“第一次调用失败”改为“第 1 次分析内都失败”。Skill 要求智能体自己判断是否重试，只坏一次调用会被它当场重试掉，演示不出失败状态。
- **没让 AI 绕过问题。** 平台环境搭建时，沙箱镜像的依赖下载反复失败。AI 给了“先跳过沙箱”和“只在本地改 Dockerfile 副本（换镜像源、调大超时）”两个方案，我选了后者：仓库文件不改，所有哈希校验照常执行。参考示例装不上时，我也没让 AI 去改示例代码，而是换一个符合规则的示例（dockyard）验证平台流程：改得越多，证明的就越是“改过的版本能跑”。

## 三、遇到问题怎么一起定位

- **递归上限。** 第一次真实分析在提交总结论之前报“已达到递归次数 40 限制”。AI 查了插件的日志表，确认 2 条结论已经保存、任务仍在运行，再结合平台的计步方式判断：每轮“模型 → 工具”还要经过两个中间件的钩子，7 轮工具调用超过了 40 步。模板改为 100，并加单测检查下限。
- **任务卡住。** 递归报错后任务一直是“分析中”，只能等 3 分钟超时。这是“分析中不新建任务”的防重复设计带来的副作用。我们加了“放弃本次分析”：这是工作台动作，不是工具，模型调不到；它带上界面看到的任务 ID，防止误放弃更新的任务；用和超时同一个条件更新，智能体之后迟到的写入会被拒绝。
- **平台数据丢失。** 11-16 重启电脑后平台数据库是空的。AI 用一次性容器只读检查了真正的挂载目录，查出原因：Docker Desktop 比 WSL 先启动，数据库一直写在 Docker 的临时目录里。经我同意后修好挂载、清掉 Redis 里残留的旧插件版本记录，我重新初始化账号和模型，然后在空库上把验证从头走了一遍。处理步骤写进了本地的环境恢复备忘。
- **AI 的记录也会错。** 阶段 6 核对数据库时，AI 发现自己阶段 5 写的“SO-1040 重试正常跑完”和实际不符：那个任务一直是 queued，运行在 2 秒后被中断。它把这条更正写进了开发记录，没有直接拿旧结论写验证文档。

## 四、怎么确认作品符合预期

- **分四层验证**，每层单独记录“操作、预期、实际”：单测与构建 → harness 加载 → 界面 → 平台业务流程。构建通过不等于加载成功，加载成功也不等于用户操作成功。详见 [validation.md](validation.md)。
- **截图之外再查数据库。** 每次平台操作后，AI 用只读 SQL 核对任务数、状态、错误码和结论条数，和截图一一对应。例如 SO-1031 库里有 2 个任务，只有第 2 个有结论，界面也只显示第 2 个。
- **截图也要检查。** 截图时浏览器自动翻译把工具返回的 JSON 改坏了（字段名被翻成“成功：错误的”），AI 检查截图时发现了，我关掉翻译后重截。

## 工具使用中的限制

- **上下文长度**：一个对话撑不完整个开发，靠开发记录和续接 prompt 在对话之间交接。
- **Windows 和 WSL**：AI 在 Windows 侧执行 WSL 命令，要先把脚本写到临时目录再调用 `wsl.exe`；用 `setsid nohup` 放到后台的进程会在 `wsl.exe` 退出时被一起结束，改为在后台任务里前台运行。
- **需要人做的事**：登录、配置模型、部署时输入凭证、截图，都是我自己做的。
