# 产品说明

## 一句话

客户要求提前交货时，计划员在 Xpert 助手的工作台里新建一条请求，点“AI 分析”。智能体调用工具展开 BOM、查询库存与在途、查询提前期与替代料，给出**带依据的缺料清单和建议交期**。计划员逐条采纳或驳回，确认后结果存档，刷新或第二天再进都能找回。

## 目标用户

**生产计划员（PMC）**。设定的企业是一家做电机控制柜的中小型离散制造厂，一个计划员同时管几十个在制订单。

只设这一个角色。采购和销售不进系统，采购能提供的信息（提前期、替代料）用模拟数据代替。多一个角色就要多一套权限、通知和界面，超出这次的范围。

## 原有工作方式与痛点

原来的做法：

1. 销售转来一句话：“SO-1024 能不能从 12 月 5 日提前到 11 月 25 日？”
2. 计划员在 ERP 里打开成品 BOM，逐层展开（成品 → 部件 → 外购件）。
3. 每个物料查库存，再查采购在途和预计到货日。
4. 库存不够的物料，用微信或电话问采购：“最快几天能到？有没有替代料？”
5. 在 Excel 里汇总，判断能不能提前、卡在哪个料、最早哪天，再回复销售。

| 痛点 | 后果 |
|---|---|
| 要在三个地方查数据（BOM、库存在途、采购提前期），全靠手工 | 一单要半小时到半天 |
| 展开 BOM 时漏掉某个二级件 | 承诺了交期，到时候缺料，影响信誉 |
| 结论只在计划员脑子里或聊天记录里 | 销售追问“为什么不行”时拿不出依据，下次类似请求也没法复用 |

本应用把第 2～5 步变成“填表 → 点按钮 → 看清单 → 逐条拍板”。**省掉的是查数和汇总，保留的是判断和拍板。** 计划员仍然对结论负责，AI 是帮他查齐数据、写出初稿的助理。

## 业务流程

```
计划员                 工作台（插件视图）                 智能体（Xpert 助手）            插件服务 / 数据
 1 新建请求 ─────────▶ 校验 → 保存为草稿 ─────────────────────────────────────────────▶ 请求表
 2 点“AI 分析” ──────▶ 建分析任务，状态=分析中
                       新开会话，发出带任务 ID 的分析指令 ─▶ 3 依次调用工具：
                                                         读取任务 → 展开 BOM → 查库存与在途
                                                         → 查提前期与替代料
                                                         → 逐条保存缺料结论 ────────────▶ 结论表
                                                         → 提交总结论 ──────────────────▶ 状态=待确认
                       轮询 / 工具完成事件 → 刷新 ◀──────
 4 逐条采纳或驳回 + 备注 ▶ 保存每条决定 ──────────────────────────────────────────────▶ 结论表
 5 确认结论 / 驳回本次分析 ▶ 已确认（锁定）/ 已驳回（可重新分析）────────────────────────▶ 操作日志
 6 刷新或重新进入 ─────▶ 从数据库读回请求、结论和决定
```

失败分支：工具失败（演示中是库存系统故障）时，智能体调用“上报失败”工具；智能体中途停下时，计划员可以点“放弃本次分析”；超过 3 分钟没完成时，读取时判为超时。这三种情况请求都进入“分析失败”，界面显示原因和“重试”。重试会新建一个分析任务，旧任务的结论不会混进来。

### 请求状态

```
              点“AI 分析”               智能体提交总结论
  [草稿] ───────────────▶ [分析中] ─────────────────────▶ [待确认]
                            │  ▲                            │    │
   工具失败 / 放弃 / 超时   │  │ 点“重试”                确认│    │驳回本次分析
                            ▼  │                            ▼    ▼
                        [分析失败]                    [已确认]  [已驳回]
                                                     （锁定）     │ 点“重新分析”
                                                                  └────▶ [分析中]
```

状态迁移由服务端校验，不只靠前端按钮置灰。确认时要求每条缺料都已经有决定，并且填了最终交期。

## 关键页面

页面放在助手的工作台里：左边是平台自带的对话，右边是本插件的视图。实际界面见 README 的截图。

- **请求列表**：搜索订单号或客户，按状态筛选；显示目标交期（原交期）、状态、缺料数。列表为空时有引导语和“载入演示请求”按钮。
- **新建请求**（对话框）：订单号、客户、产品（只能选模拟产品）、数量、原交期、目标交期、备注，以及“演示：第 1 次分析时模拟库存系统故障”开关。前端校验必填项和“目标交期应早于原交期”；订单号重复由服务端唯一约束返回，显示在字段下面。
- **请求详情**（核心页面）：
  - 顶部是 AI 总结论（可行 / 不可行 + 建议交期 + 理由）。
  - 中间是缺料清单，每条显示需求、可用、缺口、建议类型和理由，依据默认折叠；每条有“采纳 / 驳回 + 备注”。
  - 底部是最终交期、给客户答复的说明、“驳回本次分析”和“确认结论”。确认前会弹出确认框。
  - 技术详情和操作日志默认折叠。
- **分析中 / 分析失败**：分析中显示已用时间；超过 30 秒显示“放弃本次分析”；失败时显示能看懂的原因和“重试”。

## AI 的作用

| 环节 | 谁来做 | 说明 |
|---|---|---|
| 展开 BOM，算需求量、可用量、缺口 | 插件服务（确定性计算） | 工具返回算好的数字，可以单测 |
| 判断哪个料决定了最早交期 | **AI** | 结合缺口、提前期、在途到货日判断 |
| 给每个缺料选建议：催料 / 替代料 / 调整交期 / 无需处理 | **AI** | 要把在途单、提前期、替代料库存放在一起权衡 |
| 推算建议交期并写理由 | **AI** | 理由要引用工具返回的单号、日期、数量 |
| 回答追问（“为什么不能 25 号”） | **AI**（在对话里） | 只解释，不改数据 |
| 采纳 / 驳回、确认最终交期 | **计划员** | 只做成工作台动作，**不提供给智能体做工具** |

两个关键设计：

- **数字由服务端计算，AI 只给建议。** 缺口 = 需求量 − 库存 − 目标日前到货的在途，这是确定的加减法。让模型来算会出错，而且错了计划员很难发现。保存结论的工具只接收“物料 + 建议类型 + 建议日期 + 理由”，入库时服务端按同一份数据重新计算数字，不采用模型传来的数字。
- **确认和驳回只能由人在界面上做。** 智能体没有确认工具，所以不可能“自己确认自己”。这一点由系统保证，而不是靠提示词约束。

## 功能取舍

**做了**：新建、列表、详情；必填和日期校验、空状态；一次真实的 AI 分析（7 个工具）；逐条决定、确认、驳回、重新分析；结果持久化，可恢复；库存故障失败 → 重试，放弃本次分析，3 分钟超时兜底；幂等防重复；操作日志；助手模板（提示词 + 3 个中间件），可以在平台里一键创建助手。

**没做**（详见 README“已知限制”）：

| 没做 | 原因 |
|---|---|
| 对接真实 ERP / MES | 题目不要求；要真实凭证，别人无法复现 |
| 超过两层的 BOM、损耗率、批次与库位 | 两层足以说明问题，更深的层级只是循环展开 |
| 多用户、审批流、通知采购 | 先把单用户闭环做完整 |
| 分批交货、产能约束 | 缺料只是能否提前的一个维度，产能是另一个问题 |
| 在对话里用自然语言直接建单 | 结果确认和保存需要界面承载；作为后续增强 |

## 用什么开发的，遇到了什么问题

- **开发工具**：Claude Code（模型为 Claude Opus 系列）。规划阶段在 Cowork 对话里写产品设计和技术方案，开发阶段在本机 Claude Code 里写代码、跑测试、操作 WSL 里的平台。详见 [ai-collaboration.md](ai-collaboration.md)。
- **技术栈**：NestJS + TypeORM（服务端，4 张插件表），LangChain 工具 + Xpert Agent 中间件，Workbench 远程组件（React + 仓库自带的 shadcn 组件 + Tailwind，用 esbuild 打包），vitest + pg-mem 做单测。
- **主要问题**：Windows 上只能用 WSL2 跑平台；参考示例 `smart-maintenance` 不符合平台新加的命名空间规则，被拒绝安装；递归上限 40 不够用；往运行中的会话发消息会被排队；智能体中途停下后任务卡住。处理过程见 [validation.md](validation.md) 的“验证中发现并修复的问题”和 [ai-collaboration.md](ai-collaboration.md)。
