# AI 协作说明

## 工具和分工

| 工具 / 模型 | 做什么 |
|---|---|
| Claude Code（桌面版）· Claude Opus 5.5 | 整理需求、写 spec 和决策卡、拆任务、写给 Codex 的任务说明；设计并实现工作台界面；审查 Codex 的改动、跑门禁、提交；在真实 Xpert 里走查和截图；写文档 |
| Codex CLI · gpt-6-astra | 后端实现：插件骨架、领域层（表、服务、确认逻辑）、助手工具和模板、视图提供者，以及后来的「确认人姓名」「日期基准 + 重新发送」两轮改动。每轮在独立的 git worktree 里做，Claude 审查后再合并 |
| Claude Fable 5.2（只读子代理） | 对照题目做了两次只读评审（独立评审和平台能力审计），只出报告、不改代码 |
| 智谱 glm-5.3-flash | 产品运行时的模型，在 Xpert 平台里配置 |
| Xpert Skills | `xpert-agentic-app-developer`、`xpert-plugin-development`、`xpert-platform-local-environment`，作为平台约定的依据，比如表名前缀、不自开事务、工作台只走桥接 |

这样分工，一是因为 Claude 的额度紧，边界清楚的实现交给 Codex（额度单独计算）；二是换一个模型来写，Claude 审查时更容易发现问题。界面由 Claude 自己设计和实现，因为交互细节要反复对照截图调整。

## 怎么把背景交给 AI

- **先写 spec，再写代码。** spec 的第一页用大白话写清楚做什么、不做什么、怎样算做完，后面是接口、一直要成立的规矩（比如「订单交期只能由人确认时修改」）和 16 条验收标准。要我拍板的事做成决策卡，写明各选项的代价和选错了难不难退。
- **给 Codex 的任务说明要自带背景。** Codex 看不到聊天记录和私有笔记，所以说明里写清现状、要改哪些文件、逐条验收清单和「不要做」的事，并要求它在结果里逐条对照。Claude 审查时照着清单核对。
- **平台事实要有出处。** 比如「平台没有助手运行失败事件」，是在 xpert 源码里查过 `assistant.tool.completed` 之后写进 spec 的。「5 分钟超时兜底」这个决定就是由这条事实推出来的。不过这条事实只说对了一半：平台确实没有失败事件，但插件中间件可以用 `wrapModelCall` 钩子直接拦截模型调用的报错。这一点是后来让 Fable 审计 SDK 时才发现的，见第 8 段。

## 几段有代表性的过程

**1. 「回复这么短，AI 有什么用？」** 早期的示例都是「DEMO-001 第 1 行延期到 11-28」这种规整句子，规则也能处理，看不出 AI 的价值。于是换成真实的写法：一条周报混着 4 个物料，不写订单号，用「晚一周」「提前三天」，还夹着发票。改完测下来发现模型不知道「今天」是哪天，于是让工具返回回复的收到日期和星期，并在提示词里写明两种基准：相对订单的用原交期，相对收到时间的用收到日期。最终这条消息 4 个结果全部正确，发票也被正确忽略。

**2. 独立评审的结论要先核实。** Fable 评审列了一批问题，我逐条对照代码核实，确认有两条是真的：一是订单在解析后被改过时，界面只提示「过期」，用户却无路可走；二是相对日期没有基准。这两条都修了，加上「重新解析」入口和日期基准；其余没有证据的建议没有采纳。

**3. 改了提示词却不生效。** 改完模板提示词、重新部署，助手的行为没有变化。查下来发现，用模板创建助手时提示词是复制进去的，插件升级不会改到已有的助手。解决办法是用模板重新创建助手，再把 ClawXpert 绑到新助手上；这一点当时写进了已知限制；后来发现平台有「从模版更新」，这条限制删掉了（见第 8 条）。

**4. 一句含糊的话，让模型想了 9 分钟。** 第一版周报写的是「滑轨先发一半」，没说哪天发。模型不肯编日期，反复斟酌了 9 分钟，最后把这一项标为需跟进。它的判断是对的，但慢得没法用。我的取舍是：不放松「不编造日期」这条规矩，而是在提示词里写明「按原计划」指的就是当前交期，示例也改成「按原计划先发一半」。同时实测一条 4 个物料的消息要 2 分钟左右，就把超时从 3 分钟放宽到 5 分钟。

**5. 任务说明自相矛盾。** 有一轮给 Codex 的说明里写了「不许改已有断言」，可新接口本来就会改变两条断言的预期，Codex 只好把两个失败的测试留着。我审查时补改了这两条断言，并记下一条经验：说明里要分清「不许削弱测试」和「契约变了，就跟着改断言」。

**6. 真实平台才暴露的问题。** 在对话里中途停掉助手之后，再点「重新解析」被平台拒绝（409），因为对话里还挂着一个被暂停的执行。单元测试测不到这种情况。于是加了 `resend_parse` 动作和「重新发送给助手」按钮，在超时提示里写明处理办法，也记进了已知限制；后来每次解析都开新对话（`newThread`），这条限制删掉了（见第 8 条）。

**7. 交叉评审只修有依据的。** PR 前让 Codex 只读评审了确认和隔离两处，它报了 3 条。我逐条对代码核实，发现其中一条不依赖时序：工作台确认时带的版本号不覆盖提议，所以别的窗口改了审核结果之后，旧窗口仍能确认。这个问题修了。另一条（确认冻结后，原样重发的请求被拦下）也修了。两条修复都配了回归测试，并先在旧代码上确认测试会失败。剩下两条是毫秒级的竞争窗口，要封住得引入回复级的写入协调，代价和收益不成比例，所以写进了已知限制。

**8. 对平台了解不够。** 模型直接报错时，我们要等 5 分钟超时才能发现，这一点我一直当成平台的限制。后来让 Fable 系统地审计 SDK、平台源码和官方技能文档，任务说明里没有告诉它我们的结论。它找到了中间件的 `wrapModelCall` 钩子：模型调用一报错就能拦下来，几秒内落盘。原来我们只把中间件当成了装工具的盒子。它还找到三处我们没用上的平台能力：
- 发消息命令的 `newThread`：每次解析换一个新对话，原来那条「409」已知限制其实是用法问题。
- `assistant.context.set`：工作台可以把当前处理的回复直接交给助手的运行环境。
- 「从模版更新」：我们写的「提示词副本」已知限制是错的。

这些改动交给 Codex 按任务说明实现，我审查后在 sql.js 和真实 PostgreSQL 上各跑了一遍当时的 139 个用例（后来又补了中止场景、命令格式和确认中断的测试，现在是 157 个），再在平台上做了真实故障注入。第一次注入用的是不存在的模型名，结果平台在运行前就拒绝了，助手根本没调模型，钩子自然拦不到。这反而让我们看清了失败分两类：模型调用中的报错由钩子几秒内落盘；平台在运行前的拒绝只能靠超时兜底。第二次改成参数非法（`max_tokens` 越界），智谱真的返回了 400，6 秒内就落盘了，重试也没有产生重复提议。重跑完整 e2e 时又发现：在对话里结束执行，也会让模型调用抛出 `Aborted`，被钩子记成「模型调用出错」，界面还提示去检查模型配置。这是误导，于是把中止单独记成 `run_stopped`，只提示重新解析。这个问题单元测试测不出来，只有在真实平台上点了「结束执行」才会出现。后来在内置浏览器里手动演示时又发现：停止如果落在两步之间，平台只把对话暂停、不抛错，钩子拦不到。界面本来就有「重新发送给助手」，超时也会兜底，所以没改代码，只把文档里「结束执行后 5 秒显示被中止」改成分两种情况说明。

教训：写 spec 时我按「需要什么就去查有没有」的方式了解平台，应该先把 SDK 和平台能力完整过一遍。

**9. 界面自查。** 之前的几轮评审都只看架构、代码和可靠性，没有专门看交互。后来按六个方面自查了一遍工作台：首屏引导、AI 过程是否可见、结论能否追溯到原文、审核效率、失败提示、视觉。最弱的是「解析中」：1–3 分钟里只有一个转圈，停在两步之间时还会一直转下去。于是改了四处：

- 横幅显示已用时间和已保存的提议数，一段时间没有工具调用时，主按钮换成「重新发送给助手」。阈值起初定成 90 秒，重拍截图时发现一次正常的周报解析就有 105 秒没有工具调用，误报成「没有新进展」。宿主只转发工具完成事件，看不到模型是否还在生成，所以改成 150 秒，措辞也改成如实的「没有新的工具调用」，并提醒先看对话。
- 加了「全部采纳」。
- 失败横幅里直接放「重新解析」，并写明重试不会产生重复提议。
- 对话里那条消息原来只有 `reply:<64 位编号>`，跟单员看着像调试信息。在上面加了一行能读懂的「解析供应商回复（11月11日 09:03 收到，第 1 次）」，也成了对话标题；编号留在第二行。消息里没有放供应商原文：原文是外部数据，只该通过工具读取。
- 之后又试过把编号完全藏起来：查平台源码发现发消息命令的 `state` 会原样进到助手的运行状态，中间件在 `stateSchema` 里声明的键会变成状态字段，于是把编号放进 `state`，由中间件补进系统提示。平台上验证可行，模型报错也照样按编号落盘。但它让提交前的改动范围越来越大，最后还原成两行版本，写进了下一步。

「没有进展」的判断只用宿主已经转发的工具事件和服务端的提议数，没有改后端接口。界面由 Claude 设计并实现；e2e 也同步加了对这三处的断言。

**10. 干净上下文的复审。** 改了很多轮之后，让 Fable 在不带聊天记录的环境里，只看题目和代码重新审了一遍。它找到一个真问题，恰好在我们觉得最扎实的确认逻辑上：确认中途停下以后，如果剩下的某条订单被别的回复改过，这封回复就再也走不下去。继续确认会报「订单已变」，重新解析和驳回都被拦，提示还是「已经确认过了」。原来的测试把这种卡住的行为当成了预期。修法是确认开始后只放开一种操作：驳回「还没写进订单、而且订单确实被别人改过」的提议，驳回后点「继续确认」写完剩下的；确认进行中的错误码也和「已确认」分开了。同一轮还补了两个小洞：服务端不核对变更类型和日期是否一致；列表里的供应商名取哪一条不确定。另外两条里，旧对话的迟到写入写进了已知限制；「模板挂着待办清单中间件、提示词却不让用」这条，之后同样条件下的第二次复审建议直接去掉中间件（那次只剩 5 条 minor），这条建议我没有采纳：平台的 DSL 规范要求主 Agent 挂这个中间件，解析不用它是提示词层面的选择，不是矛盾，于是在模板里写明了原因。评审的建议也要先对照平台规范核实。

**11. 提交前的自查和整理。** 开 PR 前做了两件事。

- 对照仓库根目录的 `AGENTS.md` 逐条自查，改了三处。「不要从显示文字猜类型」这一条对上了两个地方：判断「运行被中止」原来靠匹配错误消息，改成读宿主传给模型调用的中止信号；判断「唯一约束冲突」原来靠驱动的错误码和消息，改成插入失败后回读，行在就是重复，不在就把原错误抛出去。发给对话的那句「解析供应商回复…」原来在代码里按语言分支写死，移进了词条文件。另外去掉了一条会盖住共享组件字体的全局样式，把列表行的两处原生按钮换成了共享的 `Button`。
- 整理提交历史。开发时有五十多个提交：Codex 和 Claude 各自 worktree 里的小步提交、三次分支合并、一次试验后的还原。它们记录了过程，但不方便审查。所以按审查者读代码的顺序整理成 9 个：脚手架、领域层、助手工具、工作台界面、界面的构建产物、视图提供者和插件入口、平台 e2e、文档、changeset；每个提交单独检出都能通过类型检查和当时已有的测试。整理前后的最终文件逐字节相同（比对了 tree 哈希），所有检查在最终代码上重跑。上面第 1–10 段讲的就是整理前的真实过程。

**12. 提交之后换模型再审。** PR 开出后，又用几个之前没用过的模型各审了一遍，其中包括 Codex 自带的代码评审，它和仓库对 PR 做的自动评审是同一种。结果找出了前面十几轮都没发现的问题，我用临时测试复现了三条并修掉，作为新提交追加在 PR 后面（见[验证结果](validation.md)第 11 节）。

回头看这三条为什么会漏掉：

- 数量不留痕是 spec 的缺口。验收标准里列了变更记录要记哪些字段，没有数量，同一条标准又允许修改数量。实现和评审都照着 spec 核对，所以谁都没看出来。
- 内容和版本号不一致，是上一次交叉评审之后的修复带进来的。那之后的评审都在看别的地方。
- 全部驳回后卡住，是因为之前修「确认中断后卡死」时，只在有两条提议的回复上验证过，只剩一条提议的情况没有试。

收获是：同一种评审多跑几遍，不如换一个模型、换一个问法、换一个场景。每个模型每次只能找到一部分问题，没有哪一次是全的。另外，每次修复都应该在引出它的场景之外再试一个场景。

## 自己做的取舍

- **AI 只提议，不改单。** 确认和驳回只做成工作台按钮，不给助手对应的工具；服务端校验出处必须是原文的一段，不依赖模型自觉。
- **确认不用事务。** 平台约定插件不能自开事务，所以确认被设计成三步、每步都能安全重做的单行操作；重复点击只生效一次，中断后再点一次就能接着做完；中断期间订单被别人改过的，驳回那几条再继续。
- **消息怎么进系统。** 我比较了两种方案：接邮箱或企业微信自动收取（A），或者一键「保存并解析」（B）。在 2–6 小时的范围里选了 B，A 列为下一步。
- **范围控制。** 可视化只做订单行的时间线，不做总览看板；分批到货当作一种提议类型，不拆成交货计划表。

## 怎么确认符合预期

- 四层验证：单元测试（162 个，断言的是业务结果，sql.js 和真实 PostgreSQL 各跑一遍）→ plugin-dev-harness → 预览宿主里的界面检查 → 真实 Xpert 里的完整流程。真实平台这一层写成了可重复执行的 e2e 脚本（`e2e/platform-e2e.mjs`），包括主流程、第二个组织的隔离检查和真实模型故障注入。
- 在真实平台上跑完之后，直接查数据库，核对提议、订单交期和界面显示一致，不只看界面。
- 每个异常分支都在平台上实际触发一遍（需跟进、超时、提议过期、工具校验失败后的自我纠正），前三个有截图；自我纠正那张后来重拍时没再触发，只留在验证记录里。细节见 [验证结果](validation.md)。

## 工具限制和应对

- **额度**：Claude 额度紧张，实现尽量交给 Codex；Claude 主要花在拆分、审查和真实平台验证上。
- **沙箱**：Codex 在沙箱里不能提交 git，所以由 Claude 审查后提交；部分命令（Docker、部署脚本、连本地服务）要在 Claude 的沙箱外执行。
- **环境**：npm 官方源直连被重置，只对那一条安装命令换用镜像；在仓库根目录用 corepack 会选到工作区以外的 pnpm 版本，要在 `community` 目录里执行命令。
- **模型速度**：glm-5.3-flash 解析长消息要 1–3 分钟，演示和超时设置都要按这个时长来安排。
