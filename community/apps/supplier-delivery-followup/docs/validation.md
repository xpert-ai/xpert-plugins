**自动复跑**：上面的流程由 `e2e/platform-e2e.mjs` 固化下来（用法见 README 的「端到端检查」）。最后一轮在本 PR 的最终代码部署后运行：

- `flow --with-stop` 12/12 通过。这次停止落在模型调用中，3 秒后回复显示「解析被中止」（`run_stopped`）；这也是改成读中止信号之后在真实平台上的验证。周报这次用了 3 分 27 秒，同一份代码的上一轮是 2 分 12 秒，模型的响应时间波动很大。4 条提议都按当时的订单交期推算正确，例如「原交期 2027-01-21 晚一周 → 2027-01-28」「原交期 2026-11-03 提前三天 → 2026-10-31」；后一条模型还注明了原交期早于收到日，请人工复核。示例订单被多轮测试反复改写，所以这些日期和截图里的不同。推算是否正确是人核对脚本日志得出的：模型每次的措辞不同，所以脚本只断言状态、出处和变更记录，不断言具体日期。
- `fault` 6/6 通过：真实 HTTP 400 后 5 秒落盘为 `model_failed`；换回正常助手后同一封回复第 2 次解析成功、没有重复提议；平台拒绝运行时，150 秒提示「没有新的工具调用」，5 分钟超时兜底。
- `isolation` 11/11 通过。
- 更早的几轮：停止落在两步之间的那条路径完整跑通过一次（13/13：150 秒后出现「没有新的工具调用」，点「重新发送给助手」后在新对话里解析完成）；每一轮修复部署后也各跑过 `flow`，结果是 10/10 或 12/12（检查项数随停止落点和是否带 `--with-stop` 变化）。
- 平台侧的崩溃：早先有两轮 `flow` 在「结束执行」时，平台写检查点和停止撞在一起，检查点保存抛出 409（`conversation_recovery_unavailable`）且没有被捕获，整个 API 进程退出。调用栈全在平台代码里（`CopilotCheckpointSaver.put` → `persistRecoveryCheckpoint`），两次都是重启后重跑通过。这是平台的竞态问题，记在这里，没有在插件里规避。最后一轮没有遇到。

更早一轮的 `flow` 有 1 项没过：断言「120 秒内显示已保存的提议数」，而那次周报解析用了 2 分 47 秒，前 2 分钟一条提议都没存。界面本身是对的，是断言的时限定得不合理，改成只断言已用时间，文案也从「通常 1–2 分钟」改成「1–3 分钟」。

脚本是一边跑一边修出来的。早期几次失败都出在脚本本身：把「已保存未解析」当成了结果；平台会记住上次的工作台布局，最大化后对话里的停止按钮不在屏幕上；重试后没有等新一轮开始就读结果。有一次失败暴露的是产品问题：加了 `wrapModelCall` 之后，在对话里结束执行会被记成「模型调用出错」，已改为单独的 `run_stopped`。

## 6. 交叉评审

请 Codex（gpt-6-astra，只读）对两处风险最高的地方做了一次独立评审：「确认只生效一次」和「按租户、组织隔离」。

- **模型故障的种类**：只注入过「参数非法」这一种真实的模型报错（HTTP 400），没测限流、超时、服务不可用这几类；按代码逻辑它们走的是同一条路径。平台在运行前就拒绝的情况，只靠 5 分钟超时兜底。
