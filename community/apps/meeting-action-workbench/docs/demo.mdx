## 演示目标

在 5 分钟内证明这不是聊天套壳：会议原文经过真实模型处理后成为可追溯、可人工确认、可持久化和可继续执行的业务对象；规则和 Agent 分工识别风险，Agent 不代替用户改变正式状态。

## 演示前准备

1. 确认 Xpert API readiness 为 `ready`，Cloud UI 可以登录。
2. 确认插件 `@xpert-ai/plugin-meeting-action-workbench` 版本为 `0.3.0` 且 `loadStatus` 为 `loaded`。
3. 打开已发布的“会议决议与行动项助手”，确认“会议行动项” Workbench 可见。
4. 使用合成或脱敏会议文本；真实组织内容只有在获得授权后才发送给模型。

建议样例：

```text
会议标题：版本验收会
1. 团队决定中文界面作为默认界面。
2. 李明在 9 月 20 日前整理验收截图和测试记录。
3. 王芳核对 README 的启动步骤，截止日期暂未确定。
```

## 五分钟主线

### 0:00 至 0:40 产品问题

说明传统做法需要人工从会议记录中重复整理决议和待办，而且缺少原文证据、确认门槛和后续执行状态。本应用把提取、确认、执行、巡检和复盘放在同一工作台。

### 0:40 至 1:40 真实 AI 提取

在“会议复核”页选择“新建提取”，可以输入样例，也可以导入 TXT 或 DOCX 会议文件。先展示长记录可独立滚动且提交按钮始终可见，再发送给 Assistant。Assistant 依次创建提取轮次、保存决议和行动项并完成提取。指出每条结果都带有原文证据与置信度；原文未给出的截止日期保持为空。

### 1:40 至 2:30 人工确认

对照原文检查一条决议和两条行动项，说明只有“待复核”状态可以确认。确认后刷新页面，展示会议、证据和行动项从 PostgreSQL 恢复，证明状态不只存在于聊天或浏览器内存。

### 2:30 至 3:50 执行治理

切换到“执行跟踪”。展示待处理、进行中、已完成和已取消的业务状态，以及规则直接计算的即将到期、缺负责人和缺截止日期。强调这些客观事实不交给模型判断。

选择“Agent 执行巡检”，展示 Agent 只分析含糊承诺、重复任务、决议冲突、依赖和负责人负载等语义问题。风险带原文证据、置信度和处理建议；接受、忽略或标记已处理只能由用户操作。

### 3:50 至 4:30 跟进简报

展示“下次会议跟进简报”：已完成项、未完成或临期项、待人工确认的语义风险和建议议程都来自持久化巡检。说明 Agent 写入的是草案，不会自行宣布任务完成。

### 4:30 至 5:00 可靠性证据

打开验证记录，说明 14 个测试、真实 TXT/DOCX 解析、长记录浏览器 E2E、`verify:dist`、插件生命周期、真实 DeepSeek 调用和已安装平台复验均已完成。用一个异常场景收尾：失败状态保留原会议，重试使用 `operationId` 和 revision 防止重复数据及陈旧覆盖。

## 演示失败时的回退

- 云端模型暂时不可用：展示已持久化的真实验收记录与失败重试状态，不伪造新的成功结果。
- 页面数据陈旧：刷新 Workbench；遇到 revision 冲突时基于最新数据重做修改。
- 插件刚更新：确认部署回执是否要求重启 API，再检查 readiness 和插件描述符。

回退只用于保证讲解连续，不应把模拟响应描述成新的真实模型调用。
