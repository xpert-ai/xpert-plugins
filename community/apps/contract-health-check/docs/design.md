# 中小企业「合同智能体检」Agent 工作流应用 — 设计与产品说明

> 本文档对应面试任务书要求，聚焦 **产品判断 + Agent 工作流框架设计**。
> 选题：面向中小企业的「销售/采购/合作合同智能体检」Agentic App。
> 交付形态：Xpert 平台独立插件（业务应用），以 Fork 插件仓库、独立功能分支 PR 形式交付。

---

## 一、选题概览

| 项目 | 内容 |
| --- | --- |
| 应用名称 | 合同智能体检（Contract Health-Check） |
| 一句话价值 | 让没有专职法务的中小企业，在签合同前 3 分钟内完成一次结构化风险体检，并拿到可直接商用的改写建议 |
| 业务领域 | 中小企业通用法务前置审查（销售合同 / 采购合同 / 合作协议） |
| 目标用户 | 中小企业老板、销售负责人、行政商务 |
| 交付形态 | Xpert 平台上的 Agentic App 插件（含 Workbench 视图 + Assistant 模板 + 中间件工具） |
| 核心闭环 | 录入合同 → AI 体检（多 Agent）→ 查看风险与改写建议 → 逐条确认 → 保存报告 → 可随时恢复 |

> **为什么选这个场景**：合同审查是中小企业"高频、高代价、强刚需、无专业人"的典型矛盾点。它天然适配 Agent 工作流（抽取→审查→改写→摘要），且闭环清晰、易于演示、风险可控，是展示"AI 在业务中的具体作用"的好载体。它不是"聊天问答"，而是把一份非结构化合同变成一份可确认、可保存、可追溯的结构化审查结果。

## 二、目标用户与角色

| 角色 | 典型画像 | 核心诉求 | 使用频率 |
| --- | --- | --- | --- |
| **老板 / 创始人** | 10–100 人公司负责人，常年签销售、采购、合作合同 | 别因为一条条款赔掉利润；签之前心里有底 | 中高频 |
| **销售负责人** | 带小团队，客户给的模板五花八门 | 快速判断"客户模板能不能用"，别卡在合同上丢单 | 高频 |
| **行政 / 商务** | 负责走合同流程、归档 | 把风险点整理清楚、格式统一，给老板看 | 高频 |

> 设计上以"老板/销售负责人"为主用户，行政商务为协作者。权限与多组织隔离按需后期扩展，本期不默认实现。

## 三、用户原有工作方式 & 痛点

### 现状工作方式
1. 收到客户/供应商发来的合同 Word/PDF，老板自己硬着头皮通读；
2. 看不懂的条款直接跳过，或微信问朋友、百度"这一条有没有坑"；
3. 真出问题（货款被拖欠、违约罚则极高、管辖法院在对方城市）才发现合同没写清楚；
4. 偶尔请律师审一份，费用 500–2000 元，频次高、成本扛不住，于是"能不请就不请"。

### 痛点归纳

| 痛点 | 说明 | 后果 |
| --- | --- | --- |
| **无专业审查能力** | 非法律背景，看不出隐藏风险 | 签了不利条款不自知 |
| **审查慢、靠记忆** | 逐字读、凭印象，无清单 | 漏看关键项（付款、违约、管辖、知识产权） |
| **风险不可见、不可追溯** | 审查结果只在聊天记录/脑子里 | 出事后无法回溯"当时为什么没发现" |
| **成本高、不可复用** | 请律师贵，模板不统一 | 要么硬扛风险，要么放弃审查 |

## 四、业务问题与产品目标

**业务问题**：中小企业缺乏「低成本、可复用、可追溯」的合同风险审查能力；现有方案要么是昂贵的律师（低频黑盒），要么是没有保障的自学（不可靠）。

**产品目标**：把"请律师审合同"这个高成本、低频、黑盒的动作，变成
> **粘贴合同 → AI 体检 → 确认风险 → 保存报告**

的低成本、高频、透明闭环。让一次审查从"半天 + 几百元"降到"3 分钟 + 0 元"，并且结果可留痕、可复用、可复盘。

---

## 五、AI 在业务中的具体作用（不是聊天问答）

AI 不是"陪你聊合同"，而是**替代/增强审查流程中的四个具体环节**：

| 环节 | AI 具体做什么 | 对比人工 |
| --- | --- | --- |
| 信息抽取 | 从非结构化合同文本中抽取主体、金额、付款、交付、违约、争议解决等关键要素 | 人工通读 10+ 分钟 → AI 秒级结构化 |
| 风险审查 | 对照「中小企业常见合同风险知识库」逐项打分、标注等级与依据 | 人工靠记忆、易漏项 → AI 清单式全覆盖 |
| 改写生成 | 对高风险条款生成可直接替换的表述（保留商业意图、降低法律风险） | 人工不会写法务表述 → AI 给可商用草案 |
| 摘要生成 | 生成一页式可读报告（总体风险评分 + 高危项速览） | 人工难提炼 → AI 即时摘要 |

> 关键：AI 的输出是**结构化、可确认、可保存**的业务结果，而非一段聊天文本。用户拥有最终确认权。

## 六、业务流程（端到端闭环）

```
[录入合同] → [发起体检] → [AI 多 Agent 处理] → [查看风险与改写建议]
     ↓                                                     ↓
[历史记录/恢复] ← [保存报告] ← [逐条确认/编辑] ← [用户审阅]
```

1. **录入**：用户在工作台粘贴合同文本，或上传 `.docx/.pdf`（触发解析/OCR，失败有提示）。
2. **发起体检**：点击「开始体检」，创建一条 `ContractReview` 业务记录，状态置为 `processing`。
3. **AI 处理**：进入 Agent 工作流（详见第八节），依次完成抽取 → 审查 → 改写 → 摘要。
4. **查看结果**：界面展示风险清单（按等级排序）、每条的改写建议、总体风险评分。
5. **确认 / 编辑**：用户逐条标记「接受建议 / 忽略 / 自定义修改」，可补充备注。
6. **保存**：报告写入业务记录，状态置为 `completed`，可随时重新打开。
7. **失败重试**：若某 Agent 调用失败，界面提示可理解的原因，支持**局部重试**且不重复产生业务结果。

## 八、Agent 工作流框架设计（核心）

### 8.1 整体架构

```
                        ┌─────────────────────────────┐
   用户录入合同文本 ───▶ │  入口 Agent（Orchestrator） │
                        └──────────────┬──────────────┘
                                       │ 调度（串行+按需并行）
            ┌──────────────┬───────────┼───────────┬──────────────┐
            ▼              ▼           ▼           ▼              │
     ┌──────────┐  ┌──────────┐ ┌──────────┐ ┌──────────┐       │
     │Extract   │  │ Review    │ │ Draft     │ │ Summary   │       │
     │Agent     │  │ Agent     │ │ Agent     │ │ Agent     │       │
     │(抽取)    │  │(审查)     │ │(改写)     │ │(摘要)     │       │
     └────┬─────┘  └────┬─────┘ └────┬─────┘ └────┬─────┘       │
          │ 要素JSON     │ 风险清单   │ 改写建议   │ 报告          │
          └──────────────┴─────┬─────┴───────────┘              │
                               ▼                                │
                     ┌─────────────────────┐                     │
                     │  结果聚合 & 校验     │                     │
                     │  (Schema 校验/去重)  │                     │
                     └──────────┬──────────┘                     │
                                ▼                               │
                     ┌─────────────────────┐                     │
                     │  Workbench 视图呈现  │◀── 用户逐条确认     │
                     │  + 持久化保存        │                     │
                     └─────────────────────┘                     │
```

### 8.2 各 Agent 职责与工具

| Agent | 职责 | 输入 | 输出 | 调用的工具 | 失败处理 |
| --- | --- | --- | --- | --- | --- |
| **Orchestrator（入口）** | 解析用户意图、调度子 Agent、聚合结果、做 Schema 校验 | 合同文本 + 元信息 | 编排后的结构化报告 | `contract.extract` / `contract.review` / `contract.draft` / `contract.summary` | 捕获任一子 Agent 异常，标记失败环节，支持断点重试 |
| **ExtractAgent（抽取）** | 抽取合同关键要素，建立审查"骨架" | 合同全文 | `ContractElements`（主体、金额、付款、交付、违约、管辖、知识产权等） | `contract.extract` | 解析失败 → 返回明确错误，提示"文本过短/含图片需 OCR" |
| **ReviewAgent（审查）** | 对照风险知识库逐项审查、打分、给依据 | `ContractElements` + 合同全文 | `RiskItem[]`（等级、条款位置、问题描述、依据） | `contract.review` + 风险知识库检索 | 模型超时/限流 → 标记 `failed`，可单独重试 |
| **DraftAgent（改写）** | 对 🔴/🟠 风险生成可直接替换的表述 | `RiskItem[]` | `Suggestion[]`（原条款 → 建议条款） | `contract.draft` | 部分条款无改写建议 → 标记"建议人工处理"，不阻塞整体 |
| **SummaryAgent（摘要）** | 生成总体评分与一页式可读报告 | 上述全部产物 | `Report`（评分、速览、导出文本） | `contract.summary` | 失败可降级：仅展示清单，不展示摘要评分 |

> **设计要点**：各 Agent 通过**明确定义的工具（Tool）**与插件通信，模型根据工具描述和参数发起调用，插件执行后返回结构化结果——符合任务书"智能体与工具"的要求。Agent 之间以**结构化数据**（而非自然语言串接）传递，便于校验、重试与持久化。

### 8.3 工具定义示例（Tool Schema）

```json
{

  "description": "对照中小企业常见合同风险知识库，对抽取出的合同要素进行逐项风险审查",
  "parameters": {
    "type": "object",
    "properties": {
      "elements": {
        "type": "object",
        "description": "ExtractAgent 输出的合同要素 JSON",
        "properties": {
          "parties": { "type": "array", "items": { "type": "string" } },
          "amount": { "type": "number" },
          "paymentTerms": { "type": "string" },
          "deliveryTerms": { "type": "string" },
          "liabilityClause": { "type": "string" },
          "jurisdiction": { "type": "string" }
        },
        "required": ["parties", "paymentTerms", "jurisdiction"]
      },
      "contractType": { "type": "string", "enum": ["销售", "采购", "合作"] }
    },
    "required": ["elements", "contractType"]
  },
  "returns": {
    "type": "array",
    "items": {
      "type": "object",
      "properties": {
        "level": { "type": "string", "enum": ["高危", "中危", "低危"] },
        "clauseRef": { "type": "string", "description": "条款位置，如 第4.2条" },
        "issue": { "type": "string" },
        "basis": { "type": "string", "description": "风险依据" }
      }
    }
  },
  "failureCases": [
    "模型超时：返回 {error:'timeout'}，前端提示重试",
    "要素缺失：返回 {error:'missing_elements'}，引导回录入页补全"
  ]
}
```

### 8.4 业务状态机

```
   draft ──(用户点击开始体检)──▶ processing
                                    │
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
         needs_review          failed                processing
      (AI 完成，待确认)    (某Agent异常)          (重试中)
              │                     │
    (用户逐条确认并保存)   (用户点击重试，幂等)
              │                     │
              ▼                     ▼
         completed ◀────────── processing
```

### 8.5 失败与重试设计（任务书硬性要求）

- **失败可感知**：模型超时 / 限流 / 解析异常时，Orchestrator 捕获并以 `RiskItem` 之外的独立字段 `pipelineError` 返回，前端渲染为"体检未完成 + 原因"提示，而非报错白屏。
- **局部重试、避免重复业务结果**：以 `reviewId` 为幂等键。重试时仅重跑失败的子 Agent，已成功的子 Agent 结果复用；不重新生成整份报告，避免"重试产生重复合同/重复建议"。
- **部分失败不阻塞**：如 `SummaryAgent` 失败，仍可展示风险清单与改写建议（`completed` 但 `summarySkipped=true`），保证主流程可用。
- **输入校验失败**：正文为空 / 含纯图片未 OCR，阻断在录入页并提示，不进入 AI 流程，节省调用成本。

### 8.6 数据保存与恢复

`ContractReview` 业务实体（持久化到平台业务库）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `reviewId` | string | 主键，幂等键 |
| `contractName` | string | 合同名称 |
| `contractType` | enum | 销售/采购/合作 |
| `rawText` | text | 脱敏后的合同原文 |
| `elements` | json | 抽取结果 |
| `risks` | json[] | 风险清单 |
| `suggestions` | json[] | 改写建议 |
| `score` | number | 总体风险评分 |
| `userDecisions` | json | 用户逐条确认结果 |
| `status` | enum | 状态机值 |
| `createdBy` | string | 用户/组织标识（权限边界） |
| `updatedAt` | timestamp | 更新时间 |

> 保存后刷新或重新进入应用，按 `reviewId`/`createdBy` 查询恢复原记录与结果，满足任务书"保存与恢复"要求；涉及多用户/组织时按 `createdBy` 做数据隔离。

## 九、功能取舍

**本期完成（最小可靠闭环）**
- 单合同体检：录入 → 多 Agent 处理 → 风险清单 + 改写建议 + 评分
- 用户逐条确认/编辑，报告持久化保存与恢复
- 一个明确的失败重试场景（模型调用失败，局部重试、幂等）
- 空状态/输入校验提示

**按需延后（不默认实现）**
- 多合同对比、合同模板库、电子签集成
- 多组织/复杂权限、团队协作批注
- 多智能体治理看板（本期为多 Agent 串行+少量并行，非完整 pipeline 治理）

> 取舍原则：先把"一条核心流程可靠跑通 + 真实 AI 调用 + 结果可恢复 + 失败可重试"做到位，再按需扩展，符合任务书"聚焦小闭环"的导向。

## 十一、验证与失败场景（验收对照）

| 场景 | 操作与通过标准 |
| --- | --- |
| 完整业务流程 | 录入合同 → 触发 AI 体检 → 查看风险与改写建议 → 逐条确认保存；界面、业务状态、保存结果一致 |
| 保存与恢复 | 保存后刷新/重进应用，能恢复原记录与结果（非仅页面内存） |
| 输入与空状态 | 缺合同名称或正文为空时按钮禁用并提示；无历史数据时有空状态引导 |
| 失败与重试 | 模拟模型 500/超时，呈现可理解原因；点击重试仅重跑失败环节，不重复生成业务结果 |
| 权限与数据范围 | 多用户下按 `createdBy` 隔离，无权限不能读取他人合同记录 |

## 十二、已知限制与后续方向

- **本期限制**：仅支持中文合同、单文档；风险知识库为通用中小企业清单，未做行业细分（如建筑/餐饮差异）；改写建议为草案，最终以用户/律师确认为准。
- **最值得改进的 3 个方向**：
  1. 行业化风险知识库（按制造/贸易/服务细分条款权重）；
  2. 合同模板库 + 一键生成标准合同（从"审查"走向"起草"）；
  3. 多合同横向对比与历史案例沉淀，形成企业自有风险画像。
