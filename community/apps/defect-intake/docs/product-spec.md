# 智能工单补全助手

面向需要将零散用户反馈整理后交给研发的测试和技术支持人员。应用保留原始反馈，由 AI 提取已有事实、提出必要的追问，用户补充并核对后形成可保存、可恢复的缺陷报告。

## 用户问题

用户常用“导出一直转圈”“登录不了”等短句反馈问题。测试或技术支持需要反复追问发生位置、操作条件和实际表现，再将信息整理成报告。信息在多次沟通中容易遗漏，推测也可能被误写成事实。

## 第一版范围

支持文本录入、真实 AI 分析、人工补充与编辑、草稿保存、报告确认、历史记录恢复和分析失败重试。采用单用户操作流程，但所有记录仍按照平台租户、组织和当前用户校验访问范围。

第一版不包含生产系统接入、自动根因诊断、自动复现、截图识别、批量文件解析或 Jira/GitHub 写入。使用明确标注的虚构反馈验证流程。真实模型调用、插件运行及数据库持久化必须实际验证。

## 核心流程

1. 创建记录，录入原始反馈并保存。
2. 发起 AI 分析。AI 读取当前记录，返回结构化草稿和有针对性的待澄清问题。
3. 用户查看每项已有事实及其来源，回答追问或直接编辑报告。
4. 保存补充信息。再次分析时保留人工编辑，要求 AI 依据最新记录处理。
5. 用户确认报告。系统保存确认时的内容；信息不完整时保留明确的待补充项，不能将其伪装成已复现、已诊断或已解决。
6. 重新进入应用，恢复原始反馈、补充内容、草稿、确认结果和处理状态。

## AI 与人工职责

AI 负责整理已提供信息，识别对定位有帮助的信息缺口，提出简明追问。缺陷报告包括标题、功能入口、环境、复现步骤、预期结果、实际结果、发生时间、频率、影响范围和待澄清项；这些字段不要求一次全部填写。

原文未说明的内容保持为空或标记待补充。AI 不得编造操作步骤、环境、日志、用户身份和故障根因；不将追问中的假设写成事实。原文引用必须能在对应来源中找到。没有查询到系统记录时，明确返回未找到，不能用模型记忆补全。

用户负责补充事实、修正草稿并确认报告。确认操作表示人工核对这份报告，不表示缺陷已被研发受理或修复。没有明确提供的根因始终保持未知。

## 页面与操作

工作台采用记录列表加详情的结构。详情包含原始反馈、待澄清问题和可编辑报告。主要操作为创建、分析、保存补充、保存草稿、确认和失败重试。空列表提供创建入口；分析期间显示状态并阻止重复提交同一次任务；离开或刷新后能够恢复已有进度和结果。

确认结果与编辑中的草稿分开保存。AI 返回结果不得静默覆盖用户已经编辑的字段。重试只处理对应记录和有效的当前尝试，过期结果不得回写或生成重复的业务记录。

关键页面采用以下结构，后续在实际 Workbench 组件中实现和验证。

```text
智能工单补全助手                                      新建反馈
─────────────────────────────────────────────────────────
记录列表           原始反馈与补充              缺陷报告
搜索               原始反馈                   标题
                   用户补充                   已有事实与来源
记录标题           待澄清问题                 可编辑字段
状态与更新时间     回答并保存                 待补充项
                   开始分析或重试             保存草稿  确认报告
```

列表选择记录后保持详情与聊天上下文一致。分析中的状态、失败后的重试和已确认结果在同一详情中呈现，不要求用户在多个页面之间往返。记录列表在窄窗口可收起，表单区域允许独立滚动。

## 状态与保存

业务状态为草稿、待补充、待确认和已确认。AI 分析状态独立记录为未开始、处理中、成功和失败，避免将模型超时误认为整条报告丢失。

保存对象包含原始反馈、用户补充、AI 草稿、人工草稿、追问与回答、确认快照、版本和分析尝试。租户、组织和用户身份从可信平台上下文获取，不允许模型或界面传入的字段替代访问校验。

## 验收标准

| 场景 | 通过标准 |
| --- | --- |
| 信息稀少 | 能根据“导出一直转圈”等反馈提出具体追问，未知字段保持未知 |
| 信息充分 | 提取已有信息并给出来源，避免重复追问已提供的内容 |
| 人工补充 | 回答追问并保存后，重新进入仍能看到补充内容 |
| 人工编辑 | 再次分析或重试不会静默覆盖人工修改 |
| 报告确认 | 保存可查看的确认结果，明确未补充项，不虚构受理或修复状态 |
| 保存恢复 | 完整刷新页面后仍能恢复记录、草稿、确认结果和状态 |
| 分析失败 | 通过可控的模型或服务失败显示可理解的原因，原记录和人工内容保留 |
| 失败重试 | 重试成功后更新原记录，重复点击或迟到结果不产生重复确认结果 |
| 空状态与输入 | 空列表有下一步入口，空白反馈不能提交并有纠正提示 |
| 数据范围 | 使用平台上下文限制访问，越权读取和修改失败 |

## 演示数据与可选扩展

第一版使用 `fixtures/intake-cases.json` 中的虚构业务案例。测试可以模拟模型响应，但平台验收必须包含一次真实模型调用，并分别记录模拟与真实验证结果。

核心验收通过后，可加入小型演示导出任务数据源，通过工具按任务编号查询状态和错误码。界面和返回结果明确标为演示数据，查询不到时如实提示，错误码不直接等同于根因。此扩展不阻塞第一版交付。

## 实施顺序

先验证本地 Xpert 环境，再实现记录创建与持久化、工作台编辑和恢复，随后接入 Assistant 工具与真实 AI 分析，最后完成重试、平台验收、截图和 PR 材料。约五天为工作安排参考，以实际进展调整，不将其当作招聘方承诺的截止时间。
