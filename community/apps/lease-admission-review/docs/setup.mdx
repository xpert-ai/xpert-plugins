Use the official Xpert Docker Compose environment, a matching SDK, and a local OpenAI-compatible model provider. Keep all connection values in the host configuration.

Build the shared shadcn package before this plugin. Run the package build, typecheck, behavior tests, freshness check and the repository plugin development harness. Harness infrastructure is mocked and does not prove database persistence.

Install with tenant scope into the Default tenant. Mount the plugin workspace into the API container and configure its allowlist. Restart if requested, verify the live view and tools, then create an assistant from the contributed template and bind a locally configured model before publication.

The template intentionally contains no provider address, credential or runtime model parameters. Configure the assistant's runtime options through the host after installation: the template installer can copy the model reference without copying the provider's runtime defaults. Validate tool calling with your selected model.

Load the assistant's `agent.copilotModel` relation explicitly when checking these options. An independent primary-node model may override the team model even when a default team response omits that relation. In this validation, the primary-node binding initially had empty options; syncing the host defaults to both the team and actual primary node corrected that omission. Do not infer the absence of an override from an unloaded relation.

In the assistant page, open the workbench panel if the host initially maximizes the chat. The review view becomes available through the `lease_admission_review.review` capability.

Each extraction uses a new host chat thread and a server-issued attempt identifier. A failed dispatch preserves the source. An extraction with no successful tool receipt expires after five minutes when its detail is read; retry creates a new attempt. A browser request timeout does not by itself prove that the server failed.

For browser tests inside Docker, use direct network access to the official Web and API ports. Buffering an event stream with a test request interceptor can change timeout behavior and is not equivalent to testing the native host connection.

Acceptance requires a real model extraction, a corrected confirmation, reload recovery, and a recoverable failure. Use synthetic records and redact evidence screenshots.

## Recorded validation

On 2026-09-22 the official Docker host completed a real extraction of the synthetic source shown in the README. The result retained a genuine zero and an 80% ratio, reporting periods, units and exact evidence. A human correction without a reason was rejected; adding the reason allowed confirmation. Reload and leaving/reopening the page restored the reviewed value and reason.

For controlled failure, the isolated host model was temporarily disabled using its official API, then restored in a `finally` block. The case retained its source and became retryable after the five-minute lease expired. Enabling the same model and retrying the same case produced real candidates and a successful human confirmation. No candidate or confirmation was inserted by the test script.

Five behavior/PostgreSQL tests passed with no skips, including timeout recovery, stale output rejection, separate candidate/confirmation values, duplicate confirmation prevention and tenant/organization/user/assistant isolation. These tests clean up only their own randomized fixtures. Plugin lifecycle checks use mocked infrastructure and are reported separately.

After deploying the final plugin, the API was restarted and the browser again restored the original human-confirmed case. A read-only database audit after restart found exactly one candidate-saved event and one confirmation event for each accepted scenario; the AI value and human value remained separate. Package, compressed assets and local management files were checked for private connection values and token-shaped content, with no matches. Screenshots were also inspected visually.

The host image can leave ChatKit blank while redirecting from an assistant entry URL to a saved conversation. Opening/reloading the canonical conversation URL generated by the host restored the chat in this validation. The plugin does not modify platform source to bypass this behavior. Browser probes wait for the actual chat composer before requesting extraction.

Source baselines were Xpert `d24ca81b9f5885cf44dd77afdb0f91359b49c4ea` and plugins `ceb57e6fd5f9ccea48d5e8f8b431e4baae4f4e55`. ## Version 0.2 scoring and draft upgrade

The additive upgrade script was executed twice successfully against the isolated host database. It adds nullable `reviewDraft` and `assessment` JSONB columns and preserves old confirmations without scoring them. See [upgrade and rule conventions](scoring).

Ten behavior tests passed with zero skips, including real PostgreSQL draft persistence, revision conflict, repeated operations, identity isolation, candidate preservation and historical null snapshots. Fixed-point tests cover four-decimal threshold neighbors, 80% versus 80.0001%, management counts, leap dates, units, missing evidence and invalid scopes. The JSONB comparison uses field content rather than serialization order. Changing previously saved complete human scoring inputs requires a correction reason at confirmation, even after saving another draft.

During scoring validation, the host provider's declared output ceiling did not match its saved runtime limit. Its context metadata was aligned through the official API; a subsequent extraction succeeded, but this does not establish the mismatch as the sole cause of incomplete output. A later streamed response still contained incomplete tool arguments, so the local host was configured to request complete model responses before parsing. All connection and runtime values remain local. A missing-data extraction also rewrote a source quotation and was rejected. Tool guidance now requires continuous verbatim substrings and permits empty evidence for missing facts. Failed attempts remain in the history and are not counted as successful acceptance runs.

Three synthetic browser scenarios then passed: a saved 14-point draft was restored, corrected against the source to 15, rejected without a correction reason and confirmed with one; missing management/pledge data could only remain a draft while valid debt data independently cleared the negative rule; 80.0001% debt produced 7/15 and hit the negative rule. Each used actual host model tool calls, then human workbench actions. Reload and navigation restored saved drafts or score snapshots, and historical confirmations remained unscored.

After the final API restart, independent browser sessions logged in through both `localhost` and `127.0.0.1` Web origins. Both restored the normal/negative score snapshots, the incomplete human draft and historical unscored records; no new model calls were used for this recovery check.

## Version 0.2.1 workbench and ordinary-user acceptance

No migration, new dependency, business service or bridge action is introduced. Build and deploy the package, honor the host restart requirement, then reload the signed-in assistant. The workbench adds labelled score breakdowns, distinct pending issues, a required-window hint, restored-draft status, a fixed action bar and a collapsible case list. Narrow views collapse the list automatically. See the [synthetic walkthrough](walkthrough).

Two VIEWER accounts were created using the official user API, joined to the validation organization, and given assistant access through a dedicated user group. Each used an independent browser context and an actual model extraction. Cross-user detail and mutation requests were denied; save_draft, preview_score and confirm reached the plugin and returned not_found. After group membership was revoked, existing-session requests were rejected at the host boundary with HTTP 403, and browser reentry did not mount the plugin. The group grant was restored afterward.

The ordinary-account confirmation covered a 14-point saved draft, correction to 15, rejection without a correction reason, cancellation/focus return and successful confirmation. An oversized evidence input was rejected without losing the unsaved field. Drafts intentionally accept incomplete or unverified evidence: an earlier test incorrectly expected verbatim validation during draft save. Its synthetic evidence edit was restored through a normal owner save; both authorized draft events remain in the history. Read-only before/after database snapshots distinguished those expected events from denied requests, which added none.

The original suite still passes ten rule/real-PostgreSQL tests without skips. Build, typecheck, dist freshness and lifecycle loading pass; Harness infrastructure is mocked. Installed-browser checks cover 1366×768, 1920×1080 and a 550px-wide iframe, semantic border colors, keyboard actions and local-dirty protection against a controlled host-event notification. This notification is an explicit bridge refresh probe, not an additional live model completion. Two actual model extractions were used for the ordinary-user scenarios.

After API restart, both ordinary users recovered their saved snapshots through localhost and 127.0.0.1. Cross-tenant/organization/assistant isolation remains service/database evidence; it is not claimed as additional browser-account coverage. The full host source build and optional historical-case reference are not part of this patch.

Dark/default and dark/compact theme messages were also sent from the actual parent into the installed iframe; background, semantic borders and density were checked, and the original theme was restored. This is a protocol smoke test, not a claim that host settings were changed. Keyboard selection waits for the Radix option to receive focus before advancing; dispatching several keys without waiting had tested the wrong option.
