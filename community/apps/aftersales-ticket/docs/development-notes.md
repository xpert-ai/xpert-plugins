# 产品设计与 AI 协作

用户是一线客服。原来的工作方式是在聊天、客户描述和独立文档之间整理问题、手写回复，容易遗漏信息并难以追踪审核结果。此应用聚焦一张工单：保留客户原话，让 AI 整理分类/优先级/待补信息/回复草稿，客服拥有最终确认权。

页面结构：工作台列表（标题、状态、时间、查看）→ 详情对话框（原始问题、分析结果、回复）→ 人工编辑确认。新建表单独立，分析从详情发起。空状态允许新建，失败保留输入，确认后只读。

不实现自动发送、退款、复杂分派、附件或统计。模型建议不是政策事实，不能承诺未经证实的处理期限、模板保留或恢复能力。

开发使用 Codex 与另一 AI 开发会话（操作者称 DSH）协作，用户负责账号、模型和页面操作。本仓库不把业务运行使用的 DeepSeek 型号冒充开发助手型号，也不记录未经确认的开发模型版本。

代表性决策：
1. 用户限定不自主搭环境，后续逐步明确授权源码 API/UI + Docker 基础设施；内存紧张时按阶段检查，避免反复全量构建。
2. 初版计划用原生表格 inputSchema；读取 Cloud UI 执行器发现不呈现表单，改用共享 shadcn React iframe，通过宿主桥接操作。
3. ORM 依赖问题通过升级测试宿主解决，保持 TypeORM/Nest ORM 为 host peers，不私自复制运行时绕过。
4. 并发分析采用 scope + status + attempt 条件更新；超时接管复用 updatedAt，并在更新条件中检查同一时间戳，避免旧读导致抢占。
5. 平台截图暴露模型把 confirmed 说成已发送；复核没有接受“模型说自己遵守规则”作为证明，而是增加返回语义与模板约束，并保留问题及待复验说明。

验证分层：业务规则与服务模拟测试、打包页面 jsdom、插件生命周期 mocks、操作者真实平台主流程。不同层的结果分别记录，不相互替代。
