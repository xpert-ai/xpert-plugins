# 01 · 产品说明与范围

整理日期：2026-09-16；当前实现：`@community/apps-testcase-workbench` 0.1.0。本文只描述代码里真实保留的功能，不把设想写成已完成。

## 用户、问题与价值

- **目标用户**：需要把一条需求尽快转成可评审测试用例、并要把结果留在自己系统里的测试工程师或开发。
- **原有工作方式与痛点**：在需求文档、聊天窗口和用例管理工具之间手工复制。AI 一次性吐出一大段用例，格式和字段对不上自己的用例库，无法逐条判断哪些能用；重跑一次常产生重复条目；结果没有可靠保存。
- **本作品的改善**：把"需求 → AI 起草 → 人工确认 → 保存恢复"做成一条闭环业务流程。用户在工作台录入并保存需求，一键把需求引用到聊天；助手按结构化契约生成用例并写入工作台（状态为草稿）；用户核对、编辑后确认；数据落在插件数据库，重进可恢复。AI 的确定作用=按需求起草结构化用例，人保留最终判定权，避免"AI 直接改数据"。

## 当前核心流程（与最小完成范围对齐）

1. 在工作台左侧填写需求标题/描述/模块，点"保存需求"（写库，`revision` 递增）。
2. 点"AI 生成用例"：把带 `requirementId` 与 `requestId` 的需求正文引用到 ChatKit，用户补充说明后发送。
3. 助手生成 3–8 条结构化用例并调用 `testcase_persist_draft` 工具，以**草稿**状态写入数据库。
4. 工作台读到草稿（含步骤、预期、P0–P3 优先级），用户勾选、必要时回聊天让助手改。
5. 点"确认选中"把草稿置为 `confirmed`；或"丢弃选中"删除草稿。
6. 刷新或重进应用，`getState` 从数据库读回需求与用例（不仅存于当前页面内存）。

第 1、4–6 步与失败/重试、幂等、作用域隔离均已有自动化单测（见 03）；第 2–3 步依赖真实模型调用与平台内助手运行，属需在测试平台验收的部分。

## 功能取舍

| 范围 | 状态 | 说明 |
| --- | --- | --- |
| 需求录入、保存、空状态提示 | 已实现并有单测 | `saveRequirement` 校验标题/描述必填 |
| AI 生成草稿用例（结构化工具写入） | 代码已实现 | 需真实模型+平台助手验证 |
| 人工确认/丢弃、保存与恢复 | 已实现并有单测 | 乐观并发 `revision` 冲突即拒绝 |
| 失败重试且不重复生成 | 已实现并有单测 | `requestId` 幂等 + 冲突有界重试 |
| 多用户/组织数据隔离 | 已实现并有单测 | 五维作用域全部参与读写键 |
| 用例直接编辑表单、导出到外部用例库 | 未做 | 超出最小闭环，主动收敛范围 |
| 多需求批量、权限分级、附件 | 未做 | 非默认要求 |

## 与题目要求的关系

题目要求"业务应用而非仅聊天问答"。本作品有可操作工作台、独立数据库持久化与恢复、带状态机的确认流程，AI 只负责起草、人来确认，符合"有明确用户、业务问题、可操作界面、输入→处理→结果查看/确认的完整流程"。风险点：AI 起草这一步的真实模型运行需在平台验收，不以"代码写完"充当"业务跑通"。
