# AI 协作说明

> 本文说明本次开发中如何使用 AI 编程工具，以及我做的判断和取舍。

## 使用的工具与模型

- **工具**：Claude Code 桌面端
- **模型**：deepseek-v4-pro
- **投入时间**：6h
- **分工**：需求拆解、代码实现、问题定位由 AI 主导；真实环境里的操作（搭建平台、安装插件、
  点击界面、查看日志）和方向性判断由我负责

---

## 一、怎么把产品想法和开发背景介绍给 AI

我没有直接说"帮我完善这个简历插件"，而是先做了一件事：**把待改的点拆成七块，
标出优先级，并指明最优先的三件事。**

那份说明里包含：

- **每块改哪个文件**——比如评分规则改 `preview.config.mjs`、抽取 Prompt 改 service 并新建
  `prompts` 模块、结构化字段改 `types.ts` 和 middleware schema
- **每块要达成什么**——不是"优化一下"，而是"把打分规则固化下来""让失败重试不产生重复记录"
- **明确优先级**——我单独写了"最优先做的 3 件事"，并说明为什么是这三件

结果是 AI 第一轮就按优先级推进，没有跑偏。对比来看，如果只说"帮我完善一下"，
大概率会平铺开做，或者先做界面、后补核心。

我从中得到的判断是：**描述需求的颗粒度直接决定输出质量。** 说清"改哪个文件、达到什么效果、
先做哪个"，比说清"我想要什么"更有效。

另外我在动手前先让 AI 复述理解——比如让它说明文档里提到的证据、置信度这些字段打算怎么处理，
确认方向一致了再动手写代码。

## 二、对 AI 建议做过的选择和调整

AI 给方案时倾向"多做"，我需要主动做减法。以下是几次实际的分歧：

| AI 的建议 | 我的判断与处理 |
| --- | --- |
| 立刻把 `evidence` / `confidence` 做成结构化字段，需同时改 `types.ts`、middleware schema、entity 和前端四处 | 我判断这会一次改动四个文件、容易留下半成品，决定按其优先级推迟，先让证据以文本形式落在既有字段里 |
| 删除未被引用的 `app.css` | 我选择先加进 `.gitignore` 保留文件，不直接删——不确定它是否还有用途 |
| 把 `demo/job.json` 换成中性样例数据 | 我不认同这个改动，要求还原 |
| 截图前先把数据脱敏、重跑一遍再截 | 我决定使用已有截图，接受其中的风险 |

**最值得说的是第一条。** AI 的方案在技术上是对的，但会让一次改动横跨四个文件。
在时间有限、明确要求聚焦一条闭环的任务里，**判断"先不做什么"比"把一件事做对"更关键**。

## 三、一起定位问题的过程

### 案例：插件无法安装进 Xpert 平台

这个案例能体现"和 AI 一起排查"的完整过程：**每修掉一层，下一层才暴露。**

#### 第一层：报错信息是空的，这本身是线索

安装插件失败，但报错在文件路径之后就断了，**没有任何 npm 输出**。

判断：如果 npm 启动后失败，一定会有 stdout 或 stderr；输出完全为空，说明进程根本没启动。
这把范围缩小到"启动进程"这一步，而不是"npm 干了什么"。

#### 第二层：最小复现，定位到 Node 在 Windows 上的行为

把平台的调用方式单独抽出来复现：

```js
execFile('npm', ['--version'], cb)              // ENOENT，stdout/stderr 均为空
execFile('npm.cmd', ['--version'], cb)          // EINVAL
execFile('npm', ['--version'], { shell: true }) // 成功
```

根因：Windows 上 npm 是 `npm.cmd`，而 Node 从 v18.20 / v20.12 起为修复 CVE-2024-27980
禁止不带 shell 执行 `.cmd`。

顺着这条线检查平台源码，发现**三处** `execFile` 调用 npm 都命中同一个问题。

**影响面比预想的大**：插件仓库里每个社区应用的 `dependencies` 都至少含 `tslib`，
因此在 Windows 上**任何社区插件都装不上**——与本插件无关。

#### 第三层：修掉之后，错误才继续前移

打上补丁后，安装走到了下一关：SDK 没有构建（平台源码里那行注释写着
"Before using external plugins, you need to nx build this library"）。构建后又暴露作用域问题：
插件声明 `level: system`，但 `package.json` 里没有对应声明。

后一个问题的定位方式值得一说：**对照仓库里已有的 9 个应用**，发现它们都在 `package.json`
里写了 `xpert.plugin.level` 和 `artifactNamespace`，只有本插件漏了。平台在安装前的预检查读的是
manifest 而非代码，读不到就按默认值处理，等真正加载插件时才发现不一致。

这个对比是关键——**同类问题在仓库里的既有实现中往往有答案。**

#### 第四层：确认是平台问题，不是自己的代码

最后卡在平台的**组织初始化失败**：因为第一层的 npm 问题，初始化时预装插件全部失败，
连锁导致没有可用模型、导入默认模板时外键冲突、初始化整体中止。平台日志里能完整看到这条链：

```
spawn npm ENOENT
  → 供应商插件预装失败
    → 没有可用的主 LLM copilot
      → 跳过模型注入
        → 导入模板时 copilot_model 外键冲突
          → 组织初始化中止
```

为确认不是自己的插件有问题，做了两件事：

1. 单独加载编译产物：`dist/index.js` **本地加载正常**，插件名和 level 都对
2. 在平台目录树下搭一个与暂存结构一致的环境（同样的 `node_modules` 布局、
   同样指向 `packages/plugin-sdk` 的 junction），**插件加载成功**

结论：插件本身没问题，卡点在平台。

**这一段的体会**：AI 在"复现和验证"上效率很高——抽出最小复现、搭同构环境这种活，
手写要很久。但**"这条路走不通了，该换个方向"这个判断，以及真实环境里的操作，
只能我自己来**。

## 四、用什么确认作品符合预期

核心思路是**分层验证**：构建通过 ≠ 加载成功 ≠ 用户操作成功，这三层必须分别确认。

| 验证项 | 方法 | 结果 |
| --- | --- | --- |
| 代码正确性 | 类型检查 + 15 项单元测试（覆盖评分规则契约、防注入规则、两种输出模式） | 通过 |
| 仓库约定 | 实体表名检查脚本 `check-plugin-entity-tables.mjs` | 通过 |
| 规则可执行 | `scripts/analyze-resume.mjs` 用真实模型跑抽取与评分 | 通过 |
| 平台加载 | 安装 → 重启 → 查询已加载插件列表 | 出现在 `system:global` |
| 组件注册 | 插件详情页 | 助手模板 / 应用 / 视图 / 中间件工具四类均被识别 |
| 界面流程 | 本地预览走完整流程，含解析失败的异常分支 | 通过 |

**怎么区分"模拟"和"真实"**：本地预览里有个 `fakeAiResult()`，是早期用来造演示数据的模拟函数。
要证明真实模型能跑通，我做了两件事：

1. 写独立脚本直接用 DeepSeek 调用；
2. 让这个脚本**导入编译产物 `dist/lib/prompts/`**，而不是自己写一份 Prompt。

第二点是关键——这样脚本跑的就是插件内实际生效的那套规则，
不存在"脚本能验证、插件里不生效"的情况。

## 五、工具的限制与不足

- **AI 会对着过期状态下结论。** 有一次它判断某个 bug 已修，实际是它读到了修改前的版本。
  上下文变长之后这种情况更容易出现，需要我主动确认"你看的是哪个版本"。
- **AI 无法替代真实环境里的操作。** 搭建平台、安装插件、在界面上点击、看平台日志，
  这些只能自己做。AI 能给出排查方向和命令，但结果必须由真实操作产生。
- **AI 的方案默认偏"多做"。** 在明确要求控制范围的任务里，需要人主动做减法。
- **AI 提供的"已完成"不等于"已验证"。** 构建通过、文件写完，都不等于功能可用，
  必须回到真实环境里确认。
