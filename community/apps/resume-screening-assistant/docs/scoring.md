# 评分规则

本文是简历初筛助手的评分标准，也是 `src/lib/prompts/resume-matching.prompt.ts` 的规则来源。
两者必须保持一致：改这里就要同时改 Prompt，改 Prompt 就要同时改这里。

## 1. 这个分数是什么

AI 给出的是**初筛建议分**，用来决定"要不要花时间看这个人"，不是录用决定。

系统里同时存在两个分数，界面上必须分开显示，不能混用：

| 字段 | 含义 | 谁产生 |
| --- | --- | --- |
| `matchResult.score` | AI 原始分，按本文规则算出 | 模型 |
| `reviewerScore` | 人工复核分，HR 自己填 | 人 |

排序规则（`service.compareCandidates`）：有 `reviewerScore` 时用人工分，没有时才退回 AI 分。
也就是人工分一旦填写，就完全覆盖 AI 分参与排序——AI 分只作为参考保留。

## 2. 总分构成

```
总分 100 = 硬性要求 40 + 经历相关 25 + 技能能力 20 + 风险完整度 15
```

计算顺序是固定的：

1. 先算四个维度各自的分数，**每个维度四舍五入到整数**
2. 再求和得到 `score`
3. 最后用 `score` 定推荐值档位，再用覆盖规则降级

`score` 必须真的等于四个维度之和。不允许为了让推荐值看起来自洽而调整总分。

## 3. A. 硬性要求（40 分）

这一维度回答的是"门槛过没过"，权重最高，也是最容易出现分歧的地方。

**判定项**由三部分构成：

- 岗位的每一条必备技能
- 最低经验年限（岗位填了才算）
- JD 正文中以「必须 / 要求 / 需具备 / 只招」明确表述的硬性条件

判定项总数记为 `n`，**每项分值 = 40 / n**。所以判定项越多，单项扣分越轻。

**每一项三态判定**：

| 状态 | 得分 | 判定标准 |
| --- | --- | --- |
| 满足 | 满分 | 简历中有明确对应的技能或经历 |
| 部分满足 | 一半 | 技术栈相近但不是同一项；年限接近但不达标；简历表述含糊无法确认 |
| 不满足 | 0 | 简历中完全没有相关证据 |

关键约定：**证据不足按"部分满足"记，不按"满足"记。**
模型看不到证据时倾向于给"满足"，这是评分虚高的主要来源，所以规则上强制往保守一侧压。

最低经验年限单独判定：实际 ≥ 要求记满足；差 1 年以内记部分满足；差 1 年以上记不满足，并写入风险项。

## 4. B. 经历相关（25 分）

分三个子项：

| 子项 | 分值 | 判定 |
| --- | --- | --- |
| B1 行业与业务域相关度 | 10 | 一致 10 / 相近 6 / 无关 0 / 看不出行业 3 |
| B2 岗位职责重叠度 | 10 | `10 × 重叠条数 / JD 职责条数` |
| B3 项目复杂度与规模 | 5 | 主导或 0-1 或带团队或大规模 5 / 参与非主导 3 / 无证据 0 / 无项目描述 2 |

B1 和 B3 在"无信息"时不记 0 分，而是记中间分。原因是信息缺失不等于经历不相关，
真正的不相关要能拿出反证（比如 JD 要金融，简历全是餐饮）。这一点与 A 维度的保守原则相反，
因为 A 是门槛判断，B 是程度判断。

## 5. C. 技能能力（20 分）

| 子项 | 分值 | 判定 |
| --- | --- | --- |
| C1 加分技能命中 | 8 | `8 × 命中数 / 加分技能总数` |
| C2 JD 其他技能命中 | 7 | JD 正文出现但未列入必备/加分的技能，按命中比例 |
| C3 技能深度证据 | 5 | 在项目或职责中实际使用 5 / 仅在技能清单罗列 2 / 无法定位 0 |

**降级规则**：岗位没有填加分技能时，C1 的 8 分并入 C2，C2 满分变为 15 分。
这样做的原因是加分技能为空时 C1 无法计算，直接给满分会凭空抬高总分。

C3 是这一维度里最有价值的区分项：技能清单是候选人自己写的，谁都可以列；
技能出现在项目描述里并带具体动作或产出，才是真的用过。

## 6. D. 风险与完整度（15 分）

**扣分制**：从 15 分开始扣，扣到 0 分为止。每扣一项都必须在 `riskFlags` 里写对应条目。

| 风险 | 扣分 |
| --- | --- |
| 时间线有 6 个月及以上缺口且未说明 | -3 |
| 工作经历只有公司名和时间段，无职责描述 | -3 |
| 学历、院校或证书表述模糊、无法核实 | -2 |
| 联系方式缺失或不完整 | -1 |
| 文本疑似截断、PDF 解析错乱或有 OCR 噪声 | -4 |
| 前后矛盾（时间、职级、技能深度对不上）或明显夸大 | -6 |
| 简历原文不足 200 字 | -3 |

这一维度惩罚的是**简历质量**，不是候选人质量。一份内容真实但写得很简略的简历会被扣分，
这是刻意的：信息不足时初筛无法判断，扣分的作用是把它推给人工复核，而不是直接判定不合格。

## 7. 推荐值判定

**第一步，按总分定档**：

| 分数 | 推荐值 |
| --- | --- |
| ≥ 80 | `interview` |
| 60 - 79 | `hold` |
| < 60 | `reject` |

**第二步，覆盖规则降级**。覆盖规则只能把推荐值调低，不能调高：

1. 硬性要求不满足项 ≥ 2 条 → 一律 `reject`
2. 存在"前后矛盾或明显夸大"扣分（-6 那项）→ 一律 `reject`
3. 硬性要求不满足项 = 1 条 → 最高只能 `hold`

覆盖规则**只改推荐值，不改分数**。

举个例子：某候选人的四个维度加起来是 84 分，但有 2 条必备技能不满足。
最终结果是 `score = 84`、`recommendation = reject`。
看起来"分数高却是 reject"有点矛盾，但这是有意的设计——分数反映综合匹配程度，
推荐值反映门槛是否通过，两者回答的是不同问题。人工复核时能看到 84 分和 reject 的原因，
比看到一个被篡改成 55 分的分数更有信息量。

## 8. 可追溯性要求

`reason` 字段必须包含固定格式的评分明细，这是人工复核核对分数的依据：

```
【评分明细】
硬性要求 A: 32/40
经历相关 B: 18/25
技能能力 C: 15/20
风险完整度 D: 12/15
合计: 77/100
【推荐值】hold，依据：...
【说明】...
```

`scripts/analyze-resume.mjs` 会解析这段明细，校验 `合计` 是否真的等于四项之和。
格式被改坏时脚本会报错，所以这不是"建议格式"，是契约。

## 9. 稳定性

同一份简历、同一份 JD 重复评分，四个维度的分差不应超过 3 分。

模型在两项判断之间摇摆时，规则要求选更保守的一项，并把摇摆原因写进说明。
分数波动过大意味着规则里有含糊处，应该回头改 Prompt，而不是接受波动。

## 10. 已知限制

- **评分是启发式的，不是统计模型产出的**。规则由人设定，模型负责执行，没有经过标注数据校准。
- **规则对"相近技术栈"的宽严程度依赖模型判断**，比如 Vue 经历应聘 React 岗位算不算部分满足，
  不同模型可能给出不同结果。
- **分数不能跨岗位比较**。40 分的硬性要求是按每个岗位自己的必备技能算的，
  A 岗位的 75 分和 B 岗位的 75 分不是同一个含义。
- **`reviewerScore` 没有校准机制**。HR 打分和 AI 打分长期偏离多少，系统不做统计。
