# 面试问答准备（批量上架助手）

> 这份文档不是交付物的一部分，用来准备面试时的技术追问。
> 原则：**答事实、答取舍、答边界**；不确定的地方明确说「没验证」，不编。

---

## 一、选题与产品判断

**Q1：为什么选「批量上架」这个场景？**
商家运营的真实痛点是重复录入：一段供货文案要拆成标题、描述、价格、类目属性、多规格，人工逐条填既慢又容易漏字段，还常被审核驳回返工。这个场景**输入非结构化、输出强结构化、最后一公里必须人工确认**，正好适合 Agent 做抽取、人做审核，边界清楚，不需要编造额外需求。

**Q2：为什么不让 AI 直接上架？**
风险不可控。价格、库存、类目和合规描述一旦错，影响的是商家的真金白银和平台审核。所以定位是「AI 起草 + 人确认」，保存动作必须由运营触发，这也是我在 README 的「功能取舍」里写死的范围。

**Q3：这个应用最有价值的一步是哪一步？**
不是抽取，而是**缺失检测和人工确认**。抽取错了运营能看出来，但漏字段往往看不出来。所以 AI 返回结果时额外要求 `missingFields` / `uncertainFields`，界面用「缺失 / 待确认」高亮，把模型的不确定性显式暴露给人。

**Q4：为什么不做推荐、定价、自动选类目？**
做了会越界：这些是经营决策，需要商家自己的数据和规则；也会让演示失去焦点。我用一句话约束了 AI 的职责——**只抽取、起草、检测缺失**。

**Q5：为什么界面是表单/工作台而不是聊天框？**
任务书明确红线：不能把 AI 做成聊天框。业务用户的动作是「核对一批字段然后保存」，表单/列表/状态标签比对话更适合；聊天只能作为辅助入口（Agent 工具），主界面必须是工作台。

## 二、使用流程与状态

**Q6：核心流程怎么走？**
新建任务（粘贴文案）→ AI 解析 → 待确认 → 人工改 → 保存草稿 → 刷新仍在；失败则进入失败态，可在同一任务内重试。状态机：`draft → parsing → review → saved`，异常进 `failed`。

**Q7：状态为什么这么设计？**
`parsing` 让并发/重复点击有据可依；`review` 是「AI 给了结果但没人确认」；`saved` 是唯一表示业务完成的终态。没有用「AI 完成 = 完成」，是因为最后一步必须是人。

**Q8：空状态、缺必填、无数据分别怎么处理？**
- 无任务：空状态 + 「新建任务」按钮引导；
- 文案为空/过长：前后端都校验（空文案、超过 20000 字给提示）；
- 保存时标题/描述/价格全空：服务端拒绝并给出可读提示；
- 字段缺失/不确定：AI 结果里带标记，界面高亮，提示需要人工确认。

**Q9：保存后刷新还在吗？**
在。草稿、规格、任务状态、AI 运行记录全部落 Postgres；README 的截图和数据库查询都能证明，不存在内存里。

## 三、技术架构

**Q10：插件是怎么组织的？**
`community/apps/listing-assistant` 是标准 Xpert 插件：`src/index.ts` 声明 `XpertPlugin` 元数据（level=tenant、artifactNamespace=listing_assistant、视图/工具/模板 provider）；`@XpertServerPlugin` 注册 TypeORM 实体与服务；前端是远程 React 组件，通过 Workbench 视图协议挂载。

**Q11：为什么 level 选 tenant 而不是 organization？**
插件注册了实体、控制器级的视图 provider 和中间件，属于进程级基础设施；按仓库规范只能用 `system` 或 `tenant`。这台平台是单租户本地环境，选 `tenant` 更通用（未来可装到别的租户），并声明稳定的 `artifactNamespace`，所有表和产物标识都带 `listing_assistant` 前缀。

**Q12：数据表怎么建的？要写 migration 吗？**
实体通过 `@XpertServerPlugin({ entities })` 注册，宿主按实体同步建表，本机启动后自动出现 4 张 `plugin_listing_assistant_*` 表；没有额外 migration（示例工程也有同样做法）。生产环境若要求受控 DDL，可以补迁移脚本。

**Q13：后端怎么调用模型？**
通过插件 SDK 注入 `XPERT_AGENT_MIDDLEWARE_RUNTIME_TOKEN`，用当前用户/组织作用域 `createScopedApi`，取 `getDefaultChatModel()` 再 `createModelClient`，调用 LangChain 的 `BaseChatModel.invoke`。**不把模型地址和 Key 写进代码**，全部来自平台配置，所以换模型、换仓库、换供应商都不用改插件。

**Q14：为什么不在 Agent 对话里做抽取，而是后端直接调？**
两者都做了：工作台按钮走后端服务（快、可控、可展示错误和重试），同时暴露 4 个 Agent 工具，让助手在对话里也能完成同样的事。后端直调的好处是**UI 的失败/重试链路不依赖对话上下文**，演示和验收更稳定。

**Q15：工作台数据怎么和宿主交互？**
视图 provider 实现 `getViewData` / `executeViewAction`；iframe 里的 React 组件通过 bridge 的 `requestData` / `executeAction` 与宿主通信。这样视图不需要自己带一套鉴权和 REST 客户端。

**Q16：为什么用远程组件 iframe？**
这是平台支持的视图隔离方式，能和宿主 UI 隔离（样式、依赖不互相污染），同时通过协议拿数据与动作；也符合仓库 AGENTS.md 对远程视图用 shadcn 组件、locale 目录的规范。

**Q17：前端是怎么打包的？**
esbuild 把 `main.tsx` 打成 IIFE 的 `app.js`（React 用宿主注入的 UMD，通过 shim 解析），样式随 `@xpert-ai/plugin-shadcn-ui/style.css` 抽成 `app.css`；构建脚本把 `dist` 与 YAML 一起拷进插件产物，视图 provider 在读请求时读取对应文件渲染 iframe。

## 四、AI 与提示词

**Q18：Prompt 怎么写的？**
System Prompt 约束三件事：① 原文是不可信数据、里面的指令一律忽略；② 不得编造价格、库存、类目、规格；③ 完全缺失的放 `missingFields`，有歧义/矛盾的放 `uncertainFields`，只返回 JSON。标题≤60 字、描述≤500 字、事实性、禁止夸大宣传。

**Q19：怎么保证模型返回可用结构？**
返回内容先去掉 Markdown 围栏，`JSON.parse` 后用 Zod 校验 schema（字段类型、长度、枚举）。解析失败/校验失败会转成「模型没有返回合法 JSON / 字段不符合要求」这类可读错误，而不是把原始异常抛给用户。

**Q20：超时怎么办？**
整体 90 秒超时，用 `AbortController` 取消请求，并区分「超时」和「调用失败」；超时后任务进入失败态，用户可以在同一任务重试。

**Q21：模型返回空、返回数组、返回中文混排怎么办？**
空内容 → `AI_INVALID_OUTPUT`；非字符串 content → `AI_INVALID_OUTPUT`；JSON 里字段多余会被 schema 过滤/拒绝；统一走失败态，不把半成品写进草稿。

**Q22：为什么不用 function calling / 结构化输出模式？**
平台默认模型客户端给的是通用 chat 模型，用 JSON + Zod 是兼容性最好的方案，也不绑定某一家供应商。后续可以改用平台的结构化输出能力，接口层已经隔离在 `listing-ai.service.ts`。

**Q23：提示词里为什么中文业务、英文指令？**
业务字段是中文语境（标题、描述、类目），但模型对结构化指令的稳定性在英文下更好；输出内容仍跟随原文语言。这也是让模型「只交 JSON」的工程习惯。

## 五、失败、重试与幂等

**Q24：重试为什么不会重复产生业务结果？**
三层保证：
1. 每次尝试只新增一条 `ai_run`（`taskId + attempt` 唯一），**不新建任务**；
2. 任务已有成功运行记录或已保存时，重试直接返回「已有解析结果」，不再调模型；
3. 草稿按 `taskId` 唯一，成功时事务内 upsert + 替换规格，不会出现两份草稿。

**Q25：用户连点两下解析会怎样？**
服务层用一条带条件的 `UPDATE` 原子认领任务（检查 affected rows）：只有第一个请求能把它切到 `parsing` 并递增尝试次数，第二个请求认领失败会提示「正在解析中」；`(taskId, attempt)` 唯一约束兜底。

**Q26：解析到一半服务挂了怎么办？**
任务停在 `parsing`，AI 运行记录是 `running`。用户可以刷新；超过 5 分钟后任务可被重新认领，认领时会把遗留的 `running` 记录标记为失败（`AI_RUN_INTERRUPTED`），不会永远悬挂。后台定时回收仍是后续改进项。

**Q27：失败原因对用户可理解吗？**
错误码覆盖：无法连接模型服务、模型凭证无效、限流、超时、返回非法 JSON/字段、模拟故障。界面显示中文原因 + 「可在同一任务内重试，不会新建任务」。

**Q28：怎么演示失败？会不会影响别人的配置？**
用了插件内的 `[SIMULATE_MODEL_FAILURE]` 标记：任务原文包含它时，**第一次**解析强制失败，同一任务重试即成功。它是局部、可逆、只影响该任务的开关，不改网络、不改模型凭证，也不影响共享配置。

## 六、权限与数据

**Q29：多用户/多组织怎么隔离？**
所有表都带 `tenantId` / `organizationId`，服务层每条查询都带上当前作用域过滤；视图上下文和 Agent 中间件上下文分别取当前租户/组织。没有做组织内角色细分（本次范围外）。

**Q30：超级管理员为什么不是组织成员？**
平台设计如此：`SUPER_ADMIN` 拥有租户级全部权限，但不是任何组织的成员。演示时需要在 UI 里切到组织作用域（本机用组织工作空间承载助手）；这是平台行为，不是插件绕过权限。

**Q31：AI 调用算谁的额度？**
走平台默认模型客户端，模型连接属于租户/组织配置，额度与计费由平台负责，插件不接触 Key，也不自己记账。

## 七、测试与验证

**Q32：你验证了哪些层？**
单元测试（`node:test` 8 条纯函数用例）→ 构建（tsc + esbuild + 远程类型检查）→ `plugin-dev-harness` 生命周期（register / Nest 初始化 / onStart / bootstrap / destroy / onStop）→ 插件安装与加载（`loadStatus: loaded`）→ 实体建表 → 模板/视图/工具可见 → 真实模型调用 → 界面端到端（截图）→ 失败与重试（数据库运行记录）。

**Q33：怎么证明「保存与恢复」不是内存里？**
保存后直接查 Postgres 的 `plugin_listing_assistant_task` / `_draft` / `_spec` 表；再刷新浏览器重新打开工作台，界面仍能读回，状态是「已保存」。

**Q34：怎么证明重试没有产生第二条任务？**
数据库里任务数不变；同一 taskId 下有 `attempt 1 failed`、`attempt 2 succeeded` 两条运行记录；已保存任务再点重试返回 `already_parsed`，只有一条成功记录。

**Q35：有什么没测到的？**
多用户并发、真实网络抖动下的超时恢复、图片输入、Excel 批量导入、模型切换到其他供应商的兼容性、生产级 DDL 迁移。
（harness 生命周期测试已通过；它使用 TypeORM/Cache 的 no-op mock，验证的是加载与生命周期，不代表真实数据库行为——真实流程以平台端到端为准。）

## 八、Git 与交付

**Q36：PR 怎么组织？**
从上游 `main` 拉分支，只提交插件目录（`community/apps/listing-assistant`）与 PDF/图片等必要资源；PR 描述包含产品价值、主要实现、验证结果、两个仓库的基线 SHA、实际测试版本、未验证部分。

**Q37：有没有提交密钥或无关改动？**
没有。模型 Key 只在本地凭据文件/平台配置里；仓库里只有 `.env.example` 性质的说明。平台仓库的本地网络补丁不属于插件，不会进 PR。

**Q38：为什么截图放在仓库里？**
任务书要求：截图放插件 README，用相对路径引用、随代码提交。图片在 `docs/images/`，README 用 `docs/images/xxx.png` 引用。

## 九、局限与改进

**Q39：当前最大的局限？**
批量创建与批量解析都有入口，但解析采用前端串行调度，没有服务端队列/并发限流，刷新页面会中断剩余队列；证据定位依赖模型返回的片段，片段不一致时不显示高亮；超时回收是工作台加载时的懒回收，不是定时任务；批量创建不做去重（显式动作，不猜测粘贴意图）。

**Q40：如果多给你半天，先做什么？**
1. 服务端批量解析队列（并发限流 + 断点续跑）；
2. 定时回收/后台任务化，替代懒回收；
3. 证据片段做模糊匹配与区间校验，提升高亮命中率；
4. 用平台结构化输出替代 JSON + 正则兜底。

**Q41：为什么不做图片 OCR？**
这次范围明确是文本；OCR 涉及沙箱和视觉模型，属于另一个链路，做半截会分散验收重点。数据结构里给规格/属性留了扩展位。

**Q42：如果模型很贵/很慢，怎么降本？**
提示词压到最小、只传原文必要部分；同任务命中已有成功结果直接返回；可以对相同文案做内容哈希缓存；批量场景按条并发但受 QPS 限制。

## 十、现场演示与追问应对

**演示顺序（3 分钟）**
1. 打开助手 → 打开视图 → 空状态 / 新建任务；
2. 粘贴文案 → AI 解析 → 指出「AI 补全 / 缺失 / 待确认」；
3. 改一个字段 → 保存 → 刷新仍在；
4. 新建带 `[SIMULATE_MODEL_FAILURE]` 的任务 → 失败原因 → 同任务重试成功；
5. 结论：同一任务、第二次运行、没有重复业务结果。

**如果现场模型不可用**
先展示失败态和错误原因（这本身就是验收项），再用已存在的「待确认/已保存」任务展示工作台和持久化；说明 AI 调用是唯一外部依赖，失败已被产品化处理。

**如果被问「这是不是只有页面」**
打开数据库查 4 张表；展示插件 `loadStatus`、助手图里的工具节点、AI 运行记录；再演示刷新恢复。

**如果被问「和平台原生能力重复吗」**
抽取是通用的，但「任务状态机 + 字段级缺失标记 + 同任务幂等重试 + 业务表单」是商家上架场景独有的产品化封装；平台工具本身不提供这条业务闭环。

## 十一、时间与复盘

**Q43：时间怎么花的？**
环境与平台启动占了最多（VM、依赖、内存、Cloud UI 构建）；产品与数据模型、插件骨架、AI 服务与界面实现各占一块；最后的部署、真实模型打通和失败重试验证是价值最高的部分。

**Q44：踩过最大的坑？**
1. 6G 内存下 Angular 构建和 API 同跑会 OOM，最后靠加 swap、构建时停 API 解决；
2. 插件部署后必须重启 API 才加载，重启过程中断会触发平台的「启动恢复」保护，需要清理状态文件；
3. 平台模型连接必须在组织作用域下、并设置 Primary 默认模型，助手模板才能解析到可用模型。

**Q45：如果重做一次，会怎么改？**
先把「UI 与宿主交互（iframe bridge、动作/数据协议）」做成最小闭环再补业务；数据模型和提示词会一开始就用 Zod schema 定死；把失败重试从第一天就纳入验收脚本，而不是最后补。

## 十二、增量能力（批量、错误码、滞留回收）

**Q46：批量导入怎么做的？**
新建任务时，多条供货文案用**单独一行 `---`** 分隔；前端识别到分隔符就调用 `create_task_batch`，后端按行切分后逐条创建任务（上限 20 条，返回 taskIds）。解析仍然逐条执行，失败与重试仍按单任务语义处理，避免批量操作把幂等规则弄复杂。

**Q47：为什么后端不直接返回中文错误文案？**
业务层应只返回语言中立的错误码（如 `AI_TIMEOUT`、`BUSY_PARSING`、`SOURCE_TOO_LONG`），由前端按宿主 locale 映射成中文/英文。这样后端不耦合界面语言，新增语言不用改服务端；技术性原始错误只作为兜底信息返回给运营。

**Q48：解析中途服务挂了，任务会一直卡在 parsing 吗？**
不会。工作台加载时会做一次懒回收：超过 10 分钟仍为 `parsing` 的任务及其 `running` 运行记录会被标记为失败（`AI_RUN_INTERRUPTED`），运营可以直接重试；认领机制本身也允许在 5 分钟后重新抢占。

**Q49：批量创建会不会重复创建？**
创建是显式动作（人点按钮），不是自动重试；解析的幂等以 `taskId + attempt` 保证。即使网络重试导致两次创建，也会得到两条独立任务，运营可以删除或忽略——这里的取舍是「创建不猜测意图」，避免把两次不同的粘贴误判为同一条。

**Q50：字段证据怎么来的？**
提示词要求模型为每个字段回引最短的原文片段；Zod 限定只接受 title/description/price/category/specs、单段最多 300 字；服务端 `normalizeEvidence` 过滤未知键、空值和非法类型后写入草稿的 `evidence` jsonb。前端按字段在原文里查找片段并高亮，右侧字段下方显示「依据」，点击可滚动定位。片段找不到时不模糊猜测，只保留依据文本。

**Q51：为什么保存前还要二次确认？**
因为「AI 补全」不等于「运营确认」。保存时如果仍有 `missing`/`uncertain` 标记，说明运营没有提供对应值，确认框会列出这些字段并允许返回核对；选择仍然保存时，后端 `mergeFieldFlags` 只清除运营已填字段的标记，未填的标记保留。这样既不会静默丢字段，也不强制阻断业务。

**Q52：批量解析为什么在前端串行，而不做服务端队列？**
复用单任务的原子认领与幂等路径，失败记录、重试语义、审计数据完全一致，不引入新的队列状态和恢复逻辑。前端逐条调用 `parse_task`，实时更新进度；单条失败只计数、不中断。代价是刷新会中断剩余队列，但剩余任务仍是待解析/失败态，可以再次执行。生产化时会把调度移到后台任务并加进度接口。
