# AI 协作说明

## 1. 使用的工具与模型

| 工具 | 模型 | 承担的工作 |
| --- | --- | --- |
| Claude 桌面端（Agent 会话） | GLM-5.3（通过 Switch cc 切换） | 阅读中文面试说明、模糊选题分析、生成开发指南、本地环境搭建与部署排障 |
| Codex | GPT-5.6 | 插件代码开发、代码自审与迭代、UI 设计参考生成、浏览器自动化测试 |
| workbuddy | Free Plan | 功能说明书.html 等文档类产出 |

辅助 Skills：Xpert 官方开发技能（平台环境 / 插件开发 / 业务应用开发）、ponytail（精简输出、节省 token）、imagegen（UI 参考图）、Computer Use（浏览器操控测试）。

## 2. 模型分工的依据

不是所有环节用同一个工具，而是按各家长处分派：

- **GLM-5.3 读中文材料**：面试说明是中文长文档，需要准确理解验收口径和隐含要求（如「单一工具不算业务应用」「必须有失败重试场景」）。相比 GPT，GLM 在中文语义细节上更稳，选题评估和指南产出由它完成；
- **GPT-5.6 写代码**：代码生成与多轮迭代是它的强项，作为开发主力；
- **workbuddy 出文档**：内置办公技能更擅长格式化文档输出，功能说明书由它生成，Codex 专注代码。

## 3. 结构约束先行的开发方式

给 Codex 的 prompt 中固化了目录结构规范，原文如下：

> 约束：生成代码项目时，请严格遵循以下目录结构规范：
>
> 1. 采用分层架构，严格区分入口层、接口层、业务层、数据层、工具层，禁止业务逻辑和数据访问混写。
> 2. 目录按职责划分，单一职责原则，每个目录只负责一类功能；业务模块按领域垂直拆分，不按文件类型横向拆分。
> 3. 公共能力统一放在 pkg/utils 层，业务私有逻辑放在 internal 对应模块内，禁止跨层反向调用。
> 4. 配置、部署、脚本、文档均放在根目录对应独立文件夹，不混入源码目录。
> 5. 先输出完整的目录树结构，确认结构清晰可扩展后，再逐文件生成代码；生成过程中保持目录结构一致性，不得随意新增顶层目录。
> 6. 所有代码文件必须放在对应职责目录下，禁止在根目录散落业务代码文件。

这样约束的原因：AI 自由发挥目录结构时容易漂移（多轮迭代后结构越来越乱），把架构决策从 AI 手里收回到人手里，后续生成质量明显更稳。

## 4. 有代表性的协作过程

### 1. imagegen 做 UI选择题

界面设计环节，用 Codex 的 imagegen skill 生成了多张 UI 设计参考图，我从中选择接近预期的方案，再让它落到代码实现；本地部署查看实际效果后继续追问微调。这个过程里 AI 出方案、我做选择——把开放式设计变成选择题，效率远高于用文字描述界面再返工。

### 2. Computer Use 自动化回归测试

功能测试除了手动走流程，还用 Codex 的 Computer Use skill 直接操控浏览器，反复执行数据相关的操作路径做回归。手动测试覆盖主观体验（交互是否顺手），自动化测试覆盖重复性验证（数据一致性、状态流转），两者互补。

### 3. 双 AI 的代码自审与人工验证闭环

开发后期让 GPT-5.6 对自己的产出做审核和迭代；同时用另一工具（Claude + GLM）做交叉评审——独立视角发现了不少单工具自查漏掉的问题（如构建链完整性、视图接口齐备性）。AI 审 AI 之外，最终仍以本地编译、测试运行、平台内部署作为裁判。

### 4. 环境与部署排障（Claude + GLM）

本地搭建平台与插件部署过程中遇到多处环境问题（包管理器多版本共存、构建工具崩溃、插件白名单配置等）。这类问题的排障由 AI 读日志定位根因、我执行验证命令确认，来回收敛。看报错猜原因的环节交给 AI 显著提速，但每一步修复都以真实运行结果为准。

## 5. 我的选择与收获

- **架构决策权留在人手里**：目录结构、技术边界、功能取舍由我定死在 prompt 和评审里，AI 负责填充实现。生成代码快不快是其次，方向对不对是人该管的；
- **按长处分派模型**比一个模型干到底效果好，代价是多工具间上下文需要手动同步（以文字结论传递）；
- **AI 的输出必须过验证链**：看起来完整的代码能通过编译、能加载、能在平台跑通之间隔着构建、测试、harness、平台部署四道关，每道都不能省；
- ponytail 类精简型 skill 在长会话里明显降低 token 消耗，让迭代轮次可以更多。

## 6. 遇到的工具限制

- 多工具上下文不互通：Claude/G LM 会话里的排障结论、Codex 里的代码约定，跨工具时要手动搬运，存在信息损耗；
- imagegen 参考图与真实组件存在视觉差距：落地到代码时仍需按实际组件库调整，参考图只定布局与风格方向，需要多次追问应用代码才能实现一致的效果
- 新框架（Xpert）的知识有时滞后于其文档，需把官方文档 URL 直接喂给工具学习后再动手，避免凭旧知识生成不兼容代码。
