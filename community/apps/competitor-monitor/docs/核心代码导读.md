# 核心代码实现逻辑

阅读顺序：插件入口 → 工作台接口 → 业务服务 → AI 工具 → 人工审核与删除。

## 1. 注册与数据入口

`src/index.ts` 声明能力与模板，`src/lib/plugin.ts` 注册实体、服务、中间件与视图提供者。`view.provider.ts` 接收宿主传入的租户和组织上下文，分派查询与动作，不采用前端输入来扩大数据范围。

## 2. 采集与确定性差异

`service.ts` 的 `collect` 在单 API 进程中阻止同范围并发采集。`collectExclusive` 根据幂等键查找轮次；成功轮次直接复用，暂停轮次要求先恢复。逐个读取监控中商品，按历史快照数量选择两组 Mock 中的一组，同轮已有快照优先复用。首次只保存基线；后续比较价格、标题、促销，使用“轮次＋商品＋维度”作为变化主键写入差异。

模型不参与差异生成。Mock 数组是重复测试用的采集证据，不代表真实行情。

## 3. 失败、重试与恢复

采集异常写入原因、失败商品和次数。轮次重试次数或商品连续失败达到三次时暂停。`retryCollection` 取回原幂等键，因此保留 roundId；`resumeCollection` 恢复对应失败商品和轮次，不恢复其他人工暂停的商品。

## 4. AI 分析

工作台 `prepareAnalysis` 标记分析在途并生成含轮次 ID 的消息。界面通过宿主助手命令发起调用，中间件提供五个工具：分页读取事实、确认严重程度、生成建议、报告问题、完成分析。

`getRoundChanges` 返回差异和已有建议状态；`createAdvice` 检查操作幂等键及变化类别，保留已存在的审核结果。`finishAnalysis` 确认所有变化都有建议后，用版本校验完成轮次并释放分析标记。模型失败由中间件尝试记录到最新用户明确指定的轮次；异常中断未释放的标记会阻止删除，应完成或报告该分析失败后再清理。

## 5. 人工审核与保存

界面按钮携带建议 ID 和 revision。`review` 在同一更新语句中校验 ID、租户、组织和版本，保存采纳或驳回状态并增加版本。页面重新查询服务端数据，采纳不会调用店铺接口执行修改。

## 6. 单条、批量删除与清空

`deleteRecords` 检查在途业务操作并开启事务；`deletion.ts` 要求明确组织，拒绝采集或分析中的数据清理。服务端计算关联集合与数量，返回当前数据摘要。人工确认时重新计算摘要，数据已变化则拒绝执行。

按建议 → 变化 → 快照 → 轮次 → 商品的顺序删除，失败整体回滚。商品删除保留历史轮次；轮次删除保留商品；单独删除建议保留事实，再分析可能生成新建议。所有查询及删除均限定宿主范围。

## 7. 界面与验证

`src/remote/main.tsx` 挂载 React；`bridge.ts` 校验宿主消息、匹配请求、处理超时及主题/语言；`App.tsx` 管理互斥和最新读取；`components/` 按商品、轮次、建议及删除职责拆分。React 默认转义文本，审核携带版本，AlertDialog 携带服务端删除摘要。当前列表有数量上限，不应将显示数量当作组织总量。

`tests/` 覆盖业务结果、隔离、失败恢复、幂等、审核与事务回滚。SQL.js 和 Harness 不是生产数据库、多实例锁或真实账号权限验收。现有互斥仅适用于单 API 进程。
