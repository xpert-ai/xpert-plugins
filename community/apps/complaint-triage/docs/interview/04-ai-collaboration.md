# AI 协作说明

## 工具与分工

- **工具**：Claude Code 桌面版（模型 Claude Fable 5.1）。业务运行时的模型是 DeepSeek（`deepseek-v4-flash`），由平台调用，与开发工具无关。
- **我做的**：给出题目说明和截止时间；在 AI 给出的候选里确定选题（客诉分诊）和模型供应商；批准开工；完成所有必须由本人操作的步骤（注册平台管理员、填写模型 Key、选择默认模型、输入账号执行部署）；审阅产品说明、代码与最终差异；决定何时 Fork、推送和发起 PR。
- **AI 做的**：通读题目与配套 Skills，排查和搭建环境，设计数据模型与状态机，编写实现、测试、脚本和文档，在平台内做验证并记录结果。
- **约定的边界**：AI 不经手任何密码和密钥（部署脚本自己提示输入，不落盘、不进命令行）；Fork、推送、发 PR 这类对外动作先问我。

下面是几段有代表性的过程，都是真实发生的。

## 1. 怎么把背景交给 AI

我只给了题目文档和一句“看一下文档”。AI 先总结硬性要求并指出文档里一处空缺（“最小完整示例”的地址写着待补齐），然后**没有直接答应“能做”**，而是先核查了本机条件：工具链版本、GitHub 登录状态、磁盘内存、Docker 是否在跑、官方示例应用的规模。核查之后才给出“能做、我来做哪些、哪些必须你来”的分工，并用选择题让我定选题、模型和是否立刻开工。

收获：让 AI 先拿证据再下结论，比直接问“你能不能做”得到的答案可靠得多。

## 2. 一起定位问题：Docker Desktop 启动即崩溃

启动 Docker 时弹出 “An unexpected error occurred … initializing Inference manager … The file cannot be accessed by the system”。界面上最显眼的按钮是 “Reset to factory defaults”。

AI 的处理：先提醒不要点重置（会清空我已有的镜像和容器）→ 查看报错目录，发现是上次异常退出残留的 AF_UNIX 套接字文件 → 普通删除失败（系统错误 1920）→ 改为**把目录改名挪开**让 Docker 重建。第一次修完报错换成了另一个目录里的同类文件，AI 没有继续逐个试，而是一次性扫描所有 Docker 目录，又验证了“连刚新建的套接字也删不掉”，据此判断是系统层面的问题，检索后确认是 Windows 11 build 26200 上的已知缺陷（docker/desktop-feedback #460、#554、#676），最后把绕行方法固化成可重复执行的脚本。

收获：第二次出现同类报错时，该做的是扩大排查面找共因，而不是再修一次。

## 3. 对 AI 建议的取舍：平台到底跑在哪

题目建议“Docker 跑基础设施 + 源码跑 API 和界面”。AI 没有照搬，而是先查了三件事：本机没有 MSVC 编译工具（平台依赖 `isolated-vm`、`node-pty` 等原生模块）；WSL 里的 Ubuntu 已损坏；官方环境脚本依赖 `lsof`，在 Windows 上直接报错。结论是把 API 和界面放进一个与官方生产镜像同为 Node 20 的 Linux 开发容器，源码和提交仍在 Windows 侧，构建前同步进容器。代价（多一步同步）和收益（不改系统、不碰坏掉的 WSL、6379 端口与我本机 Redis 的冲突自然消失、一条命令可复现）都摆出来之后我同意了。

另一个小取舍：容器里 npm 官方源只有约 24 KiB/s。AI 换成国内镜像前先说明了依据——pnpm 会用 lockfile 里的 sha512 校验每个包，换源不改变装到的内容；并检查了最终 lockfile 里没有混入镜像地址。

## 4. 设计上采纳了 Skills 的约束，而不是 AI 的第一直觉

最初的工具设计是让模型在结果里直接引用原文片段、由服务端做子串比对。读到 Skills 中 *Agent Tool Parameter Design* 的原则（“模型只提供判断；引用、修订号等应由服务端从自己的数据重建”）后，改成：`complaint_get_ticket` 返回带编号的句子，模型只回传句子编号，原文由服务端还原。这样引用**在构造上就无法伪造**，也不会因为标点空格差异导致校验失败、白白多跑几轮。同一原则还去掉了工具入参里的尝试序号和各种 id。

还有一处是我更看重的产品判断：助手通过对话“打开”工单时可以自动开始分析，但**不允许**替换一份已经在等人工确认的建议——覆盖人正在看的结果，必须是人自己点“重新分析”。

## 5. 测试发现的问题

并发用例最初写成两个请求 `Promise.all` 并行，结果失败。原因不是业务逻辑，而是测试用的 sql.js 只有单连接，不能同时开两个事务。AI 没有删用例或放宽断言，而是换成更准确的写法：让两个调用者拿着**同一份过期快照**先后发起，验证条件更新只放行一个。这比并行跑更确定地覆盖了“双击 / 并发只登记一次尝试”。

另外两个依赖层面的坑：已发布的 `@xpert-ai/contracts`、`@xpert-ai/plugin-sdk` 3.18.6 各漏声明了一个运行时依赖，单测一跑就暴露；参考 `apps/dockyard` 的做法用 `packageExtensions` 补齐。

## 6. “是我密码输错了吗？”——一次差点走偏的排查

为了给 README 截图，AI 写了一个浏览器自动化脚本（Playwright），由我输入平台账号后运行。第一次运行报错，我的第一反应是密码输错了。AI 先看报错原文——“浏览器可执行文件不存在”，根本还没走到登录——然后发现一个矛盾：它自己检查时文件明明在。它没有让我“再试一次”，而是怀疑**它的命令行和我的终端看到的不是同一份磁盘**，并用 Docker 把那个目录挂进容器、从沙箱之外看了一眼真实磁盘：目录确实不存在。原因是 AI 的命令行运行在沙箱里，它在用户目录（AppData）下新建的文件只有它自己看得见。改为把浏览器装进项目目录后解决。

第二次运行登录成功，卡在“切换到组织”。失败现场截图显示侧边栏是收起的——“展开”按钮要鼠标悬停才出现，真实点击等不到它；而 AI 此前在自己的浏览器里验证时用的是程序化点击，所以没暴露。修正后第三次一次跑完，9 张截图全部来自这一次连续运行。

收获：报错要读原文，不要先怀疑自己最近做过的那件事（输密码）；“我这里是好的”和“你那里是坏的”同时成立时，先怀疑两边的环境不一样。

## 7. 怎么确认作品符合预期

按题目的四层逐层做，且不互相替代：单元测试与构建（Windows Node 24 与容器 Node 20 各跑一遍）→ 官方 harness 生命周期加载 → 用平台自带的 `plugin:deploy:local` 安装并重启 → 在平台里用真实模型走完整流程并截图。每一层的命令、结果和**尚未验证的部分**都记在 [验证记录](03-validation.md) 里。

## 遇到的工具限制

- AI 不能替我注册账号、输入密码或填写 Key，这几步必须我自己做；它把这些步骤收敛成了“向导 + 一个会提示输入的部署脚本”。
- AI 看不到我浏览器里的页面，需要我截图，或由我在它能操作的浏览器面板里先登录。
- AI 的命令行在沙箱里：它在用户目录下新建的文件对我不可见（见第 6 段），需要我运行的东西必须放在项目目录里。
- AI 拿不到截图文件（它的浏览器工具只把画面给它自己看），所以 README 截图改由一个我来运行、提示我输入账号的自动化脚本生成。
- 长时间构建期间 AI 只能轮询日志，不能“等着”；它把等待时间用在了读参考实现和写代码上。
