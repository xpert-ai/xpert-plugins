## 已知限制

1. **工作台看不到助手运行的成败。** 平台目前只向视图转发“工具完成”事件，没有“运行失败”事件，所以模型调用失败只能靠 180 秒超时发现。超时时长是常量，未做成配置。
2. **故障注入是演示开关。** 它只影响开启了它的那一张工单的第一次保存，界面和处理记录里都明确标注；生产环境应通过插件配置整体关闭这个入口。
3. **分诊标准写在代码里**（`src/lib/domain/policy.ts`），改标准需要重新发版。
4. **只接受纯文本**，不支持图片、附件、录音；单条上限 4000 字；超过 60 句的长文会把尾部并成一句，证据粒度变粗。
5. **没有删除 / 作废 / 导出工单**，也没有对接下游系统（发信、CRM、工单系统）；“回复草稿”需要人工复制使用。
6. **隔离粒度是租户 + 组织。** 同一组织内所有能访问该助手的人共享工单，没有专员 / 主管 / 质检的角色区分；多组织隔离只有单测，未在平台实测。
7. **界面没有使用 shadcn / Tailwind。** 配套 Skill 推荐这套基线；本作品为控制范围，直接使用 SDK 外壳自带的 `xui-*` 控件和宿主主题变量，只写了布局样式。这是有意的范围取舍：换来的是零额外 UI 依赖和约 185 KB 的单文件包，代价是控件风格不如平台自身界面统一。
8. **只在一个模型上验证过**，没有批量样本的准确率评估；提示词对其他模型的稳定性未知。

## 后续最值得做的三件事

1. **让失败可见而不是可等。** 如果平台提供运行结束 / 失败事件，订阅它并立刻给出原因，去掉对超时的依赖；在此之前，把超时做成可配置。
2. **分诊标准配置化。** 把类别和 P1–P4 规则移到插件配置或知识库，让业务方自己维护，并记录每次分析用的是哪一版标准。
3. **小规模评测集。** 准备几十条有人工标注的客诉，回归比对分类与定级，用来换模型、改提示词时兜底。
