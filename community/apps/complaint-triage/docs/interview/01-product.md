# 产品说明与范围

## 用户、原有工作方式与痛点

**目标用户**：中小消费品品牌（以小家电电商为例）的售后客服主管或值班客诉专员，每天要处理几十条来自电商平台留言、客服邮箱、400 电话记录的客户投诉。

**原有工作方式**：逐条通读原文 → 在表格里手工登记产品、订单号、问题类型 → 凭经验判断严重程度和流向（退换货 / 维修 / 质量部 / 法务）→ 手写回复。

**痛点**：

| 痛点 | 后果 |
| --- | --- |
| 每条 5–10 分钟，大部分花在“读懂 + 抄录”上 | 高峰期积压，主管没时间做真正需要人判断的事 |
| 定级标准因人而异 | 同一类问题有人判“一般”、有人判“紧急”，响应时限无法兑现 |
| 涉及安全或扬言投诉监管部门的客诉混在队列里 | 最该 2 小时内响应的那条，可能第二天才被看到 |
| 事后说不清“当时凭原文哪句话这么判” | 复盘和申诉时没有依据 |

## 这个应用改变了什么

主管把客诉原文粘贴进工作台，点一次“AI 分析”；助手读原文，按**公司的分诊标准**给出分类、严重度、客户诉求、关键事实、处理建议和回复草稿，**每条结论都挂着原文里的证据句**；主管核对、按需修改，点“确认并保存”后才成为正式工单。

分工很明确：**AI 负责读、抽取、对标准、起草；人负责判断和拍板。** AI 的结果在确认前只是“建议”，确认后也保留原始建议，能看出人改了什么（例如“AI 建议 P2 → 人工确认 P1”）。

## AI 在业务里的具体作用

1. **要素抽取**：产品、订单号、时间、金额、故障现象、客户诉求。
2. **按标准分类定级**：分类枚举和 P1–P4 的判定规则、响应时限由插件提供给模型（见 `src/lib/domain/policy.ts`），模型不按自己的“感觉”判，定级理由必须写明适用了哪条规则。
3. **处理建议与回复草稿**：按统一口径起草，主管改完即可用。
4. **可核对的证据**：模型只能引用**句子编号**（s1、s2…），引用的原文由服务端从自己保存的客诉里还原——模型无法编造或改写“原话”；引用了不存在的编号会被丢弃，并把该条事实标成“无原文证据，请人工核实”。

## 核心流程（唯一的一条）

```text
新建工单（粘贴原文）
   │  必填校验：10–4000 字
   ▼
待分析 ──点“AI 分析”──▶ 分析中 ──助手保存建议──▶ 待确认 ──人工核对/修改后确认──▶ 已确认
                          │                         ▲
                          │ 失败（保存失败 / 超时 /   │ 重试（同一工单，第 N+1 次尝试）
                          ▼  发送失败 / 助手判定无法分诊）│
                       分析失败 ──────────────────────┘
```

- “AI 分析”先在服务端把工单置为“分析中”并登记一次尝试，再向右侧助手对话发送 `请分析客诉工单 TCK-…`；助手依次调用 `complaint_get_ticket` → `complaint_save_analysis`。直接在对话里说“分析 TCK-…”也走同一条路径、同一次尝试。
- 刷新页面或重新进入应用，工单、AI 建议、确认结果和每次尝试的记录都在（存于平台数据库，按租户 + 组织隔离）。

## 失败与重试

| 失败 | 界面呈现 | 重试 |
| --- | --- | --- |
| 保存分析结果时下游不可用（故障注入模拟） | “第 1 次分析失败：保存分析结果时下游服务不可用（故障注入）” | 点“重试”开始第 2 次尝试 |
| 模型调用失败 / 对话中断（工作台看不到助手的运行错误） | 180 秒无结果判定为超时，并说明可能原因 | 同上；迟到的结果若仍属于最新一次尝试会被接受 |
| 请求没能发给助手（对话未就绪） | “分析请求没能发送给助手” | 同上 |
| 助手判定文本无法分诊（不是投诉、信息不足） | 显示助手给出的原因 | 改原文后新建，或重试 |

重试**不会**产生第二张工单或第二份分析结果：开始分析用条件更新保证双击 / 并发只登记一次尝试；同一次尝试的重复保存是空操作；已确认的工单拒绝任何再分析和 AI 写入。失败的尝试保留在“处理记录”里。

## 功能取舍

| 做了 | 没做（以及为什么） |
| --- | --- |
| 一条流程做扎实：创建 → AI 分析 → 人工确认 → 保存恢复 → 失败重试 | 多渠道自动接入、批量导入：接入是集成问题，不改变核心判断流程 |
| 纯文本输入 | 图片 / 附件 / 录音：会引入文件解析和多模态的不确定性 |
| 租户 + 组织隔离，记录创建人、确认人 | 角色细分（专员 / 主管 / 质检）与审批流 |
| 内置一份分诊标准 | 标准的在线配置、接知识库：先证明“按给定标准判”这件事成立 |
| 单个助手 + 三个窄工具 | 多智能体、下游系统流转（CRM / 工单系统 / 发信）、统计报表 |

## 完成标准

1. 在 Xpert 里用真实模型走完一条工单：创建 → AI 分析 → 查看带证据的建议 → 修改 → 确认；界面状态、数据库记录、助手回复一致。
2. 刷新或重新进入后，工单与结果仍在。
3. 开启故障注入的工单：第 1 次失败并显示原因，重试后成功，全程只有一张工单、一份分析，处理记录里有两次尝试。
4. 空列表、缺必填项、超长输入都有清楚的提示。
