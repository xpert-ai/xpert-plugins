# 验证记录

验证日期 2026-09-17。平台 `xpert-ai/xpert` main `2b57565`（未修改），插件分支基于 `xpert-ai/xpert-plugins` main `9d10893`，运行时模型 DeepSeek `deepseek-v4-flash`。四层分别验证，不同层的结果不互相替代。

## 1. 单元测试与构建检查

```sh
corepack pnpm@8.15.8 --dir community/apps/complaint-triage test
```

结果：类型检查（服务端 + 远程界面）通过；构建通过；**25 个单元测试全部通过**；`verify:dist` 通过。在 Windows / Node 24.11 和 Linux 容器 / Node 20.20（宿主同款）各跑一遍，结果一致。

测试断言的是业务结果，不是“函数被调用过”。数据库用 sql.js 内存库真实执行 TypeORM 读写，没有 mock 仓储：

| 关注点 | 用例断言 |
| --- | --- |
| 完整流程与**保存恢复** | 创建 → 分析 → 保存建议 → 人工确认；换一个新的 service 实例（相当于刷新 / 重启）读回同一结果；AI 建议 P1、人工改为 P2，两者都保留 |
| **输入校验** | 过短、超长的原文被拒绝，且库里没有留下记录 |
| **失败重试不重复** | 故障注入下第 1 次保存失败、工单变为分析失败且无分析结果；不开始新尝试就无法写入；重试后成功；库里 1 张工单、2 条尝试记录 |
| **幂等** | 连续两次“开始分析”只登记一次尝试；两个请求拿同一份过期快照竞争，只有一个成功；同一次尝试重复保存不覆盖第一次的结果 |
| **超时** | 179 秒仍为分析中，181 秒读时过期为 `timeout`；迟到的结果仍被接受；已过期的可以重试，旧尝试留在记录里 |
| **确认即终态** | 已确认工单拒绝再分析、拒绝 AI 写入、拒绝二次确认 |
| **只确认看到的那一版** | 重新分析后，用旧的尝试序号确认会得到 `stale_view` |
| 对话优先路径 | 在对话里直接说“分析 TCK-…”会开始尝试；已有待确认建议时助手无权替换 |
| 证据 | 不存在的句子编号被丢弃，该事实标记为未核实；大小写不敏感 |
| **权限与数据范围** | 换租户或换组织后，列表、详情、开始分析、助手读取、助手保存全部 `not_found`，且原工单未被改动 |
| 工具契约 | 模型最自然的入参一次通过；入参里夹带的 `tenantId`、`attemptNo` 被忽略；工具返回紧凑 JSON，不含原始记录和范围 id；非法入参得到可读的校验错误 |
| 清单与产物 | 运行时 / package.json / 表名三处的 level 与命名空间一致；视图由特性开关控制；动作、客户端命令（仅 `assistant.chat.send_message`）、事件订阅与实现一致；iframe 夹带 `tenantId` 的请求被拒绝；远程包不含 Web Storage |
| 界面辅助 | 中英文词条键与占位符完全一致；服务端可能返回的每个代码都有本地化文案；繁体中文不会落入简体；宿主事件的几种信封形状都能识别 |

## 3. 界面与宿主集成

没有单独搭模拟宿主，而是直接在已安装的平台里用浏览器自动化（Playwright，Chromium 140，1440×900）驱动真实构建出的 `dist/remote/app.js`：登录 → 切到组织 → 打开助手与工作台 → 依次完成输入校验、创建、分析、失败、重试、查看证据、人工确认、刷新。每一步都等待界面出现预期状态后才继续，任何一步不符即失败；README 里的 9 张截图就是这次连续运行的产物。与宿主的契约另有单测覆盖：清单声明、动作键、客户端命令白名单、事件订阅、远程入口 HTML 的产出与拒绝路径。

自动化脚本是本机工具，需要测试账号登录，没有放进本 PR。

验收场景（全部在平台入口完成，界面结果与数据库逐项核对一致）：

| 场景 | 操作 | 实际结果 |
| --- | --- | --- |
| 空状态 | 首次进入工作台 | “还没有客诉工单 … 新建第一条工单”，各状态计数为 0 |
| 输入校验 | 空表单点“创建工单” | 提示“客诉原文至少需要 10 个字。”，对话框不关闭，焦点回到输入框 |
| **完整流程** | 新建空气炸锅冒烟的客诉 → AI 分析 | 约 16 秒后变为“待确认 · P1 紧急”。助手依次调用 `complaint_get_ticket`、`complaint_save_analysis`；分类“安全问题”；定级依据写明同时命中“安全隐患”和“扬言向 12315 投诉”两条 P1 规则、按从重原则定级；7 条关键事实全部带原文证据且通过服务端核对；回复草稿未做越权承诺 |
| 人工确认 | 填写复核备注 → 确认并保存 | “已确认 · P1”，“分析”按钮消失，处理记录：创建 → 第 1 次分析·成功 → 人工确认 |
| **保存与恢复** | 整页刷新 | 工单、状态、结果都在；库中 `status=confirmed`，`analysisJson`、`resolutionJson` 均非空，`organizationId` 已写入 |
| **失败与重试** | 新建破壁机延迟发货的客诉并开启故障注入 → AI 分析 | 第 1 次：“第 1 次分析失败：保存分析结果时下游服务不可用（故障注入）”，没有保存任何分析；助手在对话中说明“本次分析没有写入工单，请在工作台重试”，且没有在同一轮里自行重试。点“重试”后第 2 次成功：“物流配送 · P3”，定级依据同时说明了为什么**不**满足 P2 |
| 重试不重复 | 查库 | 该工单 `attemptCount=2`，尝试 1 `failed / simulated_downstream_failure`，尝试 2 `succeeded`，只有一份分析；没有多出工单 |
| 低等级不被拔高 | 新建“电饭煲刻度线太浅、顺便问内胆能否单买”的反馈 → AI 分析 | “其他 · P4 低”，定级依据引用规则“咨询、建议，或轻微不满”，并说明无安全隐患、无法使用、重复投诉或退款争议，故不升级 |
| 自动化走查（截图那一次） | 电热水壶跳闸发烫、此前因漏水找过客服 → 故障注入 → 重试 → 确认 → 刷新 | 第 1 次失败、第 2 次成功，“安全问题 · P1”；定级依据同时指出命中 P1“安全隐患”和 P2“同一问题重复投诉”，按从重原则取 P1；点“证据 s1”后原文对应句子高亮；确认后处理记录为 创建 → 失败 → 成功 → 人工确认；刷新后仍是“已确认” |

全部操作结束后库内共 **4 张工单、6 条尝试记录**，与界面一致：

| 工单 | 状态 | 严重度 | 尝试 |
| --- | --- | --- | --- |
| TCK-20260917-PXMK | confirmed | P1 | 1: succeeded |
| TCK-20260917-8D6C | pending_review | P3 | 1: failed (simulated_downstream_failure)，2: succeeded |
| TCK-20260917-ZEAK | pending_review | P4 | 1: succeeded |
| TCK-20260917-ATYV | confirmed | P1 | 1: failed (simulated_downstream_failure)，2: succeeded |

四条客诉覆盖了 P1 / P3 / P4 三个等级和安全、物流、其他三类；模型每次都在第一次调用时通过了工具入参校验。

验证过程中发现并修复的问题：

1. 模型在中文分析里用英文引用分诊规则，助手调用工具前的过渡语也是英文——原因是插件交给模型的规则文本和提示词没有约束语言。已把规则改为中文、在提示词里要求全程使用用户语言（提交 `e08c403`），重新部署后通过“从模版更新 → 发布”更新了**同一个**助手（未新建副本），复测通过。
2. 登录后的会话默认处于“租户”范围，需要先切换到组织才能初始化应用和创建助手；已写入 [运行说明](02-runbook.md)。

## 尚未验证

- **多组织 / 多用户隔离**没有在平台里实测：测试实例只有一个组织、一个用户。隔离逻辑由单元测试覆盖（换租户、换组织的全部读写路径）。
- **真实的模型故障**（Key 失效、额度耗尽、网络中断）没有在平台里制造；平台内实测的失败是故障注入。这类故障对工作台表现为“无结果 → 180 秒超时 → 可重试”，该路径由单元测试覆盖，未在平台里等满 180 秒。
- 只测了 `deepseek-v4-flash` 一个模型；没有测其他模型的工具调用稳定性，也没有做批量样本的定级准确率评估。
- 没有在移动端宽度、暗色主题下做平台内目视检查（样式全部使用宿主主题变量，窄屏有单独布局，但未实测）。
- 没有做并发压力测试；并发安全性来自条件更新，以“同一过期快照重放”的单测验证。
