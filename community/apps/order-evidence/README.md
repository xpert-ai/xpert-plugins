# 订单全流程证据

在一个制造业订单 Project 内组织合同、工程、采购、计划、质量、售后六个专业 Assistant，并通过原生 Project Pipeline 保留人工决定、执行履历与证据版本。另有协调 Assistant 负责启动与说明进展。

## 当前实现

- App 与制造业订单 Project Type，八个带企业人物头像的 Assistant 模板；平台负责调度、等待、技术重试和历史。
- 六阶段依次提交判断，每阶段由配置的真实用户确认后才进入下一阶段。使用权、维护权、业务批准权分别约束。
- 服务端绑定执行身份、项目、输入摘要与版本；人工决定必须匹配准确建议摘要。证据和最终结果不可覆盖。
- 四个 Router：要求资料完整性、供应条件、质量证据、售后改进。前三个从冻结的类型化业务事实判断，条件满足后进入人工批准；不满足则留在本阶段等待补证。售后根据已被人确认的改进建议进入“待下一单验证”或“持续观察”。Router 不调用模型，也不代替人批准。
- 版本 0.2.0 使用不可变模板 1.1.0，保留旧流水线历史。原生总览把人工审核横向放在对应 Assistant 后；角色归属和授权不变。

## 演示边界

`src/fixture.ts` 是明确标注的合成业务资料。业务链覆盖订单、BOM、物料、工单、实物序列号、试验与售后证据。原生流水线、模型调用和人工确认记录实际运行；各业务阶段的物理事件是预置快照。

本插件当前不调用 SAP 或 Data Xpert 接口，不产生采购、BOM、排程或放行的生产交易。Data Xpert 本体接入属于对应 PPT 的场景方案，已有上一场景的独立实测，不应把两个范围混为一谈。0.3.0 支持判断方法的评测、人工发布与下一单采用；真实工厂故障率或经营收益仍须独立验收。

## 构建与安装

新版绑定需要支持省略 `binding.limits.runTimeoutMinutes` 的 Xpert 契约。先升级平台与开发环境的 `@xpert-ai/contracts`，再安装插件并生成新绑定。旧绑定中的 240 分钟时限继续生效。

在 community 工作区使用其声明的 Corepack/pnpm 版本：

```sh
corepack pnpm install --frozen-lockfile
corepack pnpm --filter @xpert-ai/plugin-order-evidence test
corepack pnpm --filter @xpert-ai/plugin-order-evidence build
corepack pnpm --filter @xpert-ai/plugin-order-evidence verify:dist
```

在已验证的 Xpert 主机运行 `plugin:deploy:local --plugin-dir <本包目录> --scope tenant`，按部署回执重启 API。在目标组织打开应用详情并初始化，平台发布套件并按角色键绑定 Assistant。在表单中为合同、工程、采购、计划、质量、售后选择本组织审批人，可另选判断方法发布人。审批时仍校验项目管理权限。已有实例在应用详情选择“补全组织配置”；已启动订单保留原审批人和证据。

创建“制造业订单项目”，添加协调者及六个专业角色，向协调者发送“请启动这张 12 台电机订单的全流程证据演示”。在原生项目任务 Pipeline 查看当前证据、人工确认或退回。演示回执以 `DEMO-DECISION-` 开头。

## 验证

区分包构建、dist 生命周期、插件运行、Assistant 发布和业务端到端完成。实际本地安装记录与截图位于任务交付的演示目录，不包含在可移植包内。

## 路由演示

正常资料使用 `scenario=standard`。缺少技术澄清的反例使用 `scenario=requirements_missing`，须在新 Project 启动，合同 Assistant 运行后停在“等待技术要求补证”。不要把已有 Project 的旧实例覆盖成新模板。

供应条件为现货足量，或现货加已确认在途达到数量；后者仅支持人工确认条件性供应方案，不能视为已入库。质量条件要求试验、合格和可追溯数量均覆盖订单且交付资料齐全。业务资料均为合成快照，Router 测试覆盖缺资料、缺件、未确认在途及质量缺证。

## 应用展示与封面

0.3.0 的 Assistant 模板版本为 3，使用 `assets/avatars/` 中统一风格的虚构企业人物头像。协调、合同、工程、采购、计划、质量、售后、能力维护八个角色分别配置独立头像。人物形象只代表 Assistant，不代表业务批准人或真实员工。头像以压缩 JPEG 随包分发，由宿主管理安装后的图片地址。

已安装实例通过 Assistant Settings 的 Update from Template 更新、检查并发布，保留原 ID、对话和项目成员绑定；不要重新创建同名 Assistant。0.3.0 新增显式采用模板 1.2.0；已有 1.1.0 实例保留历史，不自动升级。

`src/app-config.ts` 是 App 展示与初始化声明的唯一维护入口，包含中英文介绍、功能亮点、使用场景、数据范围和初始化说明。封面位于 `assets/brand/`；卡片标题由宿主展示，图中只保留八字描述。

构建时 `scripts/manifest.mjs` 从实际运行元数据生成 `.xpertai-plugin/plugin.json`，同步声明封面资源。`verify:dist` 检查模板关联、manifest 一致性、PNG 格式、5 MiB 限制和打包目录。部署新版插件并按回执重启后，Explore 卡片、详情页和初始化面板使用同一张封面。

新项目从协调者的已发布协作关系加载角色成员。已有项目沿用当前成员配置。

## 售后方法演进与下一单采用（0.3.0）

能力维护 Assistant 仅可读取所在项目中已获质量 / 工程确认的售后建议与证据版本，提交候选给原生 Agent Evolution。它没有批准、发布或工程变更权限。插件使用公开 Runtime Capability 与 Evolution Target Provider，不引入独立调度器。

1. 能力维护 Assistant 由组织应用实例绑定；在组织配置中指定有源项目管理权限的判断方法发布人。
2. 将能力维护 Assistant 添加到已有完整订单项目，请其读取已确认的售后证据并提交候选。`requiredEvidence` 表示判断必须检查的类别，并非当前已有资料清单；当前缺少的工况也应作为未来补证要求。
3. 在“智能体进化 → 候选与评测”查看目标 `order_evidence.aftercare_method`。平台按冻结的 8 个独立合成样例执行同一确定性规则函数，比较基线与候选。本地实跑中，漏掉工况要求的候选为 7/8，发布被阻止；完整四类证据且保留人工确认的候选为 8/8。这里衡量规则是否符合样例，不是模型整体准确率。
4. 授权能力负责人核对候选指纹、评测记录与范围，在原生签审页面批准并写入方法版本。R2 签审遵循宿主策略。发布结果保留不可变回执，不自动修改已有订单。
5. 创建独立的“制造业订单项目”，添加协调者及六个专业 Assistant，请协调者使用 `scenario=next_order_adoption` 启动。新订单校验发布回执并固定方法版本，保留前五阶段的人工确认。售后 Assistant 收到固定规则、版本和缺证信息，提交判断后记录采用回执。新增 Router 将缺证情况转入“等待工况 / 拆检 / 实验补证”，不会越过根因人工确认。

规则适用于本组织的 M200。来源、候选、基线、数据集、人工批准与发布回执分别绑定摘要；采用记录绑定独立项目、订单、发布版本及实际 Assistant 执行。一个执行的候选与一个项目的采用均不可覆盖。平台变更编号是带 `EVO-` 前缀的不透明字符串，插件不假设它是 UUID。

本地示例用测试管理员代演业务与能力负责人，生产需配置真实职责矩阵。方法发布不修改 BOM、预算、SAP 数据或 Data Xpert 本体。实际业务效果仍需在真实订单观察窗口中验收。
