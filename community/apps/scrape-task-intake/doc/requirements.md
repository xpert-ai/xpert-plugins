# Scrape Task Intake — 产品定义

## 目标用户

- **业务需求方**(运营、分析、市场人员):需要数据,但不熟悉采集工程细节。他们用一句话描述「我要什么数据、多频繁、什么格式」。
- **数据工程师**(采集执行方):接收需求、评估可行性、受理并执行采集。

## 原有工作方式与痛点

1. 采集需求散落在聊天、邮件、口头沟通中,缺少结构化记录,难以追踪状态与回溯。
2. 业务方的自然语言描述经常缺少关键字段(目标站点、字段清单、频率、交付格式),工程师需要多轮追问,来回成本高。
3. 反爬风险与合规边界(robots.txt / ToS / 频率控制)依赖工程师个人经验,需求受理阶段没有提示。
4. 需求确认后没有统一的任务单,「谁在跟进、到哪一步」不可见。

## 业务流程

```
业务方(自然语言描述需求)
   → Assistant 提取/补全结构化任务书(目标站点、字段、频率、格式、风险提示)
   → 保存为「待确认 / 待补充」任务
   → 数据工程师在审核台:编辑、补充、确认受理 / 驳回关闭
   → 确认后开始采集 → 标记完成(附完成说明)
   → 全程状态可查询、可恢复
```

## 关键页面原型

- **提交需求页**:自然语言文本框 + 可选需求人信息 + 「发送给 Assistant 生成任务书」按钮;附站点类型字段模板与合规清单。
- **任务审核台**:左侧任务列表(状态/优先级筛选、关键字搜索),右侧任务详情:原始需求、AI 提取的任务书(可编辑)、反爬风险与合规提示、完整性提示、AI 补充草稿(一键填入)、人工确认信息、操作记录时间线。
- 工具栏按状态提供动作:保存修改 / 补充完善 / 驳回关闭 / 确认受理 → 开始采集 → 标记完成。

## AI 在业务中的作用

- **结构化提取**:从自然语言中提取目标站点、采集字段(名称/说明/示例)、页面范围、频率、交付格式,并给出置信度。
- **字段模板对齐**:通过 `scrape_intake_get_catalog` 获取站点类型字段模板,把口语化需求映射为规范字段清单。
- **缺失识别**:无法确定的必要信息写入 `completenessTips`,任务进入「待补充」,由人补充而非 AI 编造。
- **风险与合规提示**:生成反爬风险提示(antiBotNotes)与合规提示(complianceNotes),只提示、不承诺绕过。
- **补充草稿**:用户补充内容后,AI 生成补充草稿,审核台一键填入、人工保存。

## 功能取舍(第一版)

- 保留:单任务创建与去重、状态机(待确认/待补充/已受理/采集中/已完成/已驳回)、列表搜索筛选、编辑与补充、AI 补充草稿、操作日志、租户/组织数据隔离。
- 明确不做:CMMS 式真实采集执行调度、文件上传解析、多智能体协作、权限体系 UI、真实主数据表(候选模板用内置 mock catalog)。

## 完成标准

1. 用户可用自然语言提交需求,Assistant 调用工具保存结构化任务。
2. 工程师可审核、编辑、补充、确认、开始、完成或驳回任务。
3. 刷新后任务与结果仍可恢复(数据库持久化)。
4. 失败可重试且不重复建单(会话内相同内容去重)。
5. 单元测试、生命周期测试、平台内真实流程验收通过。
