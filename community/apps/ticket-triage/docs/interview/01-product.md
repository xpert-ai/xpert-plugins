# 产品说明与范围

整理日期：2026-11-03；当前实现：`@community/apps-ticket-triage` 0.1.0。本文只写已实现并验证过的功能，未验收的部分明确标注。

## 用户、问题与价值

目标用户是客服团队的当班组长。他每天要面对一堆进线工单，判断优先级、派给哪个组、怎么回第一句。现在这些判断靠人肉扫一遍，慢且标准不一致；直接让模型"自动处理"又不放心，因为发错派单或回错话的代价由人承担。

本应用把这段工作拆成两半：模型负责读工单、给建议（优先级 / 归属组 / 判断理由 / 回复草稿），人负责最后拍板。工单板是产品界面，建议和最终决定都落在插件自己的表里，刷新后还在。

## 当前核心流程

1. 从助手模板创建助手，进入助手工作台，打开「工单分诊板」视图。
2. 点「载入演示工单」写入 4 张待处理工单（T-1001 ~ T-1004）。
3. 对助手说"给最早的一张待处理工单做分诊"。助手调用 `list_pending_tickets` 读取待处理队列。
4. 助手调用 `propose_ticket_triage` 写入建议：优先级、归属组、理由、回复草稿。工单状态变为 `proposed`，工单不会被关闭。
5. 人在板上看建议，点「确认分诊」（可改写优先级/归属组并加复核备注）或「退回重做」。确认后状态 `confirmed`，退回则清空建议回到 `pending`。
6. 刷新页面或重新进入视图，已确认的结果仍在（存在插件表 `plugin_artifact_ticket_triage_ticket`）。

第 3–6 步在插件域层有自动化测试覆盖；平台侧的完整路线（真实模型调用 → 人在视图里确认 → 刷新恢复）的验收记录见 `03-validation.md`。

## AI 的作用与边界

| 环节 | 由谁完成 | 说明 |
| --- | --- | --- |
| 读工单、给优先级与归属组建议 | 模型 | 通过中间件暴露的两个工具，工具描述里写明可用的枚举值 |
| 写回复草稿 | 模型 | 只是草稿，应用不发送任何消息 |
| 最终确认 / 改写 / 退回 | 人 | 只有视图的 `confirm_triage` 动作能把工单置为 `confirmed` |
| 结果持久化 | 插件 | 按 租户/组织/工作区/用户/助手 五元组隔离，唯一约束防重复 |

模型不能关闭工单、不能跳过确认、不能批量处理：模板 prompt 明确要求"一次只处理一张，且不得声称已解决"。

## 功能取舍

| 范围 | 当前状态 |
| --- | --- |
| 助手模板 + 中间件（两个工具）+ 工作台远程组件视图 | 已实现，类型检查、域测试、插件加载、构建均通过 |
| 分诊建议的状态机（pending / proposed / confirmed / failed） | 已实现，含冲突、非法状态、跨租户隔离测试 |
| 乐观锁与唯一约束（同一范围同一工单号只有一行） | 已实现并有测试 |
| 失败重试（`failed` 回到 `pending`，不新建记录） | 已实现并有测试 |
| 真实工单系统接入（Zendesk / 飞书等） | 未实施，演示数据是常量 |
| 批量分诊、SLA 计时、通知 | 未实施（超出本题范围） |
| 管理员配置优先级/组枚举 | 未实施，枚举固定在领域契约里 |

## 与题面"合格范围"的对应

| 题面要求 | 本应用的落点 |
| --- | --- |
| 一个明确用户 | 客服当班组长 |
| 一条核心流程 | 载入队列 → 模型建议 → 人工确认 → 持久化 |
| 一个可操作界面 | 助手工作台里的工单分诊板（远程组件） |
| 一次真实 AI 处理 | 助手调用两个工具完成一次分诊并写入建议 |
| 结果保存与恢复 | 插件表持久化，刷新后仍在 |
| 一个失败重试场景 | 建议失败/冲突后，工单回到可重试状态且不产生重复业务结果 |
