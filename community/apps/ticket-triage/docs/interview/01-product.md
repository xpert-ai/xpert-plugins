# 01 · 产品说明（面试官阅读版）

> **30 秒版**：客服组长每天要人工扫一遍工单、定优先级、判断派给谁、写第一句回复。本应用把"读 + 判断 + 起草"交给助手，把"签字"留给人——助手只能提交**分诊建议**，工单变成"待确认"；人确认、改派或退回之后才算完成。模型在任何路径下都不能自己关闭工单。
>
> **看这一份能判断**：选题是否成立（有明确用户、完整流程、真实 AI 参与）、产品判断是否成熟（人机边界在哪、放弃了什么）。
> **证据**：原型线框在本文；实机截图 [05](screenshots/05-chat-tool-calls.png)/[06](screenshots/06-board-awaiting-human.png)/[07](screenshots/07-board-confirmed.png)；四层实测见 [03-validation.md](03-validation.md)。

---

## 1. 用户与问题

**用户**：客服团队的当班组长，手里压着一批进线工单。

**他每天要做的事**：读每张工单 → 判断优先级 → 判断归哪个组 → 写第一句回复 → 才能往下走。

**现状痛点**：这三步靠人肉扫，慢，而且不同班次标准不一致。反过来，直接让模型"自动处理"也没人敢签字——派错组、回错话的代价由人承担。

**本应用的解法**：把这段工作切成两半。模型负责**建议**（优先级 / 承接组 / 判断依据 / 回复草稿），人负责**拍板**。建议与最终决定都写进插件自己的表，刷新后还在。

## 2. 核心流程（一条，不做第二条）

```
载入队列 ──▶ 助手读工单 ──▶ 助手写建议 ──▶ 人看板拍板 ──▶ 持久化
（4 张演示单）  list_pending_tickets  propose_ticket_triage  confirm / reject   刷新仍在
                                      status: proposed        status: confirmed
```

用户视角的六步：

1. 从助手模板创建助手，进工作台打开「工单分诊板」。
2. 点「载入演示工单」，写入 4 张待处理工单（T-1001 ~ T-1004）。
3. 对助手说"给最早的一张待处理工单做分诊"。助手调用 `list_pending_tickets` 读队列。
4. 助手调用 `propose_ticket_triage` 写入建议：优先级、承接组、理由、回复草稿 → 工单变 `proposed`，**不会关闭**。
5. 人在板上看建议，点「确认分诊」（可顺手改优先级/组、加复核备注）或「退回重做」。
6. 刷新或重进视图，结果仍在（插件表 `plugin_ticket_triage_ticket`）。

## 3. 关键页面原型

只有两个面：**助手侧（说话）** 与 **工单板侧（拍板）**。1440 宽设计。

**A. 助手工作台（对话面）**

```
+--------------------------------------------------------------+
|  Support ticket triage        [预览] [发布]                   |
+--------------------------------------------------------------+
| 工单分诊板                                                     |
|  +--------+--------+--------+--------+                        |
|  | 全部 4 | 待处理 2| 待确认 1| 已确认 1|                        |
|  +--------+--------+--------+--------+                        |
|  工单     主题                 状态      团队                 |
|  T-1002   发票抬头写错，需要重开  待确认 P2  账务   <- 选中     |
|  T-1001   支付成功但 VIP 未解锁  待处理      —                 |
|                                          +-------------------+ |
|  你  > 先列工单，再只对 T-1002 提建议      | AI 分诊建议        | |
|  助手 > 已读取 4 条…                      | 优先级 P2          | |
|         [list_pending_tickets 0.063s]    | 承接团队 账务       | |
|         [propose_ticket_triage 0.077s]   | 判断依据（多行）    | |
|         "已完成，等待人工确认"             | 回复草稿（多行）    | |
|                                          | [确认分诊][退回重做]| |
+--------------------------------------------------------------+
```

**B. 工单板（决策面，工作台视图）**

```
+-------------------------------------------------------------------+
| 工单分诊板   App 0.1.0                  [载入演示工单]  [刷新]     |
+-------------------------------------------------------------------+
| (全部 4)(待处理 2)(待确认 1)(已确认 1)(需重试 0)                    |
| 工单      主题                  状态        团队                    |
| T-1002   发票抬头写错，需要重开   待确认 P2   账务                  |
| T-1004   升级后导出 Excel 报错   已确认 P1   产品                  |
| T-1003   物流显示已签收但没收到   需重试      —    [重试分诊]       |
+-------------------------------------------------------------------+
                                    [确认分诊] [退回重做]
```

**四条界面约定**（都是产品决定，不是实现细节）：

- **状态色 + 文字双写**：待处理灰、待确认琥珀、已确认绿、需重试红；同一行右侧只出现**一个**主操作按钮，减少误点。
- **冲突不覆盖**：`revision` 变了就返回 `conflict`，界面提示"这张工单状态已变化，已刷新"并重拉，而不是盖掉同事刚做的决定。
- **空状态有出口**：没有工单时显示"还没有工单。点『载入演示工单』开始。"（截图 [10](screenshots/10-board-empty-state.png)）。
- **失败态只留一个动作**：显示失败原因（如 `model_timeout`）与尝试次数，只给「重试分诊」（截图 [11](screenshots/11-board-needs-retry.png)/[12](screenshots/12-board-retry-recovered.png)）。

## 4. 状态机与人机边界

```
pending ──propose──▶ proposed ──confirm──▶ confirmed
   ▲                    │
   └────── reject ──────┤        （清空建议，保留退回理由）
   ▲                    │
   └── retry ──── failed◀┘        （失败可重试，不新建记录）
```

| 环节 | 谁做 | 约束 |
| --- | --- | --- |
| 读工单、定优先级、判断承接组 | 模型 | 通过中间件暴露的两个工具；工具描述里写明枚举值 |
| 写回复草稿 | 模型 | 仅草稿，应用**不发送**任何消息 |
| 最终确认 / 改派 / 退回 | 人 | 只有视图动作 `confirm_triage` 能把工单置为 `confirmed` |
| 持久化与隔离 | 插件 | 按 `tenantId + organizationId + xpertId` 归属；唯一约束防重复建单 |

**模型不能做的事**：关闭工单、跳过确认、批量处理。模板 prompt 明确写了"一次只处理一张，且不得声称已解决"。

## 5. 取舍（我放弃了什么）

| 取舍 | 决定 | 理由 |
| --- | --- | --- |
| 流程数量 | 只做一条：建议 → 确认 | 题目要看"能不能在平台上真跑通一次使用"，摊开三件事不如一件做到底 |
| AI 决策权 | AI 只写状态，不做最终决策 | 分诊错直接影响客户，必须留人在回路 |
| 看板归属 | 租户 + 组织 + 助手，不按人 | 共享团队看板本来就不该按人切；按人隔离会导致智能体侧看不到视图侧写入的数据 |
| 批量分诊 | 不做 | 一批一起提交，人只能整批点"同意"，复核就变成走过场 |
| 真实工单系统接入 | 不做（演示数据是常量） | 与"证明 AI 在业务流程里的位置"无关，且要引入外部依赖 |
| SLA、通知、枚举配置 | 不做 | 超出这道题的范围 |

## 6. 与题面"合格范围"的对应

| 题面要求 | 本应用的落点 |
| --- | --- |
| 一个明确用户 | 客服当班组长 |
| 一条核心流程 | 载入队列 → 模型建议 → 人工确认 → 持久化 |
| 一个可操作界面 | 助手工作台里的工单分诊板（远程组件视图） |
| 一次真实 AI 处理 | 助手调用两个工具完成一次分诊并写入建议（截图 05） |
| 结果保存与恢复 | 插件表持久化，重启 API 后逐条一致（截图 09） |
| 一个失败重试场景 | 失败可重试、退回可重提，全程不产生重复业务结果（截图 11/12 + 测试用例） |
