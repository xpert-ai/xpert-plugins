# 面试交流备忘

> 这是准备稿，不是交付物。数字与结论都能在 [03-validation.md](03-validation.md) 与 [evidence.json](evidence.json) 里回查。

## 60 秒版

客服每天收到的工单，先要有人读一遍、定优先级、判断归哪个组、写第一封回复，然后才能往下走。我做的是把"读 + 判断 + 起草"交给助手，把"签字"留给人：助手只能提交**分诊建议**（优先级、承接组、判断依据、回复草稿），工单状态变成"待确认"；人工确认、改派或退回之后才算完成。助手在任何情况下都不能自己关闭工单。

## 我做的三个取舍（以及为什么）

1. **只做一条流程**：工单 → 建议 → 人工确认。没有做多角色、没有做 SLA、没有做知识库检索。原因是这道题要看的是"能不能在平台上跑通一次真实使用"，摊开做三件事不如把一件事做到底。
2. **AI 只写状态，不做最终决策**：`propose_ticket_triage` 只能把工单写成 `proposed`；`confirm` 只能由看板的视图动作触发。这是产品判断，不是技术限制——分诊错了会直接影响客户，必须留一个人在回路里。
3. **看板按"租户 + 组织 + 助手"归属，不按人**：一开始按人隔离，结果智能体侧看不到视图侧写入的数据（见下面第 1 个追问）。共享团队看板本来就不该按人切，改成三元组之后两侧一致。

## AI 在这道题里的真实分工

- **我**：选题目、定验收口径（什么叫"真的跑通了"）、在真机上跑、判断哪些"看起来通过"其实是假的。
- **AI**：读两个仓库、写插件与测试、写文档、跑构建与部署，我逐轮抽查。

对应文档里那四个问题：

- **怎么介绍想法**：我给的是约束而不是需求——一条流程、要能演示、不碰真实客户数据。
- **做过哪些选择与调整**：最初按五元组（含用户/工作区）隔离 → 发现视图侧与智能体侧算出来的 scope 不同 → 收敛成三元组；最初 `team` 作为工具参数 → 被平台适配层丢掉 → 改名 `owningTeam`。
- **怎么一起定位问题**：`propose_ticket_triage` 一直报 `Received tool input did not match expected schema`。第一反应是 schema 写错，给每个字段补 `.describe()` 之后仍然失败，说明不是提示词问题。于是绕过平台：直接把同一份 JSON Schema 打到智谱的 OpenAI 兼容接口，模型老老实实返回了 `team`——问题定位到"平台的模型适配层把某个参数丢了"。改参数名后一次通过。
- **怎么确认**：域逻辑 11 个用例、harness 插件加载、真实 `view-hosts` 的 slots/data/actions、浏览器里真点一次确认、以及**重启 API 之后数据仍在**。

## 三分钟讲实现

插件向平台贡献四件东西：一个助手模板（含中间件节点）、一个 Agent 中间件（两个工具）、一个视图提供者（`agent.workbench` 两个 slot）、以及一个自带打包的 remote component（iframe，走 `xpertai.remote_component` 协议：`ready` → `init` → `requestData` / `executeAction`）。

三个工具与视图共用同一个 service，所以"助手写的"和"人看到的"是同一份数据。写操作带乐观锁：客户端拿 `expectedRevision`，服务端 `update ... where revision = ?`，`affected !== 1` 就返回 `conflict`，人不会覆盖掉别人刚做的决定。

## 大概率被追问的六个问题

1. **为什么是三元组？** 因为视图侧 `XpertResolvedViewHostContext` 有 `hostId`，智能体侧 `IAgentMiddlewareContext` 有 `xpertId`，而 `workspaceId` 在普通助手对话里不保证存在。实测日志打出来两侧这三个值一致，`workspaceId` 只有一侧有，按它做键必然对不上。
2. **`team` 那个坑到底怎么回事？** 我做了隔离实验（同一份 schema 直连模型 API，模型会返回 `team`），所以是我的代码与平台适配层之间丢的。改名为 `owningTeam` 之后稳定。这也是个风险提示：换模型或升级平台要重新验这条。
3. **外壳为什么不是平台自带的？** 平台自带的 `/chat/...` 走托管式应用外壳，要 app platform 的 definition/environment 两个 YAML。我配了，`/api/app-platform/me` 从 400 变成 `managed-apps`，但 provisioning 失败在 `application_trial_unavailable`——它要求会员计划与试用策略，而 seed 出来的库里 `membership_plan` 是 0 行。这是付费子系统，插件侧补不了，所以撤回配置，改用按协议实现的最小宿主，代码在 `tests/browser/` 里，可复现。
4. **失败是真的吗？** 不是。界面上的"需重试"是 SQL 造出来的 `failed` + `model_timeout`，我展示的是"失败状态可理解 → 重试不重复建单"。真实模型超时注入需要打断网关，没做。
5. **权限做到什么程度？** 只做到"没有权限不能读改他人数据"的域测试与三元组隔离，没做行级权限，也没造第二个租户。
6. **文档写 2–6 小时，你花了多久？** 搭建环境（Windows 源码跑平台 + 修一堆 Windows 才有的坑）就超过这个数了。插件本体不长（约 600 行 TS + 一个自带打包的前端），时间主要花在"让平台在这台机器上真的能起来"。

## 如果继续做

按优先级：真实外壳复验（配会员计划）→ 行级权限与第二租户 → 真实故障注入 → 把 `seed_tickets` 从工具栏收进初始化流程 → 批量分诊（一次提交多条建议，仍逐条人工确认）。

## 一句话自评

做得最好的是"人在回路"这条线：AI 提议、人签字、重试不重复建单，三层都有证据。最弱的是环境侧——真实外壳与多租户没验证，这两条我在文档里都写在明面上，而不是绕过。
