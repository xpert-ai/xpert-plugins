# 07 · 面试备忘（任何面试都能用的版本）

> 这不是交付物，是我自己带进面试的稿子。数字与结论都能在 [03-validation.md](03-validation.md) 与 [evidence.json](evidence.json) 里回查。

## 1. 三档口述（按对方给的时间选）

**60 秒版**

> 客服每天收到的工单，要先有人读一遍、定优先级、判断归哪个组、写第一封回复。我把"读 + 判断 + 起草"交给助手，把"签字"留给人：助手只能提交分诊建议（优先级、承接组、依据、回复草稿），工单变成"待确认"；人确认、改派或退回之后才算完成。**助手在任何情况下都不能自己关闭工单。** 这个应用是一个 Xpert 插件：一个助手模板、一个 Agent 中间件（两个工具）、一个工作台视图，数据在插件自己的表里。四层测试都做了，第四层是真机：真实模型调两个工具 → 我在看板上点确认 → 重启后数据还在。

**2 分钟版（在 60 秒基础上加这三段）**

> **为什么留人在回路**：分诊错了直接影响客户，而且真实团队里"谁派的、凭什么派的"要能追。所以状态机是 `pending → proposed → confirmed`，`proposed` 是 AI 能到达的最远状态；`confirmed` 只能由视图动作 `confirm_triage` 触发，且带 `expectedRevision` 乐观锁——两个人同时看同一张单，后点的会收到 `conflict` 而不是覆盖前一个人。
>
> **插件向平台贡献四件东西**：一个助手模板（DSL 里含中间件节点与连接）、一个 Agent 中间件（`list_pending_tickets` / `propose_ticket_triage` 两个工具）、一个视图提供者（注册 `agent.workbench.main` 与 `agent.workbench.fixed` 两个 slot）、一个自包含 remote component（iframe，走 `xpertai.remote_component` 协议：`ready → init → requestData / executeAction`）。工具与视图共用同一个 service，所以"助手写的"和"人看到的"是同一份数据。
>
> **验证怎么做的**：域逻辑 11 个用例（状态机、冲突、幂等、跨租户）→ harness 插件加载 → 真实 `view-hosts` 的 slots/data/actions → 浏览器里真点一次确认 → 重启 API 后数据一致 → 另建第二个租户打不进来（404 / SSE 记录不存在 / 模板列表无本插件）。

**5 分钟版（再加实现与坑）**

> 有两处值得展开。**第一处是归属键**：视图侧上下文给的是 `hostId`，智能体侧给的是 `xpertId`，而 `workspaceId` 在普通助手对话里不保证存在（只有 project agent 分支才注入）。我原来按五元组存，结果视图里载入的工单，助手看不到。日志打出两侧三个值一致后，收敛成 `tenant + organization + xpertId` 三元组，共享看板本来就不该按人切。
>
> **第二处是工具参数被吞**：`propose_ticket_triage` 稳定报 `Received tool input did not match expected schema`，模型每次漏 `team`。补 `.describe()` 没用之后，我把同一份 JSON Schema 直接打到模型 API——模型返回的 arguments 里 `team` 是有的。所以是我的代码和平台适配层之间丢的，改名为 `owningTeam` 后稳定。这类问题不能靠手写 JSON 示例测，必须真让模型跑一次看它交上来的 arguments。
>
> 另外我把"平台自带工作台外壳"也跑通了：它依赖会员子系统，需要 `FEATURE_MEMBERSHIP_PLAN` + 一条默认 `membership_plan`、`copilot.role='primary'` 且 provisioner 解析模型时要带上请求上下文、以及平台自己的 provisioning actor 要有常规权限。补齐后 `ready:true`，截图 13/14 就是 `/chat/…` 外壳里的 `工单分诊` tab。

## 2. 五个取舍（被问"你为什么这么做"时的标准答案）

| 取舍 | 决定 | 理由（一句话版） |
| --- | --- | --- |
| 流程数量 | 只做一条：建议 → 确认 | 题目要看"能不能真跑通一次使用"，摊开三件事不如一件到底 |
| AI 决策权 | AI 只写状态，不做最终决策 | 分诊错直接影响客户，必须留人在回路 |
| 批量 vs 单张 | 单张提议，逐条确认 | 批量会让人整批点"同意"，复核变成走过场 |
| 归属粒度 | 租户 + 组织 + 助手，不按人 | 共享团队看板不该按人切；按人隔离会让智能体侧看不到视图侧数据 |
| 外壳 | 先替身宿主，后补真实外壳 | 不为"没跑通"找借口，也不为"跑通了"掩盖三堵墙 |

## 3. 十个追问（按被问概率排序）

**产品类**

1. **为什么是人工确认，而不是让 AI 直接处理？** —— 分诊错误直接影响客户体验与赔付；且真实团队要能追"谁派的、凭什么派的"。AI 输出的 `proposed` 是"待签字"，不是"已完成"。
2. **为什么不做批量？** —— 一批建议一起提交，人只能整批同意，复核变走过场。逐条提是产品判断，不是工期妥协。
3. **如果用户就是想一键全收？** —— 那说明这个场景的信任还没建立；我会先做"同意 + 抽样复核"并把依据展示在一张卡上，而不是给一个"全部同意"。

**技术类**

4. **为什么按三元组而不是按用户隔离？** —— 视图侧 `XpertResolvedViewHostContext.hostId` 与智能体侧 `IAgentMiddlewareContext.xpertId` 说的是同一个助手，而 `workspaceId` 在普通助手对话里可能不存在；按五元组存会两侧对不上（实测过）。
5. **`team` 那个坑到底怎么回事？** —— 隔离实验证明是平台适配层丢参数，不是模型或 schema 的问题；改名 `owningTeam` 后稳定，换模型/版本要重验。
6. **乐观锁怎么实现的？** —— 客户端给 `expectedRevision`，服务端 `update … where revision = ?` 并写 `revision+1`，`affected !== 1` 返回 `conflict`；唯一约束兜住"同一范围同一工单号只有一行"。重试不新建记录，只推进同一行。
7. **插件怎么进平台的？** —— `xpert.plugin.level=tenant` 决定 scope；`plugin:deploy:local --scope tenant` 先 build + verify:dist + test，再 refresh，未安装过则回退 `source: code`；输出 `restartRequired` 要重启 API。
8. **远程组件的协议细节？** —— `xpertai.remote_component` v1：子窗口 `ready` → 宿主 `init`（带 `instanceId`）→ 请求带 `requestId`；`requestData` / `executeAction` / `resize`；宿主只接受 `event.source === window.parent`。

**工程与流程类**

9. **平台自带外壳你跑通没有？** —— 跑通了，代价是三样 seed 库不提供的东西（会员计划/特性、`copilot.role` + provisioner 上下文、provisioning actor 权限）。其中"后台任务里取不到 provider"看起来是宿主侧真实缺陷，我记在已知限制里。
10. **失败是真的吗？/ 权限做到什么程度？** —— 界面的"需重试"是 SQL 造的模拟状态（文档允许模拟，我三处文档都标了）；权限验了跨租户四级，未验同租户两组织。

## 4. 五个反问（面试尾声用，挑两个问）

1. 这个插件形态在平台里后续怎么演进？视图/中间件 API 有版本策略吗（我现在按 3.18.4 的契约写）？
2. 平台侧对"AI 建议 + 人工确认"这类人机回路的应用，有没有官方推荐的状态机或审计要求？

## 5. 演示脚本（约 5 分钟）与翻车预案

```
0:00  打开 /apps（或工作区）→ 说明：这是一个装在 Xpert 里的业务应用，不是聊天机器人
0:30  进「工单分诊」tab（真实外壳）或 board-host.html（替身）→ 点「载入演示工单」→ 4 张待处理
1:00  回到助手 → 发："请调用 list_pending_tickets 列出待处理工单，然后只对 T-1002 提交分诊建议：
      priority=P2、team=billing，并给出 rationale 与 draftReply。"
1:30  指两张工具卡（0.06–0.09 s）→ 说明：AI 只写了 proposed，没有关闭
2:30  切看板 → 选中 T-1002 → 读 AI 的优先级/组/依据/草稿 → 点「确认分诊」→ 计数变化 + toast
3:30  F5 刷新 → 数据还在（这就是"保存与恢复"）
4:00  讲失败重试：打开 board-host.html 的 needs-retry 场景 → 展示失败原因与「重试分诊」→ 行数仍 4
4:30  收尾：四层验证一句话 + 已知边界一句话
```

**翻车预案**

| 情况 | 处理 |
| --- | --- |
| 模型网关不通（TUN 把域名解析成 `198.18.0.48`） | 直接放截图 05（真实工具调用）与 `evidence.json.browserRun`，说明这是当时真实跑出的记录 |
| 平台没起或 Docker 挂了 | 用报告 PDF（截图全内嵌）+ 本文件第 1 节口述；强调"证据在仓库里，可查" |
| 界面点不动 / 权限报错 | 切 `board-host.html` 替身宿主（同协议、真接口），并说明区别只有外壳 |
| 被问"这不是你自己写的吧" | 主动讲第 3 节第 5 条隔离实验与被驳回的六件事（[04](04-ai-collaboration.md) 第 4 节） |

## 8. 不吹的部分（主动说，别等被问）

- 界面里的"失败/待确认"状态有一部分是 SQL 造的，不是真实故障注入（[06](06-gaps-and-pr.md) 第 8 条）。
- 只在 Windows 宿主 + Linux 容器上验过，宿主侧 5 处补丁不进 PR。
- 同租户两组织隔离没验；行级权限没做。
- 题面写 2–6 小时，我实际花得远超——时间主要花在"让平台在这台机器上真的能起来"，不是写业务码。

## 9. 一句话自评

做得最好的是"人在回路"这条线：AI 提议、人签字、重试不重复建单，三层都有证据，而且是在平台自带入口里验的。最弱的是环境侧：换台机器不是一键能复现的——我把这条写在已知限制第 2 条，没有绕过。
