## 已实现的协作链路

同一项目中，具有权限的成员可以通过不同 Assistant 打开同一 Markdown 文档。编辑器使用 Tiptap 与 Yjs；平台管理协作房间、身份、权限、更新日志和文件发布。Spaces 负责内容组织，独立 Markdown 插件负责编辑界面。

- 按文档与 epoch 隔离房间；同一文档不因入口 Assistant 不同而产生副本。
- 本地增量经宿主 `document.update` 提交，平台持久化后通过 WebSocket 向已授权接收者广播。Yjs 合并并发修改，重复增量不会重复追加正文。
- 在线人数按账号去重；光标和选区按窗口区分，姓名与颜色来自平台身份。状态不写入正文。
- 断线后通过状态向量补齐缺失更新。未提交增量保留在当前窗口重试；这不等于关闭浏览器后的持久离线编辑。
- 保存状态区分「编辑已接收」与「已写入项目文件」。只有文件发布完成才显示已保存；外部文件冲突不能被静默覆盖。
- 历史恢复或 schema 升级切换 epoch，旧窗口不能覆盖新版本。所有会话和广播仍检查当前项目、Assistant 及资源访问权限。

## 跨账号广播修复

2026-10-23 的真实测试复现了：两个账号能显示在线，但提交编辑会导致另一方断连。进程内广播继承了 HTTP 提交者的 AsyncLocalStorage；文档权限校验把接收者身份与提交者进行比较，误判为身份不匹配。

平台 `CollaborationGateway` 在广播投递边界退出提交者请求上下文，再按各接收者已认证的协作会话逐个授权。普通 HTTP 请求的身份一致性校验保留，撤权接收者仍被断开。Provider 必须使用显式授权上下文中的 actor，不能借用广播提交者的身份或权限。

回归测试覆盖发送方与接收方不同、HTTP 冒用 actor 被拒绝、已撤权接收者不获得广播。网关与协作服务的 6 项定向测试通过。

## 真实验收

两个独立测试账号通过正常登录获取身份，分别经两个已发布 Assistant 打开同一项目文档。测试直接连接实际 API、WebSocket、数据库和项目文件，没有替换协作服务或模拟持久化。

| 场景 | 验证结果 |
| --- | --- |
| 双账号进入 | 相同房间、不同身份，双方均看到两人在线 |
| 同一位置同时输入 | 两份内容通过远端 WebSocket 广播收敛，甲乙输入均保留，重复提交被去重 |
| 光标与选区 | 对方收到正确账号与 Yjs 相对位置 |
| 任务清单与公式 | 不同账号的节点修改同时保留 |
| 断线与重连 | 离线成员移出在线列表，重连补齐遗漏内容，缓存修改重发后收敛 |
| 未授权账号 | 获取会话与提交更新均被拒绝 |
| 文件与重开 | 两端内容、重新获取的文档状态和实际 Markdown 文件一致，SHA-256 与平台记录一致 |

这次浏览器自动化连接中断，未完成两个可见浏览器窗口的交互验收；上表为真实协议客户端验收，不能等同于双窗口视觉验收。跨 API 节点和长时间压力测试也不在本次结果中。

## 复现方式

先启动配套平台与插件，准备私有目录中的正常登录助手 `probe.mjs` 和已有测试项目配置 `editor-acceptance-fixture.json`，再从 Markdown 插件目录执行：

```bash
SPACES_TEST_DIRECTORY=/absolute/path/to/private-test-environment \
node tests/collaboration.live.mjs
```

脚本创建独立验收页面，输出七项结果，并将包含实例标识的回执保存到该私有目录。凭据不写入源码、文档或终端结果。可在同一项目的协作空间中打开标题以「双账号实时协作验收」开头的页面继续人工验证。
