## Setup

1. Install `@xpert-ai/plugin-github-connector` in the application's organization. Upgrade the platform to support scoped plugin integration resolution and the pinned Connector authorization dialog.
2. Create a GitHub App with **Contents: Read**, **Pull requests: Read & write**, and **Pull request** events. Configure OAuth callback `https://YOUR-API-DOMAIN/api/connector/oauth/callback` and webhook `https://YOUR-API-DOMAIN/api/code_review/github/webhook`.
3. In **Settings → System Integration**, create a tenant-level `github` integration in the system plugin's Default tenant. Set `appId`, `appSlug`, `clientId`, `clientSecret`, `privateKey` (complete PEM), and the matching `webhookSecret`. The secret may be omitted during setup; webhook acceptance requires at least 32 characters. Set the public API origin in the host's `API_BASE_URL`.
4. In **Plugins → Code Review → Configuration**, select that integration (`githubIntegrationId`). All App credentials are maintained in System Integration. The plugin will not read organization-scoped or other-tenant integration credentials.
5. In **Repositories → Connect GitHub**, authorize through the required integration. Existing shared connections using a different integration, PAT, or an older credential without OAuth application provenance must be disconnected in workspace connector settings and reauthorized. Install the same App on selected repositories. The connected account must have write/admin permission; it need not own the organization where the App is installed.
6. Add `owner/repository`, run a trial, then enable and save rules. For existing repositories migrated from inline configuration, save enabled rules again to confirm the integration/App binding. The migration and release order are documented in the [README](https://github.com/xpert-ai/xpert-plugins/tree/main/xpertai/apps/code-review#upgrade-from-inline-github-app-configuration).

The host must retain signed JSON bytes as `request.rawBody`, register the Managed Queue processor, and expose the `workspace.connector.connect` command with integration selection. Secrets never pass through the review view. GitHub cannot deliver events to localhost; local acceptance does not establish external webhook connectivity.

## Rules and publication

Defaults: automation paused; draft delivery; opened/reopened, ready-for-review and new-commit events enabled; drafts and bots excluded; common lockfiles ignored; all base branches; 20 model review attempts per repository per UTC day, including trials. Base branch names are exact matches; ignore paths support `*`, `**` and `?`.

Push events wait at least 30 seconds. A fresh GitHub read rejects obsolete commits, closed PRs and drafts before starting and before publishing. Results use immutable head/base evidence and validated diff anchors. Daily quota reservations and review identities are persisted before dispatch.

**Save draft** requires a separate confirmation in the inbox. **Automatic comments** posts a summary and only P0/P1 inline findings with GitHub's `COMMENT` event. It never approves, requests changes or merges PRs. Both modes use the installation identity, limited to the selected repository. Changing rules invalidates pending attempts from the previous policy revision. Review metadata and findings remain private to the configuring user, tenant, organization and Assistant.

The configuring account, Assistant and model access must remain valid for unattended runs. App installation access and a working webhook are also required. The system allows one automation configuration per App installation/repository to prevent overlapping bots posting duplicate reviews.

## Recovery

The inbox shows trigger, commit, policy revision, progress, result and actionable failure reason. Failed, skipped, cancelled and superseded attempts can be retried; a retry creates a new record against the current head and policy. Retries still consume the daily quota. Trial retries remain private.

Duplicate webhook deliveries and duplicate queue workers share database-protected operation keys. Durable Managed Queue supervision is re-armed on bootstrap. Platform task IDs are persisted before dispatch and reconciled; task completion without the result finalizer is a failure.

If an external POST might have succeeded but its response is lost, publication becomes **Check GitHub**. The plugin will not repeat that POST or offer a blind retry. Open the PR to reconcile the result. GitHub App credential revocation, unavailable models or missing repository permissions remain visible failures; the plugin never falls back to another tenant's credentials.

## Local acceptance

Run the ordinary Nx checks and lifecycle harness. The opt-in PostgreSQL acceptance script creates a disposable schema and removes it afterward. Prefer a dedicated database whose name starts with `xpert_pipeline_test_`:

```sh
XPERT_PIPELINE_TEST_DATABASE_URL=postgresql://localhost/xpert_pipeline_test_review \
node apps/code-review/scripts/automation-acceptance.mjs
```

It uses fixture GitHub/model/queue transports, real plugin services, and real PostgreSQL transactions. It tests integration scoping, secret rotation, changed-App rejection, migration, deduplication, single ownership, current-head checks, confirmation, P0/P1 filtering, ambiguous publication, quotas, pause, retry, trials and bootstrap recovery. It does not authorize a real GitHub account or post to a real PR. Browser acceptance and a real model review are separate checks.
