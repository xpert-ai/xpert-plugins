---
title: "Architecture"
---

The plugin owns Review, Repository, Run and Delivery entities, GitHub user/App adapters, a signed webhook controller, Managed Queue processor, middleware, templates and iframe view. Xpert owns authentication, model credentials, task execution, connector credentials and the conversation shell.

Records are isolated by tenant, organization, user and Assistant. Revision checks serialize changes. Source reads use immutable base/head hashes; inline findings must point into a real diff hunk. Missing diff/check evidence remains visible as coverage warnings. Completion is bound to the dispatched execution and head hash. PR text and code are untrusted evidence.

Host bridge messages validate source window, instance, protocol and scope revision. The selected review is supplied through `assistant.context.set`; tools re-authorize this context rather than trusting iframe data. No browser storage is required.

The right panel contains the PR inbox, summary, file diffs, findings and checks. The existing host chat remains the only composer.

The unattended pipeline resolves `githubIntegrationId` through the built-in `IntegrationPermissionService.readConfiguration(id)` capability. The host binds this reader to the installed plugin scope and checks declared integration access; system configuration belongs to the Default tenant and cannot resolve an organization integration. Code Review supplies only the ID, validates the GitHub identity, verifies the webhook signature and maps installation/repository IDs to one stored owner scope. Review execution still checks its business tenant against the authorized integration. Request headers and unsigned payloads never select the configuration scope. Existing plugins retain the legacy runtime `read(id, options)` contract; no plugin-specific CQRS query is required.

The workspace Connector carries the integration ID and original OAuth Client ID from its stored credential. Repository setup checks both against the selected integration, then persists its integration and App ID. Workers compare that binding before acquiring an installation token restricted to the repository. An App switch requires repository revalidation; a policy revision change invalidates pending attempts. Legacy inline configuration is accepted only without a reference, and selecting a reference removes the legacy copy.

Repository jobs only scan persisted state in keyset pages and enqueue record IDs, phases and expected state versions. A review advances through quota reservation, snapshot preparation, platform dispatch and status observation in separate Managed Queue jobs. Workflow diagnosis similarly separates evidence/quota preparation, dispatch and observation; a webhook job processes one delivery. Each job returns after its stage. Model execution and human approval never keep a plugin worker or lease alive.

Stage exclusion uses Managed Queue Redis, scoped by tenant/organization/repository and PR number (or delivery/diagnosis ID). Different SHAs of the same PR remain serialized; different PRs in the same repository can proceed independently. The lease expires after 60 seconds and renews only while that single stage runs. Ownership checks remain at external-call/mutation boundaries; they are not an atomic fence for an already issued remote request. Stable execution/command IDs, unique receipts and domain revision checks protect retries. A stale owner cannot release a replacement's lease. Old queued state versions cannot advance a later phase.

PostgreSQL row locks are limited to short policy, webhook and quota transactions. GitHub, authorization and platform capability calls run outside those transactions: holding a row lock while requesting another pooled connection can exhaust the entire API pool when duplicate supervisors accumulate. Repository rebinding validates external authority first, then rechecks the revision and pending runs in its short write transaction; conflict disclosure resolves Assistant authority after releasing the creation lock. These existing database-only transactions preserve atomic quota, audit and receipt updates until the host provides equivalent atomic domain commands.

Signed PR and workflow webhooks are acknowledged only after their normalized event and authenticated repository/App binding are stored in the Delivery inbox. No raw body, signature or credentials enter the inbox or queue. Workers create the run and acknowledge the delivery in one short transaction, clearing the normalized payload after processing. A contested policy row leaves the delivery pending with bounded backoff; duplicate deliveries retain their original digest and cannot create duplicate runs. A changed policy/App binding retires the pending event with an explicit reason rather than executing it under a replacement binding. Temporary authorization failures remain retryable.

Queue jobs contain scoped identifiers, phases and state versions only. Successful stages release their lease before enqueueing the next stage; unchanged states use delayed observation. A periodic, non-overlapping recovery pass reconstructs pending stages after process restarts or failed queue wakeups, so an already acknowledged delivery does not depend on GitHub redelivery. Database persistence failure still returns an error to the webhook caller. Quota claims skip contested rows and retry on a later wakeup. Review dispatch identity is committed before calling the platform, and publication uses a separate server policy guard rather than fabricated human confirmation.
