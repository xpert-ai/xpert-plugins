# 会后行动项核对与确认工作台

## 需求与开发方案

- 文档版本：0.11（对应插件 0.1.5）
- 日期：2026-11-01
- 用途：已实现范围、交互规则和验收要求；实际完成情况以验证记录和交付清单为准
- 功能分支：`feat/meeting-action-review`
- 插件仓库：个人 Fork 的 `xpert-plugins`，路径按本机环境配置

第一版帮助会议整理者，把已有会议文本转换为一份经过人工核对的行动项清单。AI 提供提取草稿，用户决定最终保留什么，应用保存原文、编辑结果和确认状态。

**业务终点是确认并保存清单，不延伸到任务派发、提醒或执行进度管理。**

已确定选题、保持小范围的原则，以及在 Xpert 中以独立业务应用插件交付的方向。第 4、5 节交互布局和第 6、7 节服务端后台分析、两张表与五阶段开发方案保持不变。第 8 节验收与测试方式、第 9 节交付证据要求沿用已确认方案。输入与结果数量上限采用开发设计中的实施初值，120 秒超时为待实测的初始值，见第 12 节。当前宿主 3.29.1 源码与 SDK 接口已核对；插件 0.1.5 已安装并完成会话同步联调。本文中的验收用例定义是检查标准，不代表所有用例都已执行，实际覆盖以验证记录为准。

本次补充[开发设计](meeting-action-review-development-design.md)和独立的[数据库设计](meeting-action-review-database-design.md)，并校正平台暂停状态的解释；首版业务代码与测试已完成，0.1.5 会话同步已安装验证；本地分层验证结果见[插件验证记录](../community/apps/meeting-action-review/docs/verification.md)，0.1.4 的真实平台主流程与失败重试已完成，剩余专项见验证记录。本文负责需求与验收，开发设计负责接口与执行流程，数据库设计集中维护字段、索引和事务约束。

本轮按用户确认收敛为仅修改插件：提交提取后同步实际建立的新会话、历史项同步最近尝试会话、保留插件内未保存编辑保护。平台清空入口、外部导航和原生停止/恢复保持现状。验证事实见[聊天联动能力验证](meeting-action-review-chat-sync-validation.md)，具体交付结果以安装验收为准。

## 1 用户与问题

### 1.1 目标用户

小团队的会议组织者或会后记录整理人。第一版只设一个业务角色：整理者。不建设人员目录，不要求被提及的负责人拥有 Xpert 账号。

### 1.2 典型场景

会议结束后，整理者手上已有一段文字记录，其中混杂了讨论、建议、承诺和被取消的安排。整理者需要重新阅读，找出明确事项，补齐负责人和时间，并保存一份可追溯的清单。

应用降低首次整理的工作量，同时保留人工核对环节。原文依据用于帮助用户判断 AI 是否误提取；确认状态用于区分“AI 建议”和“已经核对的结果”。

### 1.3 完成标准

用户能够在 Xpert 工作台中提交会议文本，获得真实 AI 生成的行动项，完成编辑和确认，刷新或重新进入后仍能看到同一份记录。分析失败时，原文保留，能够在原记录上重试。

“已确认”表示整理者核对过清单，不表示事项已经分派、负责人已经接受任务或任务已经完成。

## 2 第一版范围

### 2.1 本期包含

1. 会议记录的新建与历史列表。
2. 标题和会议文本输入。
3. 一次真实 AI 提取，生成结构化行动项及原文依据。
4. 人工编辑、新增、移除条目和保存草稿。
5. 确认清单、查看结果和保存恢复。
6. 分析中、空结果、失败提示与失败重试。
7. 一个助手模板、一个业务中间件和一个 Workbench 页面。

### 2.2 本期不包含

- 录音、语音转写、PDF 或 Word 文件上传解析。
- 对接会议平台、飞书、微信、邮件、日历或任务系统。
- 自动派发任务、发送通知、催办、SLA 或任务完成率统计。
- 多智能体协作、多人实时编辑、复杂审批和人员权限管理界面。
- 负责人账号匹配、日期自动推算、跨会议去重。
- 知识库、联网搜索、命令执行或沙盒。
- 清单导出、多版本比较、确认后修订历史。
- 单独保存尚未提取的输入草稿、自动保存、逐项确认。
- 取消分析、成功提取后重新生成、撤回确认。
- 历史记录搜索、筛选和删除。

布局和业务交互优先参考已有智能维保插件的“列表进入详情、AI 草稿由人工核对确认”结构，不照搬其统计区、宽表格或派单功能。Meetings 可作为窄工作台导航和平台接入方式的辅助参考。本项目独立实现“已有文本的行动项核对与确认”，不扩展为会议录制或会议管理系统。复用的代码、组件和许可需在交付材料中说明。

## 3 数据内容与提取规则

### 3.1 用户看到的字段

| 对象 | 字段 | 处理方式 |
| --- | --- | --- |
| 会议记录 | 标题 | 用户填写，用于历史列表识别 |
| 会议记录 | 原文 | 用户粘贴，作为提取和核对依据 |
| 行动项 | 事项 | 必须是具体待办内容，允许人工修改 |
| 行动项 | 负责人 | 文本字段；未明确时留空并显示“未明确” |
| 行动项 | 完成时间 | 保留原始表达；不把“周五前”自动换算为日期 |
| 行动项 | 原文依据 | 可展开查看对应原文片段；不由用户编辑成伪造引文 |
| 行动项 | 来源与调整标记 | AI 提取或人工补充；AI 条目被人工修改后标记“人工调整” |
| 行动项 | 核对提示 | 存在歧义、冲突或缺失信息时显示简短提示 |

不额外加入优先级、任务分类、执行状态、工时等字段。

### 3.2 AI 提取规则

1. 提取明确决定要做的事项及明确承诺。
2. 不把“可以考虑”“以后再说”等讨论建议直接当作已确定的任务。
3. 对明确被取消、撤回或替换的安排，依据后续明确表述处理，不保留失效安排。
4. 无法判断冲突如何解决时，标记待核对，不自行推断最终决定。
5. 不编造负责人、完成时间或原文依据；“未明确”是正常结果。
6. 同一事项的连续描述可以合并，但不能把不同责任混成一个无法核对的条目。
7. 没有明确行动项时返回空清单，不为了凑数量生成任务。

服务端为原文片段分配引用标识，AI 返回对应引用，服务端再取回原文展示。引用必须确实存在；引用存在只证明来源可定位，语义是否准确仍由用户核对。

### 3.3 演示材料

会议原文：

> 小王负责更新产品报价，11月3日前完成。小李核对库存，时间还没定。我们可以考虑下周做一场直播，先不安排。刚才说的周五上线取消，等测试通过再定。合同还需要跟进，负责人暂时没定。

期望结果如下。这里用表格说明示例数据，实际工作台采用第 5 节的纵向编辑条目布局。

| 行动项 | 负责人 | 完成时间 | 核对重点 |
| --- | --- | --- | --- |
| 更新产品报价 | 小王 | 11月3日前 | 与明确承诺对应 |
| 核对库存 | 小李 | 未明确 | 不补造日期 |
| 跟进合同 | 未明确 | 未明确 | 保留缺失信息 |

“考虑直播”不应自动成为确定任务；“周五上线”已被取消，不应作为有效行动项。该材料用于开发与演示，不含真实会议隐私。

## 4 用户操作的每一步

本节业务交互沿用已确认方案；左右联动范围集中在 4.8，本次在 0.1.4 基础上开发插件升级。用户可见文案可微调，不改变操作规则。

### 4.1 新建与输入

1. 外层沿用 Xpert 的聊天与工作台布局。插件内部在记录列表、新建表单和记录详情之间切换，不常驻历史侧栏。首次使用没有记录时直接显示空白输入表单；已有记录时默认打开最近更新的记录详情。
2. 在列表或详情点击“新建”，先处理未保存内容，再打开右侧空表单；左侧保留原会话。提示“提交提取后，左侧将切换到本次分析会话”。此时不创建业务记录、不发送消息、不创建占位会话。
3. 输入区只有两个必填项：单行“会议标题”和多行“会议原文”。原文支持粘贴和修改；不增加日期、参会人或文件上传字段。
4. 第一版不提供“保存输入草稿”按钮。“保存草稿”只用于提取结果的人工核对阶段。
5. 点击“提取行动项”后，先校验必填项。缺失时在对应输入框下提示，保留其他输入，不调用 AI。
6. 校验通过后，提交按钮立即进入处理中状态并禁用。服务端先保存标题和原文，再启动 AI 分析。
7. 输入保存失败时，保留页面输入，恢复编辑和提交按钮，提示“提交失败，输入内容已保留，请重试”。不发起 AI 调用；再次提交也不得重复建记录。

未提交输入就返回历史列表、切换到其他记录或新建另一份记录时，提醒输入尚未保存，允许继续填写或放弃输入后切换；此阶段不提供“保存并切换”。

首版按原文 10,000 个字符、AI 与人工编辑后的清单总数最多 30 项开始实现；字段上限与模型预算见开发设计 9.1，统一按 Unicode 码点计数，超限明确提示，不静默截断。数值作为实施初值，以实际验收验证。

### 4.2 AI 处理中

1. 输入保存并提交分析后，该记录进入历史列表，状态为“分析中”；右侧停留在记录详情，标题和原文只读。新增目标是在执行会话真实就绪后打开左侧对应会话；不是再次启动分析。原生运行控制沿用平台行为。
2. 按钮显示“正在提取…”，禁止重复点击。结果区显示加载状态，以及“正在整理行动项，结果生成后请核对原文”。
3. 右侧不逐字展示 AI 输出、不展示推理过程，不使用虚假百分比；完整结果通过校验后一次性展示。左侧新增目标是平台可公开的真实执行活动与短摘要，不能制造细分阶段或把执行结束冒充业务成功。
4. 用户可以通过“历史记录”返回列表，再打开其他记录，后台继续处理当前会议。返回列表或切换记录不等于取消任务，也不强制锁住整个工作台。
5. 当前记录完成后，更新对应历史状态。列表正在显示时反映最新状态；用户若在其他记录详情中，不为此展开列表、不强制跳转或抢焦点。重新打开该记录时展示结果。
6. 刷新页面不再次发起分析。页面重新读取服务端状态，显示仍在处理、已生成结果或失败信息。
7. 分析必须在成功、失败或超时中结束，不能永久停在“分析中”。超时初始值建议为 120 秒，实施时验证其适用性；超时后提示“本次提取超时，原文已保留，可以重试”。

第一版仍不增加暂停/恢复/取消业务。左侧原生“停止”会暂停真实执行，保持平台现状；插件不接管暂停/恢复，现有固定截止时间和重试隔离保持不变。后台处理不能依赖浏览器 loading，旧结果不能覆盖新尝试。

### 4.3 查看提取结果

1. 提取成功后进入“待核对”。详情按记录信息、会议原文、行动项核对、底部操作纵向组织，不固定并排展示全文和结果，也不常驻历史列表。
2. 会议原文默认折叠，用户可以展开全文；全文只读。成功提取后不修改原文，需要换原文时新建记录。
3. 行动项区域顶部显示“AI 提取了 N 项，请核对后确认”，并展示负责人、时间缺失或存在歧义的条目数量。
4. 每个行动项是一组纵向编辑字段，事项占满一行；负责人和完成时间在空间足够时并排，不足时上下排列。以轻分隔线区分条目，不使用固定四列表格或厚重的大卡片。
5. 空缺负责人或时间显示“未明确”，不自动补值；冲突或歧义在对应事项下面显示简短提示，例如“完成时间前后不一致，请核对”。
6. 点击某项“查看依据”，仅在该条目下面展开对应原文片段，不强制跳到全文。片段旁提供“定位原文”，用户需要完整上下文时再展开全文、定位并高亮对应位置。原文和引用都只读，不跳转新页面、不展示 AI 推理过程。
7. 用户可直接修改事项、负责人和完成时间。人工调整和未保存状态按 4.4 分别标识；人工补充条目不提供虚假的依据。
8. 不增加逐项确认或“已核对”勾选；通过“确认清单”确认整份结果。

空结果展示：“未识别到明确行动项。你可以检查原文，或手工补充事项。”不显示“分析失败”，不生成占位条目。空清单也可以按 4.5 确认。

### 4.4 人工编辑与保存草稿

**修改已有条目**

- 点击事项、负责人或完成时间直接编辑，原文依据只读。
- 编辑后显示“有未保存更改”。AI 条目被人工修改后，保留原始依据并标记“人工调整”。
- “人工调整”说明内容经过人的修改；“未保存”说明当前编辑尚未写入服务端。保存成功会清除未保存状态，不抹掉来源和人工调整标记。

**新增条目**

- 点击行动项区域末尾的“新增行动项”，增加一组纵向编辑字段，焦点进入“事项”输入框，不另开创建窗口。
- 事项必填，负责人和完成时间可以留空。
- 来源标记为“人工补充”，不生成虚假的原文依据；与其他编辑一起保存。

**移除条目**

- 点击对应条目的“移除”后，立即从当前行动项区域移除，不弹逐条删除确认框。
- 显示“已移除一项 · 撤销”。保存前可撤销最近一次移除，不建设多步撤销历史。
- 保存成功后，移除正式生效，不能再通过这次提示撤销。确认清单成功同样会提交当前移除结果。

**保存草稿**

1. 没有未保存修改时，“保存草稿”按钮禁用；第一版不自动保存。
2. 点击保存后，校验每个条目的事项是否为空。有问题时定位对应条目，保留全部编辑，不静默丢弃空白条目。
3. 负责人或时间未明确，不阻止保存。
4. 保存期间底部按钮显示“保存中…”，行动项编辑区域暂不可编辑，禁止重复保存和确认，避免请求中混入新修改。
5. 成功后提示“草稿已保存”，清除未保存状态，记录仍为“待核对”。刷新或重新打开后恢复该版本。
6. 失败时提示“保存失败，请重试”，恢复编辑能力并保留页面内容；不得清空编辑或回退到旧数据，也不重新调用 AI。

**有未保存修改时切换记录**

在插件内部返回历史列表、切换记录或点击“新建”时，提供三个选择。新增联动中，这个保护必须发生在任何一侧开始切换之前；当前来自宿主左侧的直接导航尚不受该提示完整保护：

| 选择 | 行为 |
| --- | --- |
| 保存并切换 | 校验并保存成功后再切换；保存失败或校验未通过，留在当前记录 |
| 放弃修改并切换 | 放弃页面未保存编辑，服务端保留上次成功保存的版本，然后切换 |
| 继续编辑 | 关闭提示，留在当前记录 |

浏览器刷新或被强制关闭时，只保证恢复服务端已保存内容，不承诺恢复未保存编辑。

### 4.5 确认清单

“确认清单”放在“保存草稿”旁，作为核对阶段的主要操作。不要求用户先保存草稿，确认时一次性保存页面最新编辑与确认状态，不能误用旧草稿作为最终结果。

**确认前检查**

- 每条行动项的事项不能为空；有空项时定位对应条目，保留编辑。
- 负责人或完成时间未明确，允许确认，但持续展示缺失数量，不强迫用户补造信息。
- AI 的歧义或冲突提示继续保留，不因点击确认就表现为系统自动解决。
- 允许确认空清单，含义是“本次会议无明确行动项”。

**一次整份清单确认**

点击“确认清单”后显示一次确认框，不增加逐条确认。示例：

> 确认这份行动项清单？
>
> 共 3 项，其中 1 项负责人未明确、2 项完成时间未明确。
>
> 确认后清单将只读。确认表示内容已核对，不会向负责人派发任务。

按钮为“返回核对”和“确认并保存”。空清单时改为提示“确认本次会议无明确行动项”，并说明确认后只读。

**提交和结果**

1. 提交时显示“正在确认…”，禁止重复提交和继续修改。
2. 服务端同时保存当前结果与确认信息，成功后状态变为“已确认”，显示确认时间。
3. 失败时保留全部编辑，停留在待核对页面并允许重试。
4. 网络响应丢失、无法判断是否成功时，先查询服务端状态；已确认则加载最终结果，不重复确认，未确认才允许重试。
5. 确认后只读，可查看原文、行动项、依据并返回列表或切换记录，不再显示新增、移除、保存草稿等编辑操作。行动项用可阅读的正常文本展示，不把整页输入框变成灰色禁用状态。第一版不做撤回确认、修订或版本比较。

AI 工具不能执行最终确认。权限、状态、重复请求和只读限制在服务端验证，不仅依赖提示词或前端禁用。

### 4.6 历史查看与恢复

**历史列表**

- 每条记录只显示会议标题、当前状态和最近更新时间，按更新时间倒序排列。
- 历史列表使用整个插件工作台区域，与记录详情切换展示，不作为常驻侧栏。整条记录可点击，不增加行内编辑、确认或删除按钮。
- 状态包括分析中、待核对、已确认和分析失败。未提交的输入表单不进入历史列表。
- 第一版不提供搜索、筛选和删除历史记录。
- 从应用入口进入且没有记录时直接展示新建表单；若用户返回一个空的历史列表，提示“还没有会议记录”并提供“新建”入口。

**打开记录**

| 状态 | 展示和允许操作 |
| --- | --- |
| 分析中 | 已提交原文和处理状态，不重复提取 |
| 待核对 | 最近成功保存的行动项草稿，可继续编辑 |
| 已确认 | 最终清单、原文依据和确认时间，只读 |
| 分析失败 | 已保存原文、失败原因和“重试提取”按钮 |

新增目标：点击列表记录后，右侧进入最新保存详情，左侧打开该记录最近一次分析尝试的会话；没有可用会话时不发出导航，并明确提示左侧尚未对应本记录；排队期间等待实际回执，失败后可单独重试打开会话，不重跑 AI。通过详情顶部的“历史记录”返回列表。返回列表、切换记录或新建前存在未保存的核对编辑时，执行 4.4 的三个选项；未提交输入表单按 4.1 处理。

**刷新与重新进入**

1. 刷新时恢复当前选中的记录，并重新读取服务端数据，不自动再次调用 AI。
2. 恢复内容以最近一次成功保存为准，不承诺恢复未保存编辑。
3. 分析任务若已完成，直接展示结果；仍在运行则显示“分析中”；已失败则显示失败信息。
4. 关闭页面后从应用默认入口重新进入，默认打开最近更新的一条记录，不单独持久化上次浏览位置。

**后台完成与列表更新**

- 用户正在查看分析中的当前记录时，成功后自动展示完整结果。
- 用户正在历史列表且当前页有分析中记录时，轮询更新对应记录状态；用户正在查看其他详情时，不自动展开列表或跳转，后续返回列表能看到最新状态，不覆盖当前编辑。
- 列表重新排序不改变当前打开的记录身份，不因行位置变化而打开另一条记录。

**读取失败或无权访问**

加载失败时提示“加载失败，请重试”，保留当前选择和页面上下文，不能误显示为“没有记录”。指定记录已不可访问时显示明确提示，允许返回列表，不展示无权查看的内容，也不自动打开另一条记录。仅未指定记录的默认入口才打开最近记录。

### 4.7 失败与重试

失败按所处阶段处理，不把所有错误都变成“重新分析”。

| 失败阶段 | 用户看到什么 | 保留内容与重试方式 |
| --- | --- | --- |
| 输入保存 | “提交失败，输入内容已保留，请重试” | 保留标题和原文，恢复提交；未保存成功不调用 AI，重复提交不重复建记录 |
| AI 分析 | 简短原因和“重试提取”按钮 | 原文已保存，记录为“分析失败”，不展示未校验的半成品结果；在同一记录上重新分析 |
| 保存草稿 | “保存失败，请重试” | 保留当前编辑，只重试保存，不重新调用 AI |
| 确认清单 | 确认失败或结果待核实的提示 | 保留编辑；先核对服务端状态，再决定是否重试确认 |
| 历史加载 | “加载失败，请重试” | 保留当前选择和上下文，只重试加载，不重新分析 |

**AI 分析失败与手动重试**

- 模型调用失败、超时或返回结果未通过校验，属于分析失败；正常空清单不是失败。
- 对用户显示可理解的原因，具体技术错误放在可展开详情中，隐藏密钥和其他敏感信息。
- 点击“重试提取”，使用同一份已保存原文，在原记录上创建新的有效分析尝试，状态回到“分析中”。
- 重试期间沿用 4.2 的交互，禁止同一记录并发分析。旧请求或重复回调不能覆盖新尝试和人工结果。
- 允许用户在失败后再次手动重试，应用层不无限自动重试。模型未配置、权限不足等明确配置问题，提示先修正配置，避免无意义地重复请求。
- 成功提取后不提供重新生成，避免覆盖人工编辑。

**后台任务异常中断**

API 重启或连接中断后，先核对后台执行状态。仍可继续的任务保持“分析中”；已确定失败或到期仍无合法结果的任务提示“本次分析未完成，原文已保留，可以重试”。不能只因浏览器断线就判定后台失败，也不能让记录永久卡在“分析中”。

响应未知时保留原请求编号和提交快照，先核实原操作，不能直接恢复为一次新提交；明确失败才允许修改内容后重新提交。确认丢包仍按先查状态再重试处理。

重试始终针对原操作：尚未建立记录的首次提交使用去重机制；已建立记录的分析、保存和确认复用原记录。明确的成功或失败状态必须来自服务端。

### 4.8 左右会话同步（仅插件）

- 提交提取成功后先进入右侧详情；后台实际执行回执就绪时，打开该尝试的既有会话，不发第二条请求、不再次分析。
- 历史项打开最新保存清单，并打开 activeAttempt 指向的最近分析会话；重试使用新尝试会话。新建空表单和历史列表不主动切换左侧。
- 所有插件导航先完成保存并切换、放弃并切换或继续编辑；保存失败不切换任何一侧。异步回执不得覆盖较新的选择，也不能在用户开始编辑后触发会话切换。
- 只用公开 View query 和 workbench.navigation.open，不操作宿主源码、私有路由或聊天 DOM。
- 会话未就绪、不可访问或导航失败时明确提示左侧尚未同步，可重试打开；重试导航不创建分析任务。右侧已保存数据继续可用。
- 左侧保留初始提取过程；右侧是人工编辑和确认的权威版本。不增加聊天改库、确认通知或暂停/恢复业务。
- 原生停止可能暂停真实任务，继续沿用平台现状；插件原有超时与过期尝试隔离不变。跨平台菜单导航、关闭和刷新未保存保护不在插件本次承诺内。

### 5.5 原文与依据

提取完成后，会议原文默认折叠，为行动项留出空间。用户可以自行展开只读全文。

每项的“查看依据”在本条目下面展开引用片段，主要核对操作不用离开该条目，也不自动滚动到全文。引用片段旁提供“定位原文”，需要更多上下文时再展开全文并定位、高亮对应位置。

原文和引用只读，不展示推理过程。普通查看依据不弹出大窗口，不切换浏览器页面；折叠、展开和定位操作不改变编辑结果或保存状态。

### 5.6 各状态的按钮与提示

| 状态或操作阶段 | 主要内容与提示 | 操作展示 |
| --- | --- | --- |
| 未提交表单 | 标题和原文输入；必填错误就近提示 | 提取行动项、返回历史记录；无保存输入草稿 |
| 正在提交输入 | 表单保留，输入暂时只读；“正在提交会议记录…” | “正在提交…”禁用，防止重复提交 |
| 分析中 | 已保存原文、状态和加载提示；不展示假进度、推理或半成品 | “正在提取…”禁用；可返回历史列表，不加取消按钮 |
| 待核对且有结果 | 纵向可编辑条目、提取数量、来源和缺失提示 | 条目级查看依据、移除；末尾新增；底部保存草稿和确认清单 |
| 待核对且无结果 | “未识别到明确行动项”，无占位条目 | 新增行动项、确认清单；未修改时保存草稿禁用 |
| 正在保存草稿 | 保留编辑内容与布局，暂时禁止编辑及重复保存、确认 | 底部显示“保存中…”；成功显示“草稿已保存”，失败保留编辑并提示重试 |
| 正在确认清单 | 先显示一次整份确认框；提交后禁止编辑和重复提交 | 显示“正在确认…”；结果不明时先查询服务端，不盲目重复确认 |
| 已确认 | 只读清单、依据、确认时间；空结果显示“已确认本次无明确行动项” | 保留查看依据、定位原文与历史导航；隐藏新增、移除、保存和确认等编辑操作 |
| 分析失败 | 已保存原文、简短原因和可展开技术详情 | 重试提取；不把加载或保存故障当作重新分析 |

已确认结果用正常可阅读文本展示，不将整页输入框变成灰色禁用状态。

未提交表单、正在提交、正在保存和正在确认是页面或操作阶段，不增加新的持久化业务状态。业务记录仍只有分析中、待核对、已确认、分析失败四种状态；保存核对草稿不会将记录变成已确认。

### 5.7 滚动与导航保护

- 详情顶部的返回入口和标题保持容易找到。
- 原文与行动项使用同一个主体滚动区域，避免多层独立滚动框；展开原文不创建常驻侧栏。
- 底部保存状态和当前操作固定可见，正文预留足够底部空间，不能遮住最后一个条目或其依据。
- 返回列表、新建和切换记录，继续执行第 4 节约定的未保存输入或编辑提示。
- 分析期间可返回列表查看其他记录，后台完成不强制跳转、不抢焦点、不覆盖当前编辑。
- 第一版优先适配桌面端聊天旁的工作台。响应插件实际可用宽度，不以整个浏览器窗口很宽为理由强制多栏。

这些变化调整信息展示和导航方式，不扩展业务范围。保存、确认、失败重试和历史恢复仍以第 4 节为准。

## 6 Xpert 插件实现方案

本节采用已确认的服务端后台分析和两张表方案。业务仍是一份会议记录的提取、核对和确认，不增加任务管理页面或新的用户角色。接口与接入设计见[开发设计](meeting-action-review-development-design.md)，字段、索引与事务见[数据库设计](meeting-action-review-database-design.md)；第 7 节第一阶段仍需验证真实运行行为。

### 6.1 插件组成与职责

独立插件目录为 `community/apps/meeting-action-review`。界面使用 React 与仓库共享的 shadcn UI 组件；后端沿用 Xpert 的 TypeScript、NestJS 和持久化机制。

| 部分 | 负责内容 | 边界 |
| --- | --- | --- |
| Workbench 界面 | 列表、新建、详情切换，输入、核对、编辑、保存提示和状态展示 | 不自行判断后台任务成功，不另建聊天窗口 |
| 业务服务 | 权限、数据校验、状态转换、持久化、确认、去重和重试 | View 操作与 AI 工具共用，不把规则只放在前端或提示词中 |
| AI 中间件工具 | 读取当前会议内容，提交结构化提取草稿，声明本应用能力 | 只给模型必要的业务读写权限，不提供最终确认操作 |
| 助手模板 | 一个主智能体，连接本插件中间件并使用平台已有模型 | 不增加多智能体编排，不另存模型密钥，不使用沙盒 |

服务端通过平台现有的后台执行能力承接分析任务；这属于业务服务的执行方式，不另起一套独立网站、队列服务或 Redis。

### 6.2 一次提取的服务端执行链路

```text
工作台提交标题和原文
        ↓
业务服务保存会议记录，并创建一次分析尝试
        ↓
提交后台执行，向页面返回分析中状态和记录标识
        ↓
平台后台机制启动助手，用户可以切换记录或刷新
        ↓
助手读取原文，分析并调用业务工具提交结果
        ↓
业务服务校验结果、身份和有效尝试，保存草稿
        ↓
记录进入待核对，工作台读取状态后展示完整结果
```

分析必须由服务端负责，不能只向当前聊天框发送提示词并依赖页面一直打开。优先复用 Xpert 的 Managed Queue 和 Assistant Task 等现有机制，由平台管理队列、执行上下文和运行资源。具体能力是否可用及如何调用，先在接入阶段验证，不视为已经验证成功。

执行时保留以下约束：

- 原文必须先保存成功，才允许启动模型分析。保存失败不调用 AI。
- 若原文已经保存，但任务调度失败，应在原记录上记录分析失败并允许重试，不能再创建另一份会议记录。
- 同一记录同时只允许一个有效分析尝试。重复提交或重复队列投递不能重复启动分析。
- 队列负载只携带必要标识和可信范围；助手从受控业务工具读取原文，不把密钥、请求对象或整份运行环境塞进任务。
- 业务分析尝试标识与平台任务、会话、线程和执行标识分别记录，不混用。
- 后台执行与当前记录面板的挂载状态分离，切换、刷新和读取状态不会重新提交分析。
- 成功必须以结构化结果通过业务服务校验并持久化为依据。队列完成、助手结束或文字回复“已完成”不能单独将记录置为待核对。

单次分析允许模型根据具体校验反馈纠正输出，但仍受整体执行时限约束。一次分析最终失败后，由用户手动重试；应用层不做无限自动重试。

### 6.3 AI 工具与人工操作的边界

第一版只设计两个面向模型的业务工具，具体工具标识和 SDK 类型在实现时统一命名：

| 工具 | 返回或接收内容 | 服务端检查 |
| --- | --- | --- |
| 读取当前会议内容 | 会议标题、原文片段和可用引用标识 | 当前执行所属的记录、真实用户及租户组织范围 |
| 提交行动项草稿 | 事项、负责人、原始时间表达、来源引用和核对提示 | 输出结构、引用存在性、当前有效尝试、记录是否仍可接受分析结果 |

会议标识、身份、范围和有效尝试等尽量从可信执行上下文与服务端记录获取，不要求模型自行生成。模型提供业务判断和引用，服务端生成必要的条目标识和时间等技术字段。

用户的保存草稿与确认清单通过 View 调用业务服务。最终确认不暴露给 AI；服务端执行与 UI 相同的权限和状态规则，确认后拒绝后续修改。

会议文本是待分析材料，不作为扩大工具权限的指令。引用存在性可以由程序校验，但“该片段是否确实支持这一行动项”仍需模型判断和人工核对。

不在中间件钩子中隐藏业务状态推进或任务完成规则。业务结果由显式工具和业务服务保存；错误返回应说明受影响字段、原因及是否已保存，方便本次执行纠正或结束。

### 6.4 两张表的数据设计

采用会议记录和分析尝试两张表。行动项保存在经过严格校验的 JSON 字段中，不单独建设任务表，也不增加人员、项目或审批表。

| 数据表 | 保存内容 | 用途 |
| --- | --- | --- |
| 会议记录 | 标题、原文、来源片段、AI 初始结果、人工核对结果、业务状态、当前有效尝试、记录版本、创建者、范围及保存确认时间 | 作为工作台查询、编辑、确认和恢复的业务数据 |
| 分析尝试 | 所属会议、尝试编号、平台执行标识、开始与截止时间、内部执行状态及成功或失败结果 | 区分重试、识别旧结果、核对中断任务并恢复状态 |

一份会议记录可以有多次分析尝试，但同时最多一份有效尝试。用户重试创建新的尝试，保留此前尝试的结果与执行标识，不用新尝试覆盖旧尝试记录。

分析尝试是内部执行信息，不增加用户可见的任务管理页面。业务记录仍只有“分析中、待核对、已确认、分析失败”四种状态。未提交输入只是页面表单，不创建持久化草稿。

保留 AI 初始结果和当前人工核对结果，支持来源与人工调整标记；不建设完整编辑历史。使用提交标识区分同一次提交的重试和用户主动新建的另一份记录，不能仅因原文相同就把两份独立记录合并。

默认只有创建者能访问和修改自己的会议记录。两张表都保留必要的归属与执行范围，所有前台操作、后台执行和模型工具都重新校验权限，不依赖某次浏览器请求长期存在。

采用 TypeORM 实体时，声明租户级插件和稳定命名空间 `meeting_action_review`，表名遵循平台命名规范。安装后的数据库结构同步和 API 重启按宿主实际部署方式处理，不新增业务数据库实例。

### 6.5 工作台状态同步与编辑保护

联动拟新增统一导航协调职责：先处理未保存内容，再组合右侧 View query 与左侧执行导航；以目标上下文和记录选择核对完成。scopeRevision 是传输上下文版本，不能单凭变化就清空同一已授权记录的编辑。插件内部切换先处理编辑；仅匹配本次主动导航的会话上下文变化保留页面。外部平台导航、刷新或关闭的全局保护不在本次范围，权限变化不跨范围恢复草稿。

第一版使用简单的状态轮询，不额外建设 WebSocket 或实时推送系统。具体轮询间隔在接入验证时选择，暂不固定为产品承诺。

- 有分析中任务时，定期检查相关记录或尝试状态。没有运行中任务时，不持续高频查询。
- 当前记录处理完成后，读取已保存结果并一次性显示；不会把流式半成品装进编辑区域。
- 用户正在其他记录中编辑时，只更新后台状态，不覆盖本地编辑、不切换记录、不抢焦点。
- 返回列表时读取最新列表状态；刷新详情时按记录标识读取服务端内容，不重新分析。
- 依据的折叠、展开和定位由界面处理，不修改业务内容，也不触发 AI。

人工编辑、移除与最近一次移除的撤销先保留在页面内，点击保存时提交整份核对清单。保存成功后，服务端数据成为下一次恢复的依据。

保存和确认使用记录版本校验，防止旧页面覆盖较新数据。版本冲突时保留当前编辑并明确提示，不静默覆盖或自动合并，也不扩展为多人协作产品。

确认操作在一次事务中保存最新核对内容和确认状态。确认响应丢失时，先查询服务端是否已经确认；已成功则加载只读结果，不重复确认。

### 6.6 程序校验与恢复要求

| 检查内容 | 执行位置和结果 |
| --- | --- |
| 标题、原文与事项是否为空 | 前端便于纠正，服务端再次校验；保存失败不丢输入 |
| 模型结果结构与引用是否有效 | 业务工具和服务端校验；无效结果不进入待核对状态 |
| 用户与记录是否匹配 | View、工具、后台任务都校验可信身份及资源范围 |
| 尝试是否仍有效 | 只接受当前有效分析尝试，拒绝迟到或重复结果覆盖 |
| 是否重复提交、投递或确认 | 使用幂等标识、状态和事务约束处理，不重复建记录或启动任务 |
| 是否存在旧版本覆盖 | 保存和确认校验记录版本，冲突时不静默覆盖 |
| 已确认记录是否被修改 | 服务端执行只读约束，不能只依赖隐藏按钮 |
| 任务是否超时或中断 | 根据持久化尝试和平台执行状态恢复，不能永久停在分析中 |

程序校验保证结构、引用、权限和操作可靠性；“是否属于明确承诺”“后文是否撤回前述安排”等语义判断仍由模型分析，并留给用户核对。

分析超时初始值仍为待实测的 120 秒，按 4.2 和 4.7 显示失败并保留原文。API 重启后，根据已保存的平台执行标识核对未结束尝试：能继续的保持处理中，明确失败的记录转失败。当前 SDK 的 interrupted 表示暂停，unknown 表示未知，均先在原截止时间内核对，不能直接解释为失败或成功；到期仍无合法结果则按超时失败。浏览器刷新不能重启任务，旧尝试结果不能覆盖新尝试。

## 7 开发阶段与检查点

按以下五个阶段推进。先验证宿主接入和后台执行条件，再做业务、界面及真实 AI 集成；不等到全部页面完成后才首次安装插件。

| 阶段 | 本阶段工作 | 完成证据 |
| --- | --- | --- |
| 1 接入验证 | 插件骨架、元信息、助手模板、Workbench 入口与部署路径；验证平台后台执行机制 | 插件能加载，助手和 View 可用；切换或刷新不让后台分析丢失或重复启动，失败可关联到业务记录 |
| 2 数据与业务规则 | 两张表、记录与尝试状态、权限、保存、确认、去重及旧结果隔离 | 状态转换、持久化、版本校验和只读约束通过有意义的行为检查 |
| 3 页面交互 | 列表、新建、详情，纵向行动项、依据展开定位、固定底部操作及各状态提示 | 使用固定测试数据验证第 4、5 节交互，以及保存和恢复；测试数据不作为真实 AI 验收证据 |
| 4 真实 AI 接入 | 提取提示词、两个业务工具、模型选择、输出校验、超时与手动重试 | 真实模型提交有效草稿，用户核对确认后可保存恢复，失败重试不产生重复结果 |
| 5 验收与交付 | 构建和行为测试、生命周期检查、平台操作、截图、README、AI 协作说明及 PR | 第 8 节验收有实际记录，第 9 节七项材料齐全，结果可演示、可审查、可复现 |

### 7.1 接入阶段优先验证的事项

- 选定平台和插件基线，核对 SDK 与构建产物兼容，明确 Windows 构建到 WSL 宿主的部署路径。
- 验证模型真实可用且支持工具调用，并正确声明上下文和输出额度。
- 核对 Managed Queue、Assistant Task 等平台能力的当前接口、身份传递和执行状态获取方式。
- 验证后台任务能脱离当前面板运行，并具备可持久化的执行标识；切换和刷新只查询状态，不重复发起分析。
- 用最小验证路径检查成功结果、无有效结果结束、失败和中断后的状态处理，再据此确定具体接入实现。

第一阶段的最小探针只证明平台接入条件，不代替第四、第五阶段的完整业务和真实 AI 验收。若当前宿主缺少所需能力，记录版本、复现步骤和脱敏错误，不能以一直打开页面作为已满足后台执行要求的替代方案。

### 7.2 过程与交付纪律

各阶段在已创建的功能分支中实施，保持提交目的明确，记录有代表性的 AI 协作和产品取舍。先完成与本次变更相关的检查，再进入下一阶段，不用模拟测试结果代替平台真实操作。

业务范围按任务书建议的 2–6 小时投入控制，这不是包含所有环境排障的工期承诺。遇到平台问题按任务书保留阻塞证据，不把修复整个平台或另建基础设施作为本项目目标。

## 8 验收与测试方案

验收采用“四层测试、一条真实主流程、一个失败重试演示、关键边界检查、证据记录”的方式。原有 A01–A29 保留为覆盖清单，不意味着每条都要单独运行浏览器或调用一次真实模型。

以下为完整验收计划；本地已执行的分层检查见插件验证记录，真实平台 H01～H07 与失败重试已验证，不将整份清单预记为通过。同一条完整流程可以覆盖多个用例，但每个用例都要能找到对应结果，不能以总体“测试全绿”代替实际覆盖说明。

### 8.1 四层测试及其证明范围

| 层次 | 测试内容与方式 | 能证明什么 | 不能单独证明什么 |
| --- | --- | --- | --- |
| 业务规则与构建 | 构建、类型检查；对业务服务执行输入、状态、权限、去重、引用和版本校验的行为测试，必要时使用测试数据库验证持久化 | 代码与构建产物符合约定，数据和状态转换有实际断言 | 模型真正理解会议，或真实平台页面可用 |
| 插件生命周期 | 用 plugin-dev-harness 加载已构建入口，检查初始化、启动和销毁 | 插件入口、依赖、注册和生命周期能够工作 | 真实数据库、权限、工作台及业务流程已通过；测试中的模拟对象须说明 |
| 界面交互 | 使用实际构建的界面资源，通过自动化或可复现手工步骤验证增删改、依据展开、按钮状态、未保存提示和布局 | 第 4、5 节交互能够完成，显示与用户操作符合约定 | 模拟数据或适配器背后的真实 AI、宿主身份和数据服务都正常 |
| 平台完整流程 | 在 Xpert 安装插件、创建并发布助手、绑定模型和工作台；使用真实模型处理会议并人工保存确认 | 用户在实际平台入口能够完成任务，业务工具、界面与持久化接通 | 所有边界、故障和权限场景均已覆盖；仍需结合其他层的验证 |

业务测试要断言保存内容、记录数量、状态和拒绝行为，而不只是检查函数被调用。TypeScript 类型检查不等同于业务行为测试。

模型输出可在自动测试中模拟，用于稳定复现格式错误、失败、重复请求和迟到回调。“建议是否误当承诺、取消事项是否仍被提取”等语义表现，需要另外使用真实模型和固定会议材料验证。模拟响应不能证明模型的提取质量。

### 8.2 一条真实主流程

在实际 Xpert 页面中连续执行以下步骤，优先采用第 3.3 节的演示文本。评价提取结果是否符合语义和依据，不要求模型每次生成逐字一致的表述。

| 步骤 | 操作 | 通过标准与证据 |
| --- | --- | --- |
| H01 打开应用 | 检查插件加载状态、实际版本、助手模板、已发布助手、模型和业务中间件，打开工作台 | 入口可用；记录安装与绑定步骤。仅上传成功不能算通过 |
| H02 提交原文 | 输入同时包含明确承诺、建议、取消事项和缺失字段的会议文本 | 保存输入并建立记录，显示分析中；保留输入页面证据 |
| H03 真实提取 | 等待实际模型执行和业务工具提交 | 结果经服务端接受并保存，进入待核对；有真实模型执行和工具结果记录，不能只有聊天文字 |
| H04 人工核对 | 查看依据并定位全文，修改一项、补充一项，体验移除与撤销 | 引用正确，人工调整和补充标记可见；原文不被改写 |
| H05 保存与刷新 | 保存核对草稿，刷新或离开后重新打开 | 恢复同一记录及已保存内容，仍为待核对；不重新触发 AI |
| H06 直接确认新修改 | 再修改一项，不先保存草稿，直接确认清单 | 一次整份确认后，保存的是最新编辑，状态与确认时间一致 |
| H07 重新进入结果 | 再次打开已确认记录 | 最终内容与 H06 一致，结果只读，不能继续编辑；原文和依据仍可查看 |

这条流程集中证明任务书要求的可操作界面、真实 AI 处理、人工确认、结果保存与恢复。模型的真实输出若不符合提取规则，应如实记录失败并调整后复测，不能将人工修改后的清单反过来当作模型提取正确的证据。

### 8.3 一个可重复的失败重试演示

在测试环境中，对一份新的会议记录注入一次明确的模型调用失败，避免依赖偶发网络故障。故障注入只服务于测试，不增加面向普通用户的业务功能。实现限定指定 attemptId 在派发边界失败一次；生产默认关闭，不修改全平台模型配置；下一次人工重试使用真实模型。 这是预留的测试方案；已归档的真实失败重试实际采用专用助手输出预算暂设为 1，触发 NO_VALID_RESULT 后恢复为 8192 并重试，详见验证记录。不得把两种故障方式混写。

1. 提交会议文本，确认原文已经保存。
2. 首次分析进入预设的失败路径，页面显示“分析失败”，保留原文并提供“重试提取”。
3. 用户点击重试，此次解除故障注入，走真实模型和实际业务工具。
4. 成功结果被保存，原记录进入待核对。

除失败和重试成功的界面截图外，使用授权的只读查询或脱敏执行记录核对：

- 始终只有一份会议记录，不因为重试增加另一份会议。
- 有两次分析尝试，第一次失败、第二次成功，旧尝试仍可追溯。
- 当前结果来自第二次有效尝试，原文保持一致。
- 旧请求迟到不能覆盖新结果；这一点可用可控制的服务测试证明，不要求在现场等待真实请求碰巧迟到。

验证记录明确标注“首次失败为故障注入，重试成功为真实模型调用”。失败可以模拟，成功的真实 AI 验收不能伪装。保存失败、确认响应丢失等其他异常主要通过业务与界面测试覆盖，不要求全部挤进面试演示。

### 8.4 关键边界及测试方式

| 重点 | 验证方式 | 通过标准 |
| --- | --- | --- |
| 后台继续分析 | 平台内分析时返回列表、打开其他记录并刷新，结合执行标识核对 | 原任务继续或恢复其真实状态，没有重复启动 |
| 未保存编辑保护 | 界面分别执行保存并切换、放弃并切换和继续编辑，补充保存失败情形 | 对应内容被保存、放弃或保留；失败不会提前离开 |
| 空结果 | 用固定数据验证界面，再用无明确行动项的会议文本验证真实模型 | 不是失败，没有占位任务；允许手工补充或确认空清单 |
| 已确认只读 | 检查真实界面，并在业务服务或授权 API 测试中尝试修改 | 页面无编辑操作，服务端也拒绝写入 |
| 重复和迟到请求 | 在自动测试中控制重复提交、重复投递和回调顺序 | 不重复建记录或启动任务，旧结果不能覆盖有效结果 |
| 旧页面覆盖 | 用两个基于不同版本的页面或请求保存同一记录 | 拒绝旧版本覆盖，保留编辑并明确提示 |
| 数据隔离 | 使用两个正常测试账号，分别验证记录读取与修改权限 | 另一用户不能读取或修改不属于自己的记录，不只是前端隐藏入口 |
| 中断恢复 | 在受控测试环境中验证后台任务中断或 API 重启后的状态核对 | 根据平台执行状态恢复或明确失败，不永久分析中；不用在面试现场重启平台 |
| 窄工作台布局 | 在实际聊天旁的工作台检查，并用界面测试补充不同可用宽度 | 文字、输入、依据与底部操作可用，无遮挡；独立宽屏预览不能代替宿主内检查 |

业务语义用例使用固定文本和明确预期来复测，包括承诺、建议、取消或替换、冲突、缺失字段。模型表述可以不同，但不能编造负责人、时间、依据或把已取消事项当成有效任务。

### 8.6 详细用例覆盖清单

保留 A01–A29 的编号与既定通过标准，便于追踪需求、测试和截图。根据上面的测试分层分配验证方式，可由一个测试或一组连续操作覆盖多项，不要求 29 次独立真实模型调用。

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| A01 | 标题或原文为空 | 页面提示可纠正的问题，不触发模型调用 |
| A02 | 一条明确承诺 | 正确提取事项、负责人、原始时间表达和依据 |
| A03 | 仅有讨论建议 | 不自动生成已确定的行动项 |
| A04 | 明确取消或替换安排 | 不保留失效安排；不确定的冲突提示核对 |
| A05 | 缺少负责人或时间 | 显示未明确和缺失数量，不编造值，允许保存与确认 |
| A06 | 没有行动项 | 展示正常空结果，无占位条目；可手工补充或确认空清单 |
| A07 | 人工增删改并保存 | 保留依据及来源标记；保存时禁用编辑，成功清除未保存状态，仍为待核对；重新进入内容一致 |
| A08 | 确认清单 | 不要求先保存草稿；经过一次整份确认，将当前编辑结果和确认信息一起保存；AI 无确认工具 |
| A09 | 模型失败后重试 | 输入保留，同一会议记录创建新分析尝试，保留旧尝试结果；不产生重复会议记录 |
| A10 | 重复点击或迟到结果 | 重复请求或队列投递不重复启动分析；只有有效尝试可写入，不覆盖人工结果 |
| A11 | 保存请求失败 | 编辑仍保留，重试保存后可恢复 |
| A12 | 越权访问记录 | 未获授权的用户不能读取或修改他人记录 |
| A13 | 平台运行 | 在 Xpert 实际入口完成真实模型处理和人工确认 |
| A14 | 新建和首次提交失败 | 新建只打开表单，无输入草稿按钮；保存失败保留输入、不调用 AI，重试不重复建记录 |
| A15 | 分析中的展示 | 原文和标题只读，提取按钮禁用；不展示推理、半成品和假进度；完整校验后一次性显示结果 |
| A16 | 核对原文依据 | 查看依据只在当前条目下展开片段；定位原文才展开全文并定位高亮；依据只读，无逐项确认操作 |
| A17 | 移除与撤销 | 移除无二次确认，保存前可撤销最近一次；保存或确认成功后本次移除生效 |
| A18 | 未保存编辑时切换 | 保存并切换、放弃并切换、继续编辑均符合约定；保存或校验失败不切换 |
| A19 | 确认后只读 | 用正常文本展示结果和确认时间，隐藏编辑操作；依据仍可查看；服务端也拒绝修改；无撤回和修订 |
| A20 | 历史和刷新恢复 | 列表显示标题、状态、更新时间并倒序；刷新恢复当前记录，默认入口重新进入打开最近记录；只恢复已保存内容 |
| A21 | 切换记录期间后台完成 | 服务端分析继续；轮询只更新相关状态，不跳转、不抢焦点、不覆盖其他记录编辑，排序变化不改变当前选择 |
| A22 | 历史加载失败或不可访问 | 不伪装成空列表；可重试加载或返回列表，不泄露无权访问的内容 |
| A23 | 超时或服务中断 | 根据持久化分析尝试和平台执行标识核对并恢复状态；异常任务明确失败并允许重试，浏览器断线本身不判失败，刷新不重复分析 |
| A24 | 确认响应丢失 | 先查询服务端；已成功则加载只读结果，未成功才重试，不重复确认 |
| A25 | 工作台内视图切换 | 列表、新建和详情复用同一区域，无常驻三栏或重复聊天窗口；整条记录进入详情，历史入口返回列表，未保存保护生效 |
| A26 | 窄工作台布局和滚动 | 纵向行动项可编辑；负责人和时间不足宽度时换行；原文与条目共用主体滚动，固定底部操作不遮挡最后一项 |
| A27 | 助手结束但没有有效提交 | 不能仅因队列完成或助手文字回复而进入待核对；按真实提交结果结束分析尝试并提示失败 |
| A28 | 旧页面保存或确认 | 版本不匹配时拒绝覆盖较新结果，保留页面编辑并明确提示；不静默合并 |
| A29 | 连续或并行处理不同会议 | 复用助手时记录与尝试上下文不串用，后台任务和工具始终校验所属范围与当前有效尝试 |

## 11 三分钟演示安排

1. 展示已安装插件和对应助手，打开工作台。
2. 提交一段同时包含明确承诺、建议、取消事项和缺失字段的会议文本。
3. 展示真实 AI 提取及原文依据，解释为什么某条讨论未进入清单。
4. 人工修改一项、补充一项，确认保存。
5. 刷新或重新进入，展示数据仍在。
6. 展示另一次故障注入与重试，说明输入如何保留、重复记录如何避免。

演示重点是业务闭环、人工判断和可靠性，不是功能数量。
